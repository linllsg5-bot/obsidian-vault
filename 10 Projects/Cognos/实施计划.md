# Cognos：第一阶段实施计划

> 当前已经可以动手，但不是按“先把某个 AI 计划全部实现”的方式动手。每阶段只固定足够支撑下一次真实回撞的部分。阶段状态与下一步只以 [[10 Projects/_状态板]] 为准。
>
> **2026-08-15 校正：下方 Phase 0—5 保留为项目如何走到这里的形成史与旧脚手架，不再作为必须顺序执行的瀑布路线。当前推进由真实运行暴露的断裂触发。**

## 2026-08-15 当前运行计划

### 当前主工程：第一组织切片

第一发生场已经从“一个人 + 一个 Codex runtime”推进到可选择 Codex / Gemini runtime，并已开始真实沟通。下一刀不再是继续完善单点聊天壳，也不先实现完整 Space / Position / Memory / Consensus 模型，而是让**多个不互相替换的持续参与者第一次在同一发生场共在**。

当前最小目标：

```text
同一发生场
├── 小林
├── Codex participant → 自己的 runtime continuity
└── Gemini participant → 自己的 runtime continuity
```

第一版只要求：

1. **Participant 与 Model / Runtime 分离**：参与者不是一个模型字符串；runtime 是其当前运行身体之一。
2. **切换不等于替换**：与 Gemini 说话后，Codex 仍作为另一个参与者持续存在，反之亦然。
3. **各自连续性不被抹平**：Codex thread 与 Gemini session 分别保留，不把两者强塞进一条伪统一模型历史。
4. **发生明确归属**：新发生至少能稳定指向 author participant、时间、内容、reply/reference 与 runtime ref；这些是当前运行引用，不预先定义主体本体。
5. **最小邀请而非自动编排**：小林可以显式让一个参与者面对另一个参与者留下的发生；暂不做自动多 Agent 轮询、中央调度器或固定角色系统。

最小真实验收：

```text
小林 → Gemini
Gemini → A

小林 → Codex，并让其面对 A
Codex → B

小林 → Gemini，再让其面对 B
Gemini 保留自己的先前连续性，同时面对后来发生的 B
```

这一验收只证明：**多个具有不同 runtime continuity 的参与者可以在同一发生场中共同面对发生。** 它不自动证明“主体”“空间”“位置”已经被实现。

### 观察线：继续真实使用第一发生场

第一发生场不再以“测试聊天是否能工作”为主，而作为真实运行现场继续使用。2026-08-15 的 Gemini 沟通已经产生了新的材料：快速把未定局面组织成完整解释、被校正后回看自身上一轮判断、关于疑惑/目的/空间的进一步讨论。

这些材料当前只作为**发生与候选认识**保存：

- 不把“模型天然伪造完整性”升格为已确认命题；
- 不把“疑惑形成空间”写成机制定论；
- 不因为出现新概念就立刻创建 `doubt`、`position`、`unknown` 等 schema；
- 如果某种现象真正阻塞后续组织运行，再由它触发最小工程探针。

### 基础设施线：conversation / lineage 保持边界

会话/发生基础设施继续保留 hard occurrence、runtime ref、来源与 lineage，但不为了“先完成基础设施”而阻塞组织切片。

第一组织切片会反过来制造更真实的 lineage 问题，例如：

- 同一个 occurrence 被多个 participant 面对或引用时，什么在持续？
- 不同 runtime session 怎样参与同一沟通？
- transfer、continuation、re-entry 在真实跨参与者使用里分别表现为什么？

等这些发生后，再补相应的 lineage 结构。

### 触发式探针（不再占据线性主路线）

以下探针保留，但只有在真实运行触发时进入：

- **来源查询 / 历史重读**：当参与者真实出现“东西都在但读不对 / 来路缺失”时进入；不预建通用 `query_sources()` / `SourceManifest` 体系。
- **撤销错误对象化 / migration probe**：当旧解释开始真实阻碍当前运行时，以 ex.1 “那根本不是什么尝试”为硬样本验证发生不灭、旧解释可查、当前对象身份可撤销；不先建通用 ontology migration framework。
- **P1 Navigable Trace**：继续可运行，但只验证外部可导航历史；不验证 Position。
- **P2 Persistent Position / P3 Viewpoint Exteriorization**：等待出现能够区分 runtime continuity、history、position、view 的真实运行条件，不再要求按编号排队执行。

### 当前禁止抢跑

暂不因为已有讨论就实现：

- 固定 `Space` 表 / 关系枚举；
- 固定 Position / Role 字典；
- 自动多 Agent orchestration；
- 中央“Cognos 总控大盘”；
- 三层上下文作为强制架构；
- 把疑惑、未闭合、空无等候选认识直接字段化；
- 为了统一不同 runtime 而抹掉其各自连续性。

> 当前唯一的工程主刀是：**让同一个发生场里第一次真正出现两个不互相替换的 AI 参与者共在。**

### A. 第一组织切片 —— 当前主工程

**目标**：从“小林 + 一个可切换的 Assistant 后端”推进到“同一发生场内多个具有独立连续性的 Participant 共在”。

**最小实现原则**：
1. **Participant 与 Model/Runtime 分离**：
   - 不把模型直接等同于身份；
   - 参与者是 `participant_id`（如 `codex-1`、`gemini-1`），各自绑定独立的运行时连续性（Codex thread / Gemini session）。
2. **切换不等于替换**：
   - 和 Gemini 对话并不抹掉 Codex 的位置；
   - 两者同时存在于同一个发生场。
3. **独立运行连续性**：
   - Codex participant 拥有自己的 `thread_id`；
   - Gemini participant 拥有自己的 `session_id`；
   - 互不覆盖各自在运行时内部的连续轨迹。
4. **明确发生归属**：
   - JSONL 准确记录 `author_participant_id`、`content`、`in_reply_to` 与局部的 `runtime_ref`。
5. **极简手动定向邀请（绝不做自动 Agent 轮询）**：
   - 小林在发生场中手动指定或 `@Participant` 对话；
   - 系统将相关发生带给被邀请者，由其生成回应并保留其独立连续性，重新落回同一发生场。

**验收标准**：
```text
小林 + Codex + Gemini

1. 小林 → Gemini
   Gemini → 回复 A（记录为 gemini-1 发生）

2. 小林 → Codex（引用或带入回复 A）
   Codex → 回应 A（记录为 codex-1 发生，保持 Codex 自身连续性）

3. 再次呼叫 Gemini
   Gemini 仍保持自己先前的连续性，同时能面对 Codex 后来产生的新发生
```

以下原定阶段降级为“按现实阻力触发的局部探针”，不再作为排期瀑布流：

- **重入与位置探针 (Position / Re-entry Probe)**：仅在特定参与者连续性真实断裂时触发。

## 历史实施谱系（Phase 0 — Phase 5 归档与演化）

范围：

- 建立第一层、第二层、工程候选、决策残余和来源之间的明确边界。
- 从 ex.1—3 核对说话人、确认、默许、候选和否决；不再只信标注标签。
- 给未来文档使用 `source_role` 与 `epistemic_status`，避免 AI 提案静默升格。
- 保留 raw 的权威地位；处理重复副本与敏感信息时不破坏可追溯性。

验收：新 AI 能说清哪些是小林确认、哪些只是方案候选；不会把 `subject_level`、五对象模型或某个技术栈说成已定。

## Phase 0B：Codex Runtime Adapter 探针（已验收）

只验证一条外部运行链，不提前建立 Cognos 本体数据模型：

1. 通过官方 Python SDK 控制本地 Codex app-server。
2. 使用 ChatGPT 登录，不使用模型 API Key；当前账户未启用 device-code，因此采用标准浏览器 OAuth。
3. 创建 thread，保存用于恢复的 `thread_id`，并让每次回复带回精确 `turn_id`；最终文本只是该次发生的一个投影。
4. 第一阶段强制只读 sandbox；状态文件不保存 token 和对话正文。
5. 旧 `models.py / database.py / test_phase1.py` 冻结保留，不在其上继续堆功能。

验收：两个独立进程得到相同 `thread_id`，第二轮能准确取回第一轮标记；每次回复有可引用的 `turn_id`；单元测试覆盖创建、保存、恢复、损坏状态与缺失 turn 引用。

2026-08-13 结果：标准 ChatGPT 浏览器 OAuth 成功；两个独立进程均使用 thread `019ff791-3c1a-76a1-b6ec-4b1125e2388a`，第二轮从历史取回 `COGNOS-PHASE0-A`。折返后 adapter 已暴露 SDK 的精确 `turn_id`，4 项无网络测试通过。

## Phase 1：从现有实现内部折返，再做连续性回放

这一阶段不是 ex.1—3 完成后的新哲学分析，也不先发明一个总结构容纳新认识。先把当前实现重新作为认识对象，回答：

1. 现有代码在哪里已经把 schema、主体边界、对象/关系/事件类型或上下文形态预先固定？
2. 哪些结构只是最小接口或局部投影，实际上仍允许后续展开？
3. 一次原始发生怎样获得稳定引用，使之后的解释可以改变而不覆盖原发生？
4. 重放 ex.2 数学探针时，哪些材料实际缺失、怎样被重新查询；不能先假定答案必然是三层或五块快照。
5. 当真实回路要求一个新结构时，怎样同时保留它的来源、适用空间和可重新打开条件？
6. 一件当前模型无法充分表达的发生，怎样在不归入 `other/unknown` 的情况下完整保存，并明确留下“当前建模失败”？
7. 一件被现有模型非常顺利地装错的发生，后来怎样撤销对象化，而不是通过增加 subtype 为旧判断自救？

第一轮折返已经得到两个局部结果：旧根目录固定 schema 冻结为历史实验，不再作为现行模型；Phase 0 的 `RuntimeAdapter` 保留，因为它没有定义 Cognos 本体，但回复必须携带 `turn_id`，不能只剩最终文本。

接着以现有 Codex 运行时做 ex.2 回放。回放先产出可观察的缺失、查询和来源痕迹；`ContextSnapshot` 若出现，只能是读取这些结构的一个当时视图，不是这次认识本身的容器。

验收：能够指出回放中的实际断裂发生在哪里，并沿 thread/turn/来源回到原发生；形成的最小结构来自该断裂，而不是先填一张上下文模板。规格本身必须区分“发生未被表达”与“发生不存在”。

2026-08-13 进度：已实现来源锚定的 `phase1/replay_probe.py`，可逐字读取指定行，记录整文件 SHA-256、实际输入/输出与 thread/turn，并只追加 JSONL；3 项 Phase 1 测试通过。原拟做的 ex.2 第 183 行空上下文基线经小林追问后取消：它只会重复已知失败，不是一次真实沟通，也不再阻塞网页竖切。

## Phase 2：最小沟通竖切（旧脚手架；第一发生场已越过初始验收）

范围（当时）：

- 一个本地 Web 界面。
- 一个空间，一名人类成员，至少一个可调用模型；结构允许第二模型接入。
- 对话原始内容、参与者、时间、引用和模型调用来源清单被持久保存。
- 解释与原始发生分开保存；当前解释改变时不改写原始内容，也不假装新解释在当时已经成立。
- 三层上下文的最小版本；成员可主动查询来源，而非只被动接受拼接。
- 关闭再打开后能继续同一场沟通。

暂不要求：完整关系图、主体梯度、自动多 Agent、固定位置体系、全套任务管理。

验收包含两支：

1. 重放一段 ex.2 数学探针，AI 可以认真处理局部内容，同时知道它为什么属于 Cognos，并把结果重新带回当前空间。
2. 输入一段当前结构装不下的真实材料：`t0` 完整保留发生和建模失败；`t1` 保存带来源的候选解释；结构改变后，`t2` 可以产生新解释，同时仍能看见 `t1` 当时为何成立，旧引用不因新解释而断掉。

第二支优先不用合成材料：采用 ex.1 中“创作特质 → 被识别成 trigger-type Attempt → Reading 全空 → 试图新增 subtype → 小林纠正‘那根本不是什么尝试’”的真实谱系。验收必须允许撤销旧对象身份，而不只是把它迁移成新类型。

### 2026-08-15 第一发生场现状

已完成或越过：

- 本地三栏网页“第一发生场”；
- 小林原文与 AI 原文追加保存到 Obsidian Vault；
- Codex / Gemini 作为可选 Runtime 接入，回复保留 runtime / thread / turn 引用；

- runtime 失败时用户原文仍保留；

原 Phase 2 中“主动查询来源、解释版本、schema migration”等未完成项不再被视为 Phase 2 必须清空的 backlog，已移动到上方“触发式探针”。

## Phase 3：让记忆与关系开始产生行为差异（历史方向，不再等待编号启动）

范围：

- 从对话中提出候选纠正、阶段判断、开放问题和未采纳意见；在沟通中确认或改写。
- 这些变化进入未来上下文，但保留原句、提取者和确认过程。
- 实现“同一对象、两个空间”的关系实验。
- 记录某条关系如何显现：改变了检索、上下文、提醒或下一行动中的哪一项。

验收：旧纠正能在相关情境中生效；换到不相关空间时不会全局污染；关系的差异不只是数据库里多一个 `space_id`。

## Phase 4：调度、学习与位置从沟通中长出（历史方向，不再等待编号启动）

范围：

- 调度以主体联合邀请开始，记录双方从哪里接上、扩展了什么，而不是只写 assignee。
- 位置先记录实际显现的局部视角和承担，不提供固定岗位字典。
- 学习先观察“这次完整展开使之后能看到/能做什么发生了变化”；同时明确当前模型外部记忆与真正主体改变之间的差距。
- 阶段共识带来源、作用域、牺牲和重新打开条件。

验收：至少一次真实沟通使后续行为改变，并能沿记录解释改变从哪里来；不是只新增了一条摘要。

## Phase 5：把自身建设搬进 Cognos（方向已开始提前发生）

旧计划假定 Phase 2—4 骨架足够后才开始自身建设。2026-08-15 的真实使用已经表明，自身建设不会严格等到前序 Phase 完成：第一发生场本身已开始承载对 Cognos 当前局面的讨论，并反过来改变下一步工程计划。

长期方向仍保留：

- 后续架构提案、判断、实现、现实反馈和残余越来越多地在 Cognos 承载中发生；
- 软件代码修改与组织历史互相链接，但不让系统自动修改自己而绕过审阅和测试；
- schema 变更记录触发它的实际发生、旧结构何处失败、新切法牺牲什么以及仍未表达什么。

但不再把“Phase 5”理解为未来某天才开启的单独功能阶段。
