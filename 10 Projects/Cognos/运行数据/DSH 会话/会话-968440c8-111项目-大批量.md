## 1. “解析 dsh 自己的参数”是什么意思？

这里的“参数”不是业务数据，而是 **命令行参数**。

`dsh` 是一个 CLI 启动器，它启动时先要区分两类参数：

```text
dsh --profile web --port 8080
     └─启动器参数─┘ └─app 参数─┘
```

- `--profile web` 是 **dsh 自己的参数**，告诉它：启动哪个 profile；
- `--port 8080` 是 **web app 的参数**，dsh 自己不解析，原样交给 web 插件去解析。

源码里 `lib/bin.js` 做的事情就是：

```text
解析 dsh 自己的 flag
  ↓
识别还剩哪些参数
  ↓
把剩余参数交给被启动的 profile
```

所以“解析 dsh 自己的参数”不是说“参数对应数据”，而是说：

> dsh 先决定“我要启动哪个 harness profile”，剩下的配置和参数再交给 profile 里的应用自己处理。

## 5. “组装 context”这个环节有什么不一样？

这是 DSH 里比较关键的一个设计。

普通 LLM 应用常见的做法是：

```text
把历史消息全部拼起来
  ↓
加上 system prompt
  ↓
发给模型
```

DSH 不是这样。它有一个专门的 `SystemPrompt` 服务，把 context 拆成 **可注册、可排序、可作用域覆盖** 的部分。

看 `dsh-system-prompt` 源码，它有这些注册项：

- `sections`：system prompt 的各个段落；
- `contexts`：动态 runtime context；
- `toolProviders`：工具 schema 提供者；
- `variables`：prompt 变量，比如 `{{cwd}}`。

每个插件 / 每个 agent scope 都可以注册自己的内容。

每次模型调用前，`assemble()` 会做：

```text
合并 global + 当前 agent scope 的注册项
  ↓
按 order 排序 sections
  ↓
收集所有 tool schema
  ↓
按 toolOrder 排序工具
  ↓
渲染变量
  ↓
生成 system prompt
  ↓
触发 system-prompt/assemble 的 waterfall，让其他插件还能再改
```

然后 `preStep` 里还有一个特殊机制：

```text
把动态 context 渲染成一个 snapshot
  ↓
如果和上一次 snapshot 一样，就不重复注入
  ↓
如果变了，作为一条 user message 追加进 session
```

这个 snapshot 的文案是：

```text
Current runtime context. This snapshot supersedes earlier runtime-context snapshots.
```

所以 DSH 的“组装 context”不一样在：

1. **不是简单拼历史**，而是插件化、分节、有序组装；
2. **支持 scope**，不同 agent 可以有不同 context；
3. **工具 schema 也是 context 的一部分**，并且可以排序；
4. **动态 runtime context 是一等公民**，有快照、有去重、有“取代旧快照”的语义；
5. **有 waterfall 钩子**，其他插件可以在真正发给模型之前修改整个 assembly。

这也是为什么 DSH 不是一个“聊天壳”，而是一个可以长出复杂 agent 行为的框架。

## 2. 能否稳定 resume

## 5. 最小 result 输出能提供什么

从 `session.jsonl.zstd` 可以机械提取，不需要模型重新总结：

```json

  "model": "deepseek-v4-flash",

可以直接获得的字段：

- `session_ref` = session id + session log path；
- `commands_run` = 所有 `tool/call` 的 command；

- `files_changed`：

    git status --porcelain
    git diff --name-only
    ```
- `diff_ref`：
  - 跑 `git diff` / 记 commit hash。

**机械导出能力已经存在**：

- Web 有 session export ZIP 端点：
  ```text
  GET /api/session.export?sessionId=<id>&includeDescendants=true
  ```
- 底层 raw log 本身就是完整机器可读事件流。

**需要补的只是两层薄代码：一个 handoff runner，一个 result exporter。**
