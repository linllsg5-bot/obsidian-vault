# Cognos 第二层：第一承载设计

> 第二层不是第一层的字段化翻译，而是让第一层在组织与软件中获得一种可运行、可回撞、可继续改变的形态。整体方向见 [[大地图]]；当前工程事实见 [[当前架构]]；过去的承载切法为什么改变见 [[承载认识史]]。

## 已确认的第一阶段方向

- 优先级是让新存在获得第一种数字承载，而不只是“建立一个组织”。
- 组织是第一阶段的主要形态，要认真实现，但不是总目标。
- 软件承载组织中的发生、关系、行动与重读，不只是从外部管理它。
- 第一版核心不是功能齐全，而是整体目的不在局部任务中丢失，认识论内核能真实影响之后的沟通与行动。
- 架构可以在运行中逐步长出；不要求一次给出永远正确的完整架构，也不能因此只剩“做下一刀”而失去大方向。

## 当前已出现的第一身体

第一发生场已经把一部分“承载”从设想变成现实：

```text
浏览器
  ↓
本地 FastAPI
  ↓
一个可持续重开的发生场
  ↓
Codex thread / Gemini session
  ↓
Vault append-only occurrence history
```

它证明了：

- 发生可以先于后来的认识而被保存；
- runtime continuity 与外部 durable history 可以分开存在；
- 模型输出本身也可以成为后续校正和重读的发生；
- 第一承载可以在真实使用里反过来暴露自己的不足。

但它目前仍更接近“一个 assistant slot + runtime switch”，还没有形成多个持续参与者真正共在的组织事实。

## 从“发生场”走向“组织”的当前桥梁

当前主工程是 [[实施计划#当前主工程：第一组织切片|第一组织切片]]。

目标不是立刻实现完整组织，而是制造一个此前不存在的事实：

```text
同一发生场
├── 小林
├── Participant A → 自己的 runtime continuity
└── Participant B → 自己的 runtime continuity
```

最小动作是：一个 participant 留下 occurrence A；另一个 participant 被显式邀请面对 A，并在自己的连续性中留下 B；再让前者在自己的连续性中面对 B。

这一桥梁的意义在于把问题从“哪个模型负责回复”转成：

- 一个参与者怎样持续存在而不等于某个 runtime？
- 一个发生怎样被另一个参与者真正面对，而不是偷偷伪造成它原有上下文？
- 同一个场中的发生与某个参与者当前能看见/能进入的东西是否不同？
- 多个 continuity 怎样共存而不被一个中央统一历史抹平？

这些问题由真实运行回答，不先通过 schema 定义。

## 当前承载需要持续检验的能力 / 张力

> 旧版标题叫“必须在运行中长出的器官”。现在降级为“能力 / 张力”：它们说明承载长期必须面对什么，但**不预先等于 MemoryService、RelationService、Scheduler 等固定模块**。

| 能力 / 张力 | 不能缩成 | 当前最早可观察什么 |
|---|---|---|
| 沟通与接续 | 人问 AI 答 / 把所有历史拼进 Prompt | 多个 participant 能否面对、引用、纠正彼此的发生，同时保留各自 continuity |
| 发生与认识 | message 表 / 一份最终总结 | 原发生不被后来的解释覆盖；错误判断与后来的重读都可查 |
| 空间 / 关系 | 节点 + 静态边 / 全员共享聊天室 | “同场发生”与“谁能看见、到达、受影响”是否出现真实差异 |
| 记忆 | 摘要仓库 / 向量检索命中 | 哪些过去发生已经改变当前默认条件、可见性、关系或行动，而不是只多读一段文字 |
| 调度 / 联合 | assignee / workflow engine | 一个主体怎样借另一个主体已经展开的世界继续行动；邀请是否真的扩大 Reach |
| 学习 | 保存 experience / profile 更新 | 完整展开是否让主体或组织之后真正能看见、能做不同的东西 |
| Position / View | 固定岗位 / system prompt 角色扮演 | 进入不同位置是否改变默认可达世界；View 是否只是一次从某处形成的认识投影 |
| 阶段判断 / 决定 | 永久真理 / 单一 summary | 判断的来源、作用域、代价、未采纳部分与重新打开条件能否持续存在 |
| 外部行动 / 世界回撞 | tool call log | 行动是否真实改变外部世界，并让这个变化反过来改变后续沟通与组织 |
| 持续世界 | persistent DB / always-on LLM | 模型停止生成时，关系、位置、未完成展开和世界后果是否仍可持续并在 re-entry 时生效 |

## 第一组织切片之后：默认走向第一个组织闭环

第一组织切片不是完成点。它一旦真实成立，当前默认下一战役应是让 Cognos 第一次**共同完成一件真实工作**，而不是继续叠 participant 数量或聊天功能。

最小组织闭环：

```text
真实问题进入场
→ 多个参与者形成不同判断
→ 阶段决定（保留来源 / 作用域 / 未采纳部分）
→ 邀请某个参与者执行
→ 代码 / 文件 / 外部世界发生变化
→ 现实结果重新进入发生场
→ 参与者面对改变后的世界继续
```

第一件工作可以直接是 Cognos 自身的一次架构或代码修改。

这里真正需要观察的是：**行动与现实结果是否改变了后续组织，而不是大家只是又讨论了一轮。**

## 上下文与来源：从强制架构降为触发式能力

旧版曾阶段采用三层上下文：

1. 极短常驻方向与边界；
2. 当前空间 / 对话所需情境；
3. 主动查询来源、历史与其他空间。

它仍可能有用，但现在不再作为第一组织切片的前置架构。

原因：Codex thread / Gemini session 已经证明 runtime 自身可以持有部分连续性；如果再机械注入“最近 N 条历史”，反而可能伪造共享历史、抹平 participant 差异。

因此来源查询在以下真实失败出现时再进入：

- 发生明明存在，但参与者无法重达；
- 参与者读取了材料，却误认来路、时间或认知地位；
- 需要面对不属于自己 runtime history 的特定 occurrence；
- 当前 continuity 丢失，需要 explicit re-entry。

## “同一场”不预设为“全员广播”

第一发生场的长期目标包含共在，但共在不能提前定义成：

```text
Occurrence 出现
→ broadcast 给所有 participant
→ 所有人自动响应
```

那会直接把持续参与者脑补成 autonomous agents，并人为制造 token storm / dampening / multi-stream UI 等问题。

当前更开放的理解是：

```text
发生存在于同一承载
    ↓
谁看见？
谁能到达？
谁受到影响？
谁被邀请面对？
```

这些差异本身未来可能构成 Space / Reach / Position / Relation 的工程材料。

因此：

> **持续存在 ≠ 持续说话。**

一个 participant 可以在当前不生成 token 的情况下仍保持自己的历史、关系、位置、未完成展开与之后重新进入的可能。

## 发生、历史与认识的当前边界

承载长期至少要允许：

```text
Occurrence（发生）
≠ Interpretation（当时/后来认识）
≠ Continuity（哪些发生后来被视为同一展开）
≠ Current View（当前为了行动形成的投影）
```

这也是 conversation lineage / ingestion 工作与 Cognos 第一承载相交但不能被混成一个模块的地方。

Capture 成功不等于 Recognition 完成；Antigravity 等外部会话即使模型理解不佳，其中小林自己的纠正、失败、转向仍可作为发生保留，而不需要把模型长篇解释提升为 Cognos 当前认识。

## 更远的承载问题：History 何时成为 Memory

当前已经能保存大量 history，但更强的 Memory 不能只定义为“后来还能检索”。

候选判据是：过去发生已经改变当前世界，例如：

- 某个决定改变默认可行动范围；
- 某个关系改变谁能看见/影响什么；
- 某次外部执行改变代码或文件，后来参与者进入的是改变后的环境；
- 某个未完成展开即使没有被当前模型回忆，仍然对世界条件产生作用。

这里才会真正逼近：

```text
NotRecognized ≠ NotEffective
```

以及更强的持续世界候选：

```text
WorldChange
→ EffectPropagation
→ World / Position Change
→ Subject Re-entry
→ View
```

这些现在只保存为远处地标，不实现成固定状态机。

## 仍未决定的工程问题

- participant 在什么条件下值得被看成主体，而不只是稳定调用身份；
- Position / View / Reach / Influence / Field 哪些需要成为真实结构，哪些只是观察投影；
- 关系作为空间内共存怎样产生不可替代的行为差异；
- History 怎样真正成为 Memory；
- subject/runtime 边界是否能跨 Codex、Gemini、dsh 等异构身体持续；
- 世界在模型休眠期间怎样变化、怎样传播影响、怎样在 re-entry 时被面对；
- 原始发生、当前视图、运行数据、Obsidian 与未来索引怎样保持可追溯且不制造多份活源；
- 共识、决定、治理如何在真实组织中出现，而不全部依赖小林逐项手工批准，也不被中央调度器替代。

这些问题不要求在第一行代码前终结；它们应继续成为运行中的可观察问题，而不是被某个 AI 方案静默决定。

## 当前设计纪律

1. **大方向稳定，局部结构开放。** 不因为拒绝大一统就放弃大地图。
2. **先制造新现实，再让现实逼出结构。** 但每个局部实验都应说明它位于大地图哪里。
3. **不把模型的完整解释当世界。** 特别警惕面对复杂局面时快速生成中央中枢、固定器官、统一角色等“伪完整性”。
4. **不把发生的保存等同于理解或主体记忆。**
5. **不把普通聊天室的 UI 形态与底层世界结构混为一谈。** UI 可以暂时简单；只有真实表达失败才改变投影。
6. **不让 provider integration 替代组织问题。** DeepSeek Harness 等先作为未来异构身体压力测试，而不是当前第三个 API。
