# Cognos：当前工程假设

> 这里不是“已定架构”。ex.3 结束时，第一阶段方向已经可以开始分阶段动手，但数据对象、技术栈和阶段顺序仍没有最终确认。本文件只保存可验证、可替换的工程候选。

## 已经能约束工程的要求

这些要求不是具体数据表，但后续方案不能绕开：

1. 第一版首先承载**同一空间中的多主体持续沟通**，以及沟通中形成的阶段共识、决定、执行和历史。
2. 架构设计本身要进入沟通；雏形做出后，后续设计逐渐搬进系统内部。
3. 关系依附于空间。关系不是对象之间后来补的一根线，而是对象在空间中共存这一存在的显现。
4. 记忆必须影响未来沟通；不能只有“存了文件”，也不能每次把全部文件机械拼进 Prompt。
5. 每个成员应取得当前需要了解的内容、记录和文件，同时保留必要的全局方向，不假装掌握所有细节。
6. 位置不预先定死；尝试、可能、学习、调度不能被缩成任务管理字段。
7. 历史不得被后来的漂亮总结覆盖；未采纳意见和被跳过部分仍可重新进入。
8. 当前结构装不下的发生可以先完整存在。系统应能承认“当前建模失败”，而不是强制放入 `other/null/unknown`。
9. schema 变化本身需要可追溯：新解释不能回写成过去当时的意义。
10. “顺利装入 schema”也可能是失败。后续必须能够撤销“这个发生就是某对象/类型”的旧认识，同时保留它为何当时看起来合理。

## 候选 A：上下文与记忆

ex.3 后段对三层上下文的评价是“还可以”，因此可作为首轮实验，不是最终协议：

1. **常驻上下文**：极短的总方向、不可压缩边界、当前参与身份。
2. **空间上下文**：空间为何存在、其中的对象、活关系、开放残余。
3. **对话上下文与动态查询**：当前对话，以及按需查询原始会话、项目文件、纠正和历史。

每次模型调用还应保存“实际看见了什么”的来源清单，才能区分没找到、没注入和模型没使用。

## 候选 B：空间—对象—关系投影

`Space / EntityObject / ObjectInSpace / Relation / Movement` 来自 ex.3 的 AI 方案。它与部分确认内容相容，但**尚未被确认为正式数据模型**。

| 候选对象 | 想验证的东西 | 主要风险 |
|---|---|---|
| `Space` | 同一对象在不同空间显现不同共存关系 | 把空间重新做成数据库容器 |
| `EntityObject` | 不把主体类型封死在人与 AI | 用统一表面抹平对象差异 |
| `ObjectInSpace` | 对象可以进入多个空间 | 只记录 membership，仍没有关系存在 |
| `Relation` | 关系有自己的历史、状态和显现 | 虽有 ID，仍只是“边表” |
| `Movement` | 追加记录主体运动留下的痕迹 | 偷偷把事件确立为本体最小单位 |

### `subject_level` 的地位

0—4 级主体化梯度是某个 AI 方案中的实现猜想，不是小林确认的主体理论。小林较明确的是：

- 主体有一定独立性和展开性；
- 是否视为主体有门槛；
- 最小单位是相对的，问题更像“什么在什么情况下不能被忽视、能决定或组成什么”；
- 非人/非 AI 主体的实现放到后续阶段。

因此第一阶段不应先把 `subject_level` 固化进不可逆的数据契约；可以作为实验视图或推导结果。

## 候选 C：存储与技术

- 小林明确偏向第一版以**网页**呈现，并采用 agent 分阶段执行。
- Python、FastAPI、SQLite、JSONL、Markdown、Tauri、Svelte/HTML 等都只在 AI 方案中出现过；小林对技术栈明确表示过“不确定”，并希望继续由 AI 分析优化。
- `JSONL = 历史真相源 / SQLite = 可重建索引 / Markdown = 人类投影` 是 2026-08-13 的 Codex 建议，尚待技术 spike 和重建测试。

### 已进入现实的第一组织切片（2026-08-16 验证通过）

`Playground/cognos/web/` 现在是可运行的第一组织承载身体，而不只是单模型对话框或工程候选：

1. **Participant 与 Runtime 彻底解耦**：
   - 参与者（Participant）是发生场内的工程身份锚点（如 `Gemini`、`Gemini-B`、`Codex`），而不是底层模型 API；
   - 运行时（Runtime）只是参与者当前借用的算力身体（Google Gemini REST API 或本地 Codex App-Server）；
   - 各自持有独立、隔离的会话连续性（`gemini_thread.json`、`gemini_b_thread.json`、`codex_thread.json`），实现 $\text{Field Continuity} \neq \text{Participant Continuity}$。
2. **显式面对已有发生（Occurrence Quoting）**：
   - 任何已有发生可被显式指给另一参与者面对，不伪造其原生历史，也不污染 System 指令；
   - 以结构化的带 provenance 发生上下文（`[来自当前发生场的已有发生] ... [/发生]`）呈现给目标参与者。
3. **发生落盘与溯源**：
   - `AppendOnlyHistory` 把原文实时追加写入 Vault `第一发生场.jsonl`；
   - 精准记录 `id`、`occurred_at`、`author`、`author_participant_id`、`target`、`quoted_occurrence_id` 及局部 `runtime_ref`。
4. **前端三栏极简交互**：
   - 本地 Vendor 库（marked.js + purify.js），零外部 CDN 依赖；
   - 受话方药丸切换（`@Gemini` / `@Gemini-B` / `@Codex`）与消息卡片“引用”一键挂载；
   - 右栏实时呈现空间共在参与者清单及其各自的底层 Thread 状态。

## 2026-08-16：从“运行时切换”到“第一组织切片”的认识折返

这只记录当前真实跑通的代码事实与认识收敛：

| 现有结构 | 折返后的认识 | 当前动作 |
|---|---|---|
| 根目录 `models.py` 声明五种基础实体 | 早期旧工程投影，固定 schema 提前封闭了显现 | 冻结为历史实验；现行代码不予导入 |
| `RuntimeAdapter` 只定义 `send(message)` | 对外部运行时的最小非本体接口 | 保留，并拓展出 `GeminiRuntimeAdapter` 与 `CodexRuntimeAdapter` |
| 单一 Assistant Slot + 模型切换 | 本质仍是单线程流水线中的算力代换，不是多主体共在 | 拆除；演进为多 `Participant` 注册表与独立连续性 Session 隔离 |
| 历史全局广播或硬塞 | 容易导致虚假同步与 Token 爆炸，同一场不等于默认共享全部上下文 | 改为显式定向受话与精准 `Occurrence Quoting` |
| 服务跨进程重启 | Participant 连续性不依赖当前 Web 进程存活 | 验证通过：持久化 thread/session 文件在服务重启后无损恢复 |

这轮没有决定正式 schema、主体边界、关系形态或上下文块。已经具有展开性的地方也不因“仍不完整”而被替换：最小 runtime 边界、外部 thread 的可恢复性，以及候选文件明确标注认知地位，都是后续可以继续重读而无需先封闭世界的结构。

### 数据投影的两项新推断（待真实关系实验）

- 若试验 `subject_level`，更适合放在 `ObjectInSpace` 而不是全局 `EntityObject`：同一对象在不同空间中的主体化程度可能不同。
- 关系不先固定成 `from → to` 二元边；优先试验 `Relation + RelationMember`，以容纳多个对象在同一空间中的共存。关系本身还需要可被引用的对象身份。

因此当前不写“技术栈已采用”。第一轮只要求：本地可运行、Web 可见、历史可追溯、数据可导出、不要把 Obsidian 变成隐藏数据库。
