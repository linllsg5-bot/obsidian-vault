# Cognos：当前工程假设

> 这里不是“已定架构”。它只保存**当前已经成为工程事实的承载、正在验证的局部假设，以及明确不应被误读为本体的技术投影**。过去怎样走到这里见 [[承载认识史]]；整体方向见 [[大地图]]；当前战役见 [[实施计划]] 与 [[10 Projects/_状态板]]。

## 0. 先区分三类东西

### 已经发生的工程事实

- 第一发生场已经真实运行，而不是设计稿。
- 当前 Web 身体位于 `C:\Users\lnp\Documents\Playground\cognos\web\`。
- FastAPI + 本地 HTML/CSS/JS + Vault append-only JSONL 已进入实际使用。
- Codex thread 可以跨进程恢复；Gemini session 也已接入第一发生场。
- 发生可以保存 user / AI 原文、时间、reply 关系以及 runtime / thread / turn 引用。
- 本地 Markdown、Trace、启动诊断已经进入运行体。
- 第一发生场中已经出现真实 Cognos 讨论与模型被校正后的继续，不再只是 smoke test。

### 当前主工程假设

下一步不是继续扩大“可切换 runtime 的 assistant slot”，而是验证：

```text
同一发生场
├── 小林
├── Participant A → 自己的 runtime continuity
└── Participant B → 自己的 runtime continuity
```

当前最小假设是：**participant 可以先作为稳定工程身份锚点存在，而不等于已经证明了主体本体。**

第一组织切片只需要：

- participant 与 runtime / model 分离；
- Codex、Gemini 各自连续性同时保留，不互相替换；
- occurrence 明确归属于 author participant；
- 一个 participant 可以显式面对另一个 participant 留下的 occurrence；
- 服务重启后 field history 与各 runtime binding 分别恢复。

### 明确仍只是候选的结构

以下仍不能称为“当前架构已决定”：

- 正式 `Space / Position / View / Relation / Memory` schema；
- `subject_level`；
- Position 的 runtime 实现；
- Reach / Influence / Field 是否成为独立结构；
- JSONL / SQLite / Markdown 的长期权威关系；
- participant 是否最终可被视为主体；
- 自动多 Agent orchestration、always-on agent、sleep service、中央 state updater。

## 1. 已经能约束工程的要求

这些要求不是具体数据表，但后续方案不能绕开：

1. 第一版要承载**同一场中的多主体/参与者持续沟通**，并继续向阶段判断、决定、执行和历史影响未来推进。
2. 架构设计本身要逐步进入 Cognos 内部；设计提案、采用、执行、现实反馈都应成为可重读发生。
3. 关系依附空间；不能先退化成与空间无关的静态边。
4. 记忆必须表现为过去改变未来的行为条件，而不只是“存了文件”或“下一轮多拼一段 Prompt”。
5. 每个参与者不必默认看到全部世界；“发生存在”与“某主体看见它”不能预先等同。
6. 位置不预先定死；尝试、可能、学习、调度不能缩成任务管理字段。
7. 历史不得被后来总结覆盖；未采纳意见、旧解释、错误对象化和建模失败仍可重新进入。
8. schema 装不下与 schema 顺利装错都是真实失败类型。
9. runtime continuity、persistent history、position、view 必须区分；不能用上下文注入冒充位置。
10. 持续参与不等于持续生成 token；未来若进入持续世界问题，要允许 `ActiveCognition=0` 时关系、位置、未完成展开与世界后果仍可能持续。

## 2. 当前运行体：第一发生场

当前已采用的局部技术事实：

```text
浏览器
  ↓
FastAPI
  ↓
当前发生场
  ├── Codex RuntimeAdapter → Codex thread
  └── Gemini RuntimeAdapter → Gemini session
  ↓
Vault append-only JSONL
```

这里的“选择 Codex / Gemini”目前仍更接近 runtime selector。第一组织切片要把它推进为 participant selector / binding，但**不重做现有 occurrence 存储**。

### 当前数据边界

已有 occurrence/history 继续作为事实层使用；新增字段只为支持真实组织切片的最小需要，例如稳定 participant attribution 与显式 reference。不要因为要实现 participant 就重新设计一个更贫瘠的 `Occurrence{id,author,content,time}` 模型覆盖现有 runtime/ref 信息。

### runtime 的当前地位

`RuntimeAdapter` 仍保持小作用域：它调用一个外部运行身体并返回可引用的运行事实。

```text
Participant
    ↓ binding
RuntimeAdapter
    ↓
Codex thread / Gemini session / future dsh...
```

这只是当前工程分层。它没有证明“一个主体可以任意换 runtime 而保持同一主体”；后者需要未来异构运行身体实验。

## 3. 第一组织切片的最小工程形状

### participant binding

第一版只需类似：

```text
participant_id
display_name
runtime_kind
runtime_state_ref
```

暂不增加：

```text
role
position
subject_level
memory_policy
perspective definition
cognition compiler
relation graph
```

因为这些会让 Participant 过早变成传统 Agent Framework。

### 已进入现实的第一组织切片（2026-08-16 验证通过）

`Playground/cognos/web/` 现在是可运行的第一组织承载身体，而不只是单模型对话框或工程候选：

1. **Participant 与 Runtime 彻底解耦**：
   - 参与者（Participant）是发生场内的工程身份锚点（如 `Gemini`、`Gemini-B`、`Codex`），而不是底层模型 API；
   - 运行时（Runtime）只是参与者当前借用的算力身体（Google Gemini REST API 或本地 Codex App-Server）；
   - 各自持有独立、隔离的会话连续性（`gemini_thread.json`、`gemini_b_thread.json`、`codex_thread.json`），实现 $\text{Field Continuity} \neq \text{Participant Continuity}$。
2. **显式面对已有发生（Occurrence Quoting）**：
   - 任何已有发生可被显式指给另一参与者面对，不伪造其原生历史，也不污染 System 指令；
   - 以结构化的带 provenance 发生上下文（`[来自当前发生场的已有发生] ... [/发生]`）呈现给目标参与者。
3. **发生落盘与溯源**：
   - `AppendOnlyHistory` 把原文实时追加写入 Vault `第一发生场.jsonl`；
   - 精准记录 `id`、`occurred_at`、`author`、`author_participant_id`、`target`、`quoted_occurrence_id` 及局部 `runtime_ref`。
4. **前端三栏极简交互**：
   - 本地 Vendor 库（marked.js + purify.js），零外部 CDN 依赖；
   - 受话方药丸切换（`@Gemini` / `@Gemini-B` / `@Codex`）与消息卡片“引用”一键挂载；
   - 右栏实时呈现空间共在参与者清单及其各自的底层 Thread 状态。

## 2026-08-16：从“运行时切换”到“第一组织切片”的认识折返

这只记录当前真实跑通的代码事实与认识收敛：

| 现有结构 | 折返后的认识 | 当前动作 |
|---|---|---|
| 根目录 `models.py` 声明五种基础实体 | 早期旧工程投影，固定 schema 提前封闭了显现 | 冻结为历史实验；现行代码不予导入 |
| `RuntimeAdapter` 只定义 `send(message)` | 对外部运行时的最小非本体接口 | 保留，并拓展出 `GeminiRuntimeAdapter` 与 `CodexRuntimeAdapter` |
| 单一 Assistant Slot + 模型切换 | 本质仍是单线程流水线中的算力代换，不是多主体共在 | 拆除；演进为多 `Participant` 注册表与独立连续性 Session 隔离 |
| 历史全局广播或硬塞 | 容易导致虚假同步与 Token 爆炸，同一场不等于默认共享全部上下文 | 改为显式定向受话与精准 `Occurrence Quoting` |
| 服务跨进程重启 | Participant 连续性不依赖当前 Web 进程存活 | 验证通过：持久化 thread/session 文件在服务重启后无损恢复 |
### occurrence attribution

现有发生继续保留 runtime/thread/turn provenance，同时增加稳定 participant attribution。`participant_id` 是当前工程身份锚点，不是主体本体 ID。

### 面对已有发生

第一版不做“所有 occurrence 自动广播给所有 participant”，也不把其他 participant 的输出偷偷伪装成本 runtime 原生历史。

最小动作是：

```text
选择 occurrence A
→ 指定 participant B 面对 A
→ Cognos 以带 provenance 的普通材料呈现 A
→ B 在自己的 runtime continuity 中回应
→ 新发生追加回场
```

因此：

```text
同一场中发生
≠ 所有主体默认可见
```

谁能看见、怎样进入、什么会影响谁，后续才可能成为 Reach / Position / Relation 的真实问题。

## 4. 第一组织切片验收

当前最小真实链：

```text
小林 → Gemini → occurrence A

小林 → Codex，使其面对 A → occurrence B

（中间可重启服务）

小林 → Gemini，使其面对 B
```

验收只看：

1. Gemini 第三轮仍回到它自己的原 continuity；
2. Codex 使用自己的 continuity；
3. B 面对的是明确的 A，而不是系统偷偷把整个 Gemini transcript 注入；
4. Gemini 面对 B 时，同时保留它自己先前的连续性；
5. JSONL / trace 能重构谁通过哪个 runtime 面对了什么发生，又留下了什么；
6. 服务重启不会把 field history、Gemini session、Codex thread 三者混成同一个状态。

这只能证明“多个持续 participant 可以共同面对发生”，不能证明主体、空间或位置已经实现。

## 5. 触发式探针，而非线性 backlog

以下旧候选仍保留，但不再作为必须顺序做完的前置：

### 来源 / history query

当真实参与者出现“东西都在，但读不对来路 / 找不到需要的发生”时再进入。三层上下文是曾经可用的候选，不再作为第一组织切片强制架构。

### ex.1 migration / 撤销对象化

当错误旧认识真实阻碍当前运行时，用“那根本不是什么尝试”验证：发生保留、旧解释可查、对象身份可撤销、新解释不伪造过去。

### P1 / P2 / P3

- P1 NavigableTrace：只验证外部可导航历史；
- P2 Persistent Position：只有 `enter(P)` 真正改变默认可达世界时才有资格讨论；
- P3 Viewpoint Exteriorization：等待 Position / View 能被真实运行区分。

不再要求严格按 P1 → P2 → P3 排队。

## 6. 更远的运行架构地形（候选，不是当前实现）

8/14 讨论已经打开一个比“持久会话”更强的问题：真正的持续世界可能需要允许世界先变化、影响先传播，主体之后重新进入已经变化的位置，而不是每次启动时读一段“未读事件”。

候选运动：

```text
WorldChange
→ EffectPropagation
→ World / Position Change
→ Subject Re-entry
→ View
```

以及：

```text
NotRecognized ≠ NotEffective
ActiveCognition(S)=0
并不自动推出 Situated/Relational Existence(S)=0
```

这些内容目前只用于约束未来实验：**不要把 persistent DB、event log 或 prompt reconstruction 轻易叫 persistent world。**

## 7. 旧工程候选的当前地位

### 三层上下文

曾经得到局部接受，仍可作为历史重读 probe；但它不是当前第一组织切片的强制设计。

### `Space / EntityObject / ObjectInSpace / Relation / Movement`

继续作为旧数据投影候选保留，不升级为采用骨架。特别是 `Movement` 不能因为方便追加日志就成为本体最小单位。

### `subject_level`

继续降为实验视图。即便未来试验，也不能把 0—4 梯度当一般主体理论。

### `Relation + RelationMember`

仍是比二元边更开放的旧候选，但当前没有真实关系实验支撑，不应因为“看起来更合理”就实现。

### DeepSeek Harness / dsh

未来可作为异构运行身体压力测试，但当前不应因为“第三 runtime 可接”就把第一组织切片变成 provider integration 项目。

## 8. 当前禁止抢跑

暂不实现：

- 固定 Space 表 / Relation 枚举；
- Position / Role 字典；
- Participant 的人格、立场、视角编译器；
- occurrence 全局广播；
- 自动 Agent 对吐 / round-robin；
- 多路 streaming 作为当前核心问题；
- dampening / autonomy 机制；
- 中央 Cognos 总控大盘；
- always-on agent / sleep service；
- 把疑惑、未闭合、空无、unknown schema 化。

这些不是“永远不要”，而是当前还没有被现实逼出来。

## 9. 当前架构的下一次改写条件

本文件不应因为一次概念讨论就更新。至少满足一种条件再改：

- 第一组织切片真实跑通或失败，并产生新的不可忽视工程事实；
- 第一个组织闭环完成，现实行动与反馈改变后续沟通；
- 某个触发式探针真正进入运行；
- participant/runtime、history/memory、position/view 等当前区分被真实反例推翻；
- 新 runtime / 外部身体带来当前架构无法表达的差异。
