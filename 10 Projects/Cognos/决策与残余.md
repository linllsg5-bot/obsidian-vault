# Cognos：决策与残余

> 这里保留阶段性采用、未采纳意见和重新打开条件。它不是“最终答案”清单。

## 当前采用

| 决策 | 状态 | 来源 | 重新打开条件 |
|---|---|---|---|
| 组织是第一阶段形态 | 已确认定位 | ex.2 + ex.3 | 真实运行出现组织无法承载的运动 |
| 软件是第一数字身体 | 已确认定位 | ex.2 + ex.3 | 软件持续表现为外部管理工具而非承载 |
| 关系依附于空间 | 已确认原则 | ex.3 | 数据运行出现必须脱离空间才成立的关系反例 |
| 主体不限于人和 AI | 已确认原则 | ex.3 | 主体化机制无法产生任何实际行为差异 |
| 判断本质是透支 | 已扎根信念 | ex.1—ex.3 | 出现能否定“一次性展开/牺牲完整性”的反例 |
| A 防线 + B 数据骨架 | 当前工程选择 | ex.3 | Phase 1 运行证明防线或骨架阻塞真实沟通 |
| Python/FastAPI/SQLite/HTML/JS | 当前技术选择 | ex.3 | 技术栈本身成为主要认知负担或无法满足运行需求 |

## 已否决但保留

| 提案 | 为什么未采用 | 仍可保留的部分 |
|---|---|---|
| 四文件 + CLI 机械拼 Prompt | 没有情境层级，像每次开会朗读整本手册 | 宪法级目的防线 |
| 把 Cognos 做成普通任务管理/群聊 | 压缩了新存在、组织和软件的层次 | 沟通、调度等局部交互器官 |
| 预设固定 AI 岗位 | 把位置冻死，违背位置轮转与主体涌现 | “位置”作为局部视野仍保留 |
| 把原语做成强制消息标签 | 用表格替代了认识论的运行 | 后台提出候选结构、由沟通确认 |

## 开放残余

- `effect` 怎样改变 Context Builder，才不是又一段说明文字？
- 关系的显现梯度如何由事件推动，而不是人工改数字？
- `subject_level` 怎样升降；谁提议、谁确认、如何保留历史？
- 调度如何成为共同展开邀请，而不是换名的任务分配？
- 学习怎样表现为“系统接下来能看到什么改变了”？
- 位置如何自然长出并轮转，同时保留必要的全局方向？
- JSONL / SQLite / Markdown 的权威关系能否经重建测试成立？
- 原始会话中的敏感信息怎样既不破坏来源追溯，也不进入公开 Git 历史？
