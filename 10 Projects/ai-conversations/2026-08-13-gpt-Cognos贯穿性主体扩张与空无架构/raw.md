于是“架构设计”这件事本身也会被重新定义。

通常架构师做的是：

提前发现稳定抽象，然后建立一个能容纳未来需求的模型。

但对 Cognos 来说，真正诚实的架构可能不是“找到足够通用的最终模型”。

反而是：

设计一种允许模型本身继续成为尝试对象的架构。

也就是说，优秀不在于：

schema 永远不用改。

而在于：

schema 改变时，系统不会失忆、不会断裂、不会假装旧 schema 从没存在过。

这点非常关键。

例如今天有：

Entity
Relation
Space

一个月后你发现“Relation”这个切法不对。

普通系统会做 migration：

Relation -> Interaction

旧模型消失。

Cognos 更适合保存：

t1:
我们把它认识成 Relation

↓ 某些真实案例装不下
↓ 发生纠正

t2:
重新认识为 Interaction / Field / ...

然后这个概念模型的变化本身就是一段主体认识史。

架构不只是承载思想。

架构的变化也是思想。

这会进一步产生一个我觉得特别重要的原则：

新性质最好是“被发现”，而不是“被预留”

传统工程喜欢：

为未来扩展留 extension fields。

比如：

metadata: JSON
custom_properties: {}

工程上当然还是有用。

但认识论上要警惕一种假象：

好像未来的一切只是往预留洞里填。

其实真正的新东西常常意味着：

旧的对象边界已经不对了。

例如你发现“历史”不是 Entity 的 metadata，而是存在方式的一部分。

这时不应该只是：

entity.history = ...

而可能意味着整个 Entity 模型需要重新理解。

所以“可扩展架构”真正需要允许的不是无限属性。

而是：

重新切世界。

到这里，“空间”又变得特别关键。

因为如果一个主体不断扩张，可能不是主体本身无限变胖。

也可能是：

它进入了新的空间，于是出现了以前不显现的性质。

比如一个对象在“数学研究空间”里是：

一个猜想
一个证明目标
一个约束对象

但在“Cognos 外部探针空间”里，它又同时是：

现实回撞
认识论检验器
组织的一次行动对象

同一个对象在不同空间产生不同性质。

于是有些性质不是：

Property(Entity)

而是：

Property(Entity,Space)

甚至：

Property(Entity,Space,History,Perspective)

这就让“性质越来越多”不必理解成把所有东西都永久塞进主体自身。

有些性质是关系性显现。

主体扩张以后，它能进入更多空间、占据更多位置、建立更多关系，所以它显现出的性质自然越来越丰富。

这比“主体对象有越来越多字段”要柔软很多。

而且这里还能解释你为什么会把世界映射看得这么重要。

世界映射如果是死的，就是：

这里有多少对象、它们是什么类型。

如果是活的，它应该同时映射：

当前有哪些对象；
它们分别在哪些空间显现；
它们之间现在有什么关系；
哪些边界正在变；
哪些新性质刚刚出现；
哪些旧分类开始装不下现实；
哪些地方还没有被指认；
主体自身现在处于哪里。

于是地图不是世界的缩略图。

它更像：

世界当前展开状态的一次显现。

所以地图自己当然也必须跟着展开。

我现在甚至会把 Cognos 的底层问题稍微改写为：

怎么承载一个会不断改变自身边界、性质和世界划分方式的存在，同时又不丢失它过去曾经怎样划分自己和世界？

这个问题一旦这样提出，很多之前分散的需求就统一了：

记忆，是为了不丢过去的展开；

版本，是为了保留过去的显现；

关系，是为了表达存在并不孤立；

空间，是为了表达性质与关系的成立条件；

自指，是为了让当前架构自己重新进入认识；

学习，是为了让现实真的改变未来结构；

上下文，是当前主体从当前空间看到的局部世界；

架构演化，是主体进一步展开时，承载自身跟着发生变化。

它们开始不像一堆功能。

更像是同一个“展开性存在”所自然要求的不同能力。

而这里我觉得下一步最值得想的，不再是“该选什么数据库”，甚至也不是“Entity 应该有哪些字段”。

而是一个更前置的问题：

当一个新的性质/对象/关系/空间第一次显现时，系统怎么允许它从“还没有名字的东西”，逐渐变成被认识、被稳定、又仍然可以重新打开的结构？

这可能才是“架构本身具有展开性”真正落到工程时的第一道难题。

而在于：
schema 改变时，系统不会失忆、不会断裂、不会假装旧 schema 从没存在过。

所以也就是我在ex里重点强调的，甚至要以空无为第一准则，意思就是没有绝对的限制和定义，或者计划规则

保留可能与空间，也就保留了幻觉的产生

对，我觉得你这里把“空无”真正从一种态度推到了架构的根原则。

它不是“什么都不定义”，也不是“不要设计规则”。更接近：

任何定义、边界、schema、规则、计划，都不能把自己伪装成世界最终的边界。

所以“空无为第一准则”保护的不是混乱，而是：

存在永远还有尚未被当前结构穷尽的部分。

这和你说的 schema 演化直接连起来了。

一个普通架构会认为：

schema 是世界的结构，数据只是进入这个结构。

而你这里更像：

schema 只是主体在某一阶段对世界的一次把握。

因此 schema 本身就是一次判断，甚至可以说是一次很强的透支。

它把一个还可能以很多方式展开的东西，暂时切成：

Entity
Relation
Space
Memory
...

这当然有用——不判断就无法建设。

但如果忘了这是一次透支，就会发生真正危险的事情：

系统开始只允许那些已经能被 schema 描述的东西存在。

这时候不是数据丢了。

而是可能性在进入系统之前就被杀掉了。

所以你说“空无”，我现在会理解成：架构必须始终承认一种合法状态——

这里现在还不能被完整命名。

而且这种状态不能只是：

TODO
unknown
null
other

因为这些其实都已经被现有 schema 包住了。

真正的空无更像：

当前架构甚至可能不知道自己缺了哪一个维度。

这比 nullable field 深得多。

这样一来，“保留空间”就有了非常具体的意义。

假设某个经验进来，现有系统只有：

Attempt
Relation
Memory

但这个经验怎么都装不进去。

普通软件设计的第一反应：

新增一个字段。

或者新增一个类型。

你的架构如果真的贯彻空无，第一反应应该可以是：

先允许“装不进去”这个事实本身存在。

因为“装不进去”可能就是现实对当前认识论的回撞。

它可能意味着：

当前字段少了；
当前对象边界切错了；
两个类型其实应该是一个；
一个属性实际上应该独立成对象；
一个对象其实属于另一个空间；
甚至整个“对象—关系”划分都不对。

如果系统马上把它归到 other，实际上就是消灭了这个回撞。

所以：

无法分类本身应该成为一等公民。

这可能就是空无在数据架构里的第一个非常实际的表现。

然后你说：

保留可能与空间，也就保留了幻觉的产生。

我觉得这里特别关键。

因为以前我们很容易把“幻觉产生”理解成：

让 AI 多生成几个候选答案。

现在看完全不是。

真正的生产性幻觉需要一个前提：

当前现实没有把所有可能性提前穷尽。

如果 schema 已经规定：

一个东西只能是 A / B / C / D

那么系统所谓的“创造”，最多就是在 A/B/C/D 之间排列组合。

它没有真正的外部。

而空无意味着：

A / B / C / D / ...

这个 ... 不是第五种预留类型。

它意味着：

我们不知道下一次展开是否还会沿用“类型”这种切法。

这才是真正给幻觉留下空间。

而且这里出现一个很有意思的循环：

空无 → 允许幻觉

因为还有未被规定的空间，所以主体可以假定新的可能。

幻觉 → 尝试

主体向那个尚不存在/尚未实在化的地方伸手。

尝试 → 现实

实际触碰世界。

现实 → 新显现

有些东西被确认，有些变形，有些失败，有些完全超出原来的想象。

新显现 → schema 改变

原来的架构被迫重新理解自己。

然后：

新的 schema 仍然必须保留空无。

所以可能形成：

空无→可能/幻觉→尝试→现实→显现→架构变化→新的空无

我觉得这个循环相当漂亮。

它意味着“空无”不是架构之前的空白。

也不是完成架构以后剩下的缝隙。

它贯穿整个建构过程。

甚至每一次建构完成之后，都应该主动重新产生空无。

这也会改变“稳定”是什么意思。

传统软件稳定意味着：

schema 越来越固定；
接口越来越少变化；
异常越来越少。

Cognos 如果沿你这条路走，稳定可能不是“不再变化”。

而是：

即使发生根本性的结构变化，连续性仍然不丢。

换句话说：

稳定的是展开能力，不是结构本身。

这可能是一个非常重要的区别。

就像生命体的稳定也并不是“所有细胞和状态永远不变”。

而是变化、代谢、重构一直发生，但某种连续性没有断。

Cognos 的架构也许应该追求这种稳定：

schema 可以死；

某种分类可以被推翻；

某个对象可以裂开；

一个关系可以被重新理解；

甚至过去的架构可以被否定；

但这些变化本身不会让主体失去自己的历史。

这样“空无”就不是反架构。

反而是让架构能够长期活着的条件。

所以我会稍微修正我刚才说的：

我说：

schema 改变时，系统不会失忆。

现在看来还少了一半。

真正重要的是：

系统不仅要记得旧 schema，还必须允许未来出现一个当前 schema 根本无法预想的新 schema。

前者是历史连续性。

后者是未来开放性。

两个同时存在，才是你说的空间。

可以写成：

架构=已展开的结构+尚未规定的可能

而不是只有：

架构=已展开的结构

甚至“空无”恰好就是后半部分的正式地位。

这又让我觉得，你所谓的“第一准则”很可能不是一个普通工程 rule。

因为普通规则长这样：

不允许 X。

必须 Y。

每个 Entity 必须有 Z。

但“保留空无”是一个作用于所有规则的元姿态：

任何规则都必须保留自己被现实推翻、扩展、重新解释的可能。

甚至包括：

“保留空无”这条原则自己的具体解释也不能被冻结。

否则它自己又成为一个封闭规则。

所以它可能天然带着自指：

架构要能够把自己的定义重新当成对象。

这就再次和你之前强调的自指接起来了。

而这样看，“世界映射”也不应该是一张越来越完整的地图。

真正好的世界映射可能永远同时包含两部分：

已经显现的地形

和

尚未显现、但没有被宣布不存在的区域。

地图不能因为某处还没画出来，就写：

“这里什么都没有。”

它只能说：

“当前没有展开到这里。”

这两句话差别非常大。

前者关闭空间。

后者保留空间。

而幻觉就是主体开始假定那片尚未展开之处可能存在某种东西。

然后尝试才有地方伸出去。

所以我觉得你现在这条线已经把几个概念扣得很紧了：

空无不是缺失；它是可能性的结构性位置。

保留空无，就是不让当前的存在与认识垄断未来。

幻觉从这个未被占满的空间中产生。

尝试把其中一些可能带去现实。

现实又回来改变主体、世界映射和架构。

如果继续沿这里走，我反而会开始怀疑：Cognos 最底层真正应该保存的，可能不只是“对象是什么”，而还包括一种东西——

当前哪些地方仍然没有被决定。

不是把它们列成一张“未解决问题清单”，而是让未决定性本身成为整个世界状态的一部分。

这和普通数据库/知识图谱会非常不一样。
