"判断是透支" 和 "旧定义" 之间的关系是**纠正**——这个纠正在未来所有讨论判断的场合都会生效； - "组织" 和 "新存在" 之间的关系是**第一阶段形态**——这个关系约束了不能把组织当成终点； - "哥德巴赫" 和 "数学探针" 之间的关系是**实例**——这个关系约束了 AI 进入哥德巴赫时不能只解题。 **关系的特点**： - 它有方向（A → B 和 B → A 不一样）； - 它有作用范围（在什么场合生效）； - 它有实际效果（会改变什么行为）； - 它可以被讨论、修改、废弃、重新激活。 ### 关系空间是什么？ **关系空间不是"存放关系的容器"**，那是数据库。 **关系空间是**：所有关系相互连接、相互影响、相互约束形成的整体。 在这个空间里： - 一个关系可以支持另一个关系（"判断=透支" 支持 "尝试是广义的"）； - 一个关系可以冲突另一个关系（"AI 应该独立判断" 冲突 "第一阶段单点裁决"）； - 空间内的可能，还没被兑现的、可以长出来的。 **判断** - 尝试的一种特殊形态——透支； - 浓缩、高效、一次性的展开； - 一般展开是完整的，判断是一次性把可能全部兑现，所以叫透支； - 因此会牺牲完整性和细节。 **现实** - 幻觉/可能在实际情况上的落地； - 落地有多种形态：成功、变形、阻碍、空响、超出预期、主体不适。 **残余** - 判断（透支）之后必然留下的、被跳过和牺牲的部分； - **人**（有独立性、有持续展开） - **AI**（有独立性、有当前展开） - **概念**（有独立性、有历史和关系） - **讨论**（有独立展开的过程） - **张力**（有独立牵引力、有展开方向） - **共识**（有独立效力、有作用范围） - **行动**（有独立后果、有落地过程） - **残余**（有独立牵引、有重新进入的可能） - **关系**（有独立存在、有历史） 每一个都是主体，都可以被引用、被讨论、被修改、被联合。 第一阶段先实现人、AI、讨论、张力、共识、行动、残余、关系这几种。概念作为主体后续再做。 ### 从"关系是独立存在"长出：关系的存储方式 第一层说：关系不是对象的附属属性，是独立的存在。 那软件里关系不能只是数据库里的一张边表。关系需要： - 有自己的ID和记录； - 有自己的历史（谁在什么时候建立、经历了什么修改）； - 有自己的状态（活跃/休眠/废弃）； - 能被引用、被讨论、被修改； - 能显现（在特定场合被看见）也能不显现（存在但当前不影响）。 工程实现：关系是一等对象，和主体一样有独立的表和ID。但同时，关系的"显现"通过一个"作用范围"字段控制——什么场合下它会被检索出来影响上下文。 ### 从"共存本身是存在，显现有很多情况"长出：关系的显现机制 第一层说：关系是共存的存在，存在需要显现。 那软件里，关系不是静态显示的连线。关系有几种显现方式： - **被引用时显现**（讨论涉及相关概念时，关系自动进入上下文）； - **被冲突触发时显现**（新判断和旧判断冲突，冲突关系激活）； - **被主动查询时显现**（用户或AI问"这两个东西什么关系"）； - **默认隐藏但一直在**（不激活时不显示，但存储着）。 工程实现：关系有一个"显现条件"字段，系统根据当前对话上下文自动匹配哪些关系需要浮现。 ### 从"调度是主体的联合"长出：调度的形式 第一层说：调度是主体为了展开自己做不到的部分，与另一个主体联合。 那软件里调度不是"分配任务"的界面。调度应该是： - 发起联合的主体说明：我想展开什么、我到了哪里、我需要对方从哪里接上； - 被联合的主体收到的不是命令，是这个说明； - 联合的结果是两个主体共同展开某个部分； - 联合的历史被记录，成为两个主体共同的历史。 工程实现：调度是一个特殊的消息类型，包含"发起方当前展开状态"、"需要联合的原因"、"预期共同展开的方向"。不是任务卡片，是联合邀请。 ### 从"学习是完整展开"长出：学习在软件里的形态 第一层说：学习和判断对立。判断跳步，学习走完。 那软件里的"学习"不是"记录一条结果"。学习是： - 一次尝试被完整地走完（没有被判断中途兑现）； - 主体本身在这个过程中发生了变化； - 变化被记录，改变未来的展开可能。 工程限制：AI没有持续状态，所以真正的"AI主体变化"做不到。第一阶段的妥协是： - AI的"学习"通过组织记忆模拟——把完整展开的过程写入组织记忆，下次AI进入时读取，表现得像学过了； - 明确记录这是模拟，不是真正的学习； - 未来当AI能有持续状态时（微调、长期记忆机制），再改。 **学习不打断对话**：AI在对话中提出"这里我觉得完成了一次完整展开"或"这里被判断截断了"，你在对话中回应。系统在后台把被确认的完整展开写入记忆。 ### 从"最小单位是相对的"长出：数据存储的方式 第一层说：不固定最小单位，只要满足主体+展开性就是一个单元。 那数据库不能只围绕一种原子设计。可能的方式： - 每种主体都有自己的存储表（人、AI、讨论、张力、共识、行动、残余、关系）； - 但底层用一个统一的"事件流"记录所有变化（谁在什么时候做了什么、谁被引用了、谁改变了状态）； - 事件流是记录方式，不是最小单位； - 用户和AI操作的是主体，不是事件。 工程上：SQLite做主体表和索引，JSONL做事件流历史（追加式，不可修改）。两者可以互相重建。 ### 从"分层是生成关系"长出：软件的自身生长 第一层说：第二层从第一层长出来。以此继续延伸。 那软件的架构不是一次设计完的。软件应该： - 有一个"自身建设"项目，所有关于软件设计的讨论都在里面进行； - 讨论产生的决定直接变成开发任务； - 软件的每一次修改都被记录为组织的一次共同展开； - 软件的形态随讨论演化。 第一阶段的先有鸡还是先有蛋问题：先在外面做出最小骨架（能沟通、能记录、AI能带上下文），骨架跑起来后，后续的设计讨论都搬进去。 ### 从"空无是建构态度"长出：不做什么 第一层说：空无是保留未透支可能性的态度。 那软件设计的每个决定，都要检查：**这个决定有没有关闭未来的可能？** 第一阶段明确不做的： - 不预定义位置类型（位置在讨论中涌现，命名可以但不固定）； - 不预定义关系类型的完整列表（先给几个基础类型，用的过程中增加）； - 不预定义"工作单位"（讨论、张力、共识、行动、残余各自存在，不强行统一）； - 不做"完美UI"（第一版UI就是普通的，避免UI设计限制探索）； - 不做多Agent自动对话（每次AI发言都是明确的、可被你介入的）。 --- ## 三、第一阶段实施步骤 现在把上面的设计落到具体步骤。 ### 步骤零：先把第一层写清楚 在动工之前，把第一层的所有定义整理成一份文档，放在Obsidian里。这份文档不是给人看的说明，是软件运行时会自动读取的"底层宪法"。 内容包括： - 被采纳意见； - 未采纳意见； - 反对意见； - 残余； - 来源； - 未来重新打开的可能。 共识记录大概是： ```text 阶段性共识 { 所属空间 相关主体 采纳内容 未采纳内容 当前裁决者 为什么暂时这样决定 牺牲了什么 未来何时重开 } ``` --- ## 5.3 调度 调度不是任务派发，而是主体联合。 在沟通中可以这样发生： ```text 小林：这里我需要一个红队主体来反驳这个关系模型。 系统：是否创建调度？ 调度：小林 ↔ AI-红队，围绕“关系作为独立存在是否能用边表实现”形成联合。 ``` 调度完成后，这个 AI 的上下文不是： > 请反驳这个方案。 而是： > 你现在作为一个被联合的主体，接入小林当前未能展开的部分：判断关系模型是否把关系降级成对象附属。你的任务不是完成任务，而是扩展当前主体的认识边界。 --- ## 5.4 学习 学习发生在沟通之中，不是对话后复盘。 例如： ```text AI：我发现前面把关系实现成边表，会把关系降级成附属结构。 小林：对，这里出现了残余，关系作为独立存在还没被承载。 系统：是否将此登记为学习变化？ ``` 一旦确认，它改变未来： - 关系模型设计不能直接退回普通边表； - Context Builder 后续检索时注入这个纠正； - 当前项目状态更新； - 新张力出现：如何让关系作为独立存在被工程承载。 --- # 6. 记忆系统设计 你问“该怎么设计组织记忆”。 我认为第一阶段至少需要四种记忆。 --- ## 6.1 原始记忆 不可覆盖。 包括： - 原始会话； - 原始文件； - 原始 AI 回复； - 原始代码； - 原始错误。 作用： > 保留实际发生过什么。 --- ## 6.2 当前记忆 当前组织认为“现在有效”的内容。 包括： - 当前项目目的； - 当前阶段性共识； - 当前采用的概念定义； - 当前治理状态； - 当前活跃张力。 作用： > 让成员快速知道现在在哪里。 --- ## 6.3 关系记忆 保存对象、主体、关系的显现和变化。 包括： - 哪些对象共存； - 哪些关系显现； - 哪些关系生效； - 哪些关系被纠正； - 哪些关系形成压缩风险。 作用： > 让过去的结构影响未来。 --- ## 6.4 运行记忆 每次具体沟通和调度时实际使用的上下文。 包括： - 当前对话； - 当前参与主体； - 当前被注入的文件； - 当前相关关系； - 当前目的链； - 当前开放残余。 作用： > 事后能看出一次 AI 为什么丢失或没有丢失上下文。 --- # 7. 上下文系统设计 不能把全部 vault 塞给 AI。 应该做成分级记忆。 ## 7.1 常驻上下文 很短，始终注入： ```text 你在 Cognos 组织中。 该组织是新存在的第一数字承载。 组织不是项目全部，软件不是最终目标。 当前采用非对称共同生成。 不要把当前任务压缩成普通任务。 ``` --- ## 7.2 项目上下文 根据当前项目读取： - 项目为什么存在； - 当前张力； - 已有共识； - 相关残余； - 相关关系。 --- ## 7.3 对象上下文 如果讨论“判断”，系统注入： - 判断当前定义； - 判断作为透支； - 相关历史纠正； - 不要退回“判断可延迟”的旧说法。 如果讨论“关系”，系统注入： - 关系是对象共存的存在； - 关系不是边； - 当前尚未解决：如何工程实现。 --- ## 7.4 按需上下文 当 AI 需要深挖时，再读取： - 原始会话； - 长文档； - 历史记录； - 外部资料。 这样上下文不会爆，也不会丢整体。 --- # 8. 数据结构第一版 这里不是本体论，只是工程表示。 ## 8.1 Object / Existence 所有存在先统一称为对象。 ```ts Object { id name description status subject_level created_from current_summary } ``` `subject_level` 不是类型，而是主体化程度。 ```text 0 = 普通对象 1 = 可展开对象 2 = 候选主体 3 = 活跃主体 4 = 组织器官 ``` --- ## 8.2 Space 空间是对象和关系共存的场。 ```ts Space { id name purpose parent_space_id objects relations } ``` 空间可以是： - 整个组织； - 一个项目； - 一次讨论； - 一个关系空间； - 一个软件自身建设空间。 --- ## 8.3 Relation 关系作为存在。 ```ts Relation { id space_id participants description manifestation_level current_effect history status } ``` `manifestation_level`： ```text 0 = 潜在共存 1 = 已显现 2 = 活关系 3 = 主体化关系 ``` --- ## 8.4 Movement / Trace 不要叫“最小单位”，叫“运动记录”。 ```ts Movement { id space_id subject_id content movement_type created_at linked_objects linked_relations } ``` 类型可以是： - message； - judgment； - attempt； - dispatch； - landing； - residue； - correction； - decision。 它只是记录形式，不是本体原子。 --- ## 8.5 Dispatch 主体联合记录。 ```ts Dispatch { id space_id initiator_subject joined_subjects shared_tension extension_needed boundary expected_return status } ``` --- ## 8.6 Consensus / Decision 阶段性共识。 ```ts Consensus { id space_id participants adopted_claim unadopted_claims decided_by reason cost residue reopen_condition } ``` --- ## 8.7 LearningRecord 学习记录不是复盘表，而是主体因完整展开产生的改变。 ```ts LearningRecord { id subject_id attempt_or_process what_fully_unfolded what_changed_in_subject new_relations new_residue } ``` --- # 9. 第一版软件页面 ## 9.1 组织空间首页 显示： - 组织当前目标； - 当前软件承载状态； - 当前活跃项目； - 当前活跃主体； - 当前显现关系； - 当前开放张力； - 最近学习变化。 --- ## 9.2 沟通界面 三栏结构： ```text 左：空间 / 项目 / 主体 / 关系 中：沟通流 右：当前上下文生命面板 ``` 右侧面板动态显示： - 当前空间； - 当前主体； - 当前关系； - 当前张力； - 当前调度； - 可能的残余； - 调度产生的学习。 --- ## 9.5 关系空间界面 显示： - 当前空间中的对象； - 潜在关系； - 已显现关系； - 活关系； - 主体化关系； - 关系如何影响上下文； - 关系自身历史。 --- # 10. 实现路线 ## 阶段 0：先做设计骨架文档 不是写最终理论，而是写当前开发准则。 需要几份文件： ```text 01-项目当前目标.md 02-核心原语当前理解.md 03-主体与关系当前理解.md 04-组织第一阶段形态.md 05-压缩风险分类.md 06-软件第一阶段设计原则.md ``` 这几份文件不是给人看的说明书，而是后续软件上下文的基础。 --- ## 阶段 1：做最小沟通软件 先不要做复杂 AI。 功能： - 创建组织； - 创建空间； - 创建项目； - 多参与者聊天； - 消息保存； - 从消息中手动创建对象； - 手动创建关系； - 手动创建调度； - 手动记录阶段性共识。 目的： > 先让组织有一个能沟通、记录、显现关系的场。 这一步可以很粗糙，但必须能跑。 --- ## 阶段 2：加入 AI 参与者 功能： - 添加多个 AI 主体； - 每个 AI 可以进入某个空间； - 调用 AI 时带入当前空间上下文； - 当前有哪些空间； - 哪些主体； - 哪些关系； - 哪些项目； - 哪些张力。 --- ## 2. 关系不是死链接 一条关系能： - 被打开； - 被讨论； - 有历史； - 有状态； - 影响 AI 上下文。 --- ## 3. 主体不是固定用户类型 一个 AI、一个概念、一个项目、一个关系，都可以被提升为不同程度的主体。 --- ## 4. 调度不是任务分配 调度记录体现的是主体联合，而不是派单。 --- ## 5. 学习在沟通中发生 学习不是对话结束后的表格，而是在沟通中被提出、确认、写入，并改变后续。 --- ## 6. 架构能在自身内部继续设计 软件能承载“软件如何继续设计”的沟通、关系、调度和学习。 --- # 12. 最后给一个真正的第一步 不要先做 Context Builder。 也不要先做完整 UI。 第一步应该是： > **做一个最小组织沟通空间。** 它只需要： 1. 创建空间； 2. 创建对象； 3. 创建主体； 4. 多主体沟通； 5. 从沟通中创建关系； 6. 从沟通中创建调度； 7. 从沟通中记录阶段共识； 8. 所有内容保存； 9. 下次打开仍然在。 第一版哪怕没有复杂 AI，也可以先手动模拟 AI 主体；之后再接模型。 因为你现在真正想验证的是： > **组织形态能不能作为第一数字承载开始存在。** 而不是： > Context Builder 能不能拼上下文。 Context Builder 是后续器官。 第一器官应该是： > **沟通空间 + 关系显现 + 主体共存。** 这才更接近你现在说的第一阶段。

数据库里的边； - Obsidian 里的链接； - 两个对象之间的注释； - 静态知识图谱连线。 ### 关系是： > **一种独立存在。** 它有： - 自己的显现方式； - 自己的历史； - 自己的状态； - 自己的变化； - 自己的被讨论可能； - 自己成为主体的可能。 ### 工程含义 关系不能只存在于： ```text A --link--> B ``` 而应该是一个可独立存在的对象： ```text Relation { id space_id participants: [object_a, object_b, ...] description manifestation_state history current_effect status } ``` 重点是： > **关系不是对象的附属物，而是空间中的一种存在。** --- ## 1.2 关系的显现等级 因为你说“共存本身就是关系，但存在需要显现，显现情况有很多”，所以软件里可以这样处理： ### 第一层：潜在关系 只要两个对象共处一个空间，就有潜在关系。 例如： - “判断”和“透支”同处于认识论空间； - “组织”和“软件”同处于当前项目空间； - “哥德巴赫”和“数学外部探针”同处于某次尝试空间。 这时不一定要命名，只知道它们共存。 --- ### 第二层：显现关系 当沟通中有人指出： > “组织不是项目全部，而是第一阶段形态。” 这时关系显现了。 它可以被记录为： ```text 组织 —— 作为第一阶段形态 —— 新存在 ``` --- ### 第三层：活关系 当这条关系会影响未来行为，它就是活关系。 例如： ```text 关系：组织是新存在的第一阶段形态，不是项目全部。 影响：以后 AI 不能把项目压缩成组织建设。 ``` 这时它会参与上下文构建、AI提醒、项目判断。 --- ### 第四层：主体化关系 当某条关系本身被持续讨论、改变、成为张力来源时，它可以被视为主体。 例如： > “组织与新存在之间的关系”本身成为一个待展开对象。 这时它不再只是连接，而成为一个可被讨论、可被调度、可被学习的存在。 --- ## 1.3 调度 你的定义： > **调度是主体与主体的联合，主体的延伸扩展。** 这比“分配任务”更根本。 ### 调度不是： - 上级给下级派任务； - 用户命令 AI； - 项目管理里的任务分配。 ### 调度是： > **一个主体为了展开自身做不到、看不到、够不到的部分，与另一个主体形成联合。** 例如： 你不能同时严密检索全部资料、红队反驳自己、组织代码实现，所以你调度 AI。 不是“让 AI 干活”，而是： > **你通过 AI 扩展了自己的展开能力。** --- ## 1.4 调度在软件里的形态 调度应该更像“联合请求”。 ```text 调度 { 发起主体 被联合主体 共同张力 发起主体目前走到哪里 需要对方从哪里接上 联合的边界 预期产生什么 结果如何返回组织 } ``` 示例： ```text 发起主体：小林 被联合主体：AI-A 共同张力：关系空间如何实现 小林当前位置：已定义关系为对象共存的存在，但不知道软件如何承载 需要对方接上：从工程角度提出关系作为独立存在的实现方式 边界：不要退化成静态边表 预期产物：关系模型草案 返回方式：进入当前项目沟通，并被其他主体继续讨论 ``` 这比“任务：设计关系系统”更接近你的意思。 --- ## 1.5 学习 你的定义： > **学习是认知，是尝试的完整展开，是主体本身的完整展开，是对于存在的尝试的完整展开。** 所以学习不是： - 系统更新一条记录； - AI 变得聪明； - 把结果归档； - 完成一次复盘。 学习是： > **主体完整经历一次尝试，使自身发生改变。** 它和判断/透支形成对照： | 判断 | 学习 | |---|---| | 尝试的透支 | 尝试的完整展开 | | 高效抓核心 | 走完整体过程 | | 牺牲细节 | 保留展开过程 | | 一次性兑现 | 过程性改变主体 | --- ## 1.6 学习在第一阶段如何实现 当前 AI 本身不会真正持续改变，所以第一阶段只能通过组织记忆模拟学习： 1. 某个主体经历一次尝试； 2. 尝试过程被完整保留； 3. 落地结果进入组织记忆； 4. 关系被更新； 5. 下一次同一主体或相关主体进入时，读取这段历史； 6. 它的行动因此改变。 这不是完美学习，但这是第一数字承载中的学习雏形。 关键不是“存档”，而是： > **这次完整展开会改变下一次展开。** --- ## 1.7 主体 你现在的倾向是： > **不同对象都可以被当作一个完整主体，只要它有一定独立个体性和展开性。** 所以主体不只是： - 人； - AI。 还可以是： - 一个概念； - 一个问题； - 一个项目； - 一个关系； - 一段历史； - 一个数学结构； - 一个软件模块； - 一个组织自身。 --- ## 1.8 主体门槛 不是所有对象一出现就是完整主体。 更合理的是做成层级： ### 0. 对象 被指认出来的存在。 例如： ```text 判断 组织 软件 哥德巴赫 关系空间 ``` --- ### 1. 可展开对象 这个对象自身有未展开部分，可以继续被追问。 例如： ```text 判断是什么？ 组织如何成为第一形态？ 关系如何作为存在？ ``` --- ### 2. 候选主体 它开始拥有： - 相对边界； - 历史； - 关系； - 可被重新进入的状态； - 能牵引后续讨论。 例如： ```text “关系空间”已经不是一个词，而是一个持续牵引项目的问题。 ``` --- ### 3. 活跃主体 它可以进入沟通、被调度、产生影响。 例如： ```text 某个 AI； 某个项目； 某个概念的当前定义； 某个数学问题； 软件自身建设项目。 ``` --- ### 4. 组织器官 如果某个主体持续承担某种组织功能，它会成为器官。 例如： - 记忆器官； - 检索器官； - 关系器官； - 调度器官； - 红队器官； - 外部行动器官。 这个过程不预先规定，而是在运行中形成。 --- # 2. 第一阶段软件的核心形态 你说你目前的简单想法是： > 有个组织沟通软件，软件里有需要记录的内容，然后你进行沟通，各个 AI 给出回复，相互之间继续沟通，达成阶段性共识，然后决定，然后执行。 这个想法不潦草。它其实就是第一阶段最接近可实现的形态。 更准确地说： > **第一阶段软件 = 以沟通为中心的组织生成空间。** 不是先做任务管理。 不是先做复杂知识库。 不是先做自动 Agent。 而是先做： > **多人 / 多 AI / 多主体在同一组织空间中沟通，并让沟通产生关系、调度、学习、共识和行动。** --- # 3. 第一阶段的基础结构 第一版需要四个核心区域。 --- ## 3.1 沟通空间 这是中心。 功能类似 QQ / Discord / Slack，但内核不同。 普通聊天软件里，消息只是消息。 Cognos 里，消息可能显现为： - 一个对象； - 一个主体； - 一个关系； - 一个张力； - 一个判断； - 一个调度； - 一个残余； - 一个行动； - 一个学习节点。 但这些不是发消息前就填标签，而是在沟通中逐渐被识别和确认。 --- ## 3.2 项目空间 项目不是任务列表。 项目是： > **多个主体围绕某个持续方向形成的组织空间。** 项目里应当看到： - 当前在做什么； - 为什么在做； - 现在卡在哪里； - 有哪些不同意见； - 形成过哪些阶段性共识； - 哪些行动已发生； - 哪些残余还在牵引； - 和总项目有什么关系。 --- ## 3.3 调度空间 这是组织知道“自己现在怎么动”的地方。 它显示： - 当前开放张力； - 哪些主体正在参与； - 哪些主体可以被联合； - 哪些调度正在进行； - 哪些行动等待结果； - 哪些结果已经返回； - 哪些学习正在形成。 它不只是任务面板，而是： > **主体与主体联合展开的组织面板。** --- ## 3.4 关系空间 这是项目重点。 关系空间不是一张漂亮图。 它要显示并保存： - 对象之间的共存； - 哪些关系已经显现； - 哪些关系正在影响未来； - 哪些关系本身正在主体化； - 哪些关系导致了调度、判断、学习； - 哪些关系属于压缩风险。 关系空间是： > **组织内部存在结构的显现层。** --- # 4. 第一阶段的核心流程 第一阶段不要设计太多功能，只要跑通一条真实流程。 这条流程是： ```text 沟通 ↓ 对象 / 张力显现 ↓ 多个主体继续参与 ↓ 关系显现 ↓ 阶段性共识 ↓ 调度联合 ↓ 行动 / 尝试 ↓ 落地 ↓ 学习 ↓ 组织状态改变 ``` 注意：这不是硬流程，不是每次必须按顺序填。 它更像组织自然运动的骨架。 --- # 5. 各机制如何在沟通中发生 ## 5.1 沟通 沟通是所有机制的发生场。 不是先有结构再沟通，而是： > **结构从沟通中显现。** 沟通中可能出现： - 一个新对象； - 一个候选主体； - 一条关系； - 一个判断； - 一个残余； - 一个调度； - 一个学习变化。 系统的任务不是打断你，而是在右侧面板或后台提示： ```text 这里可能出现了一个新关系 这里可能形成了一个阶段判断 这里可能有一个残余 这里可能需要调度 ``` 由你或组织在沟通中确认。 --- ## 5.2 阶段性共识 共识不是所有人平权投票。 第一阶段是： > **多主体沟通后，由小林作出阶段性组织决定。** 但软件必须保留： - 被采纳意见； - 未采纳意见； - 反对意见； - 残余； - 来源； - 未来重新打开的可能。 共识记录大概是： ```text 阶段性共识 { 所属空间 相关主体 采纳内容 未采纳内容 当前裁决者 为什么暂时这样决定 牺牲了什么 未来何时重开 } ``` --- ## 5.3 调度 调度不是任务派发，而是主体联合。 在沟通中可以这样发生： ```text 小林：这里我需要一个红队主体来反驳这个关系模型。 系统：是否创建调度？ 调度：小林 ↔ AI-红队，围绕“关系作为独立存在是否能用边表实现”形成联合。 ``` 调度完成后，这个 AI 的上下文不是： > 请反驳这个方案。 而是： > 你现在作为一个被联合的主体，接入小林当前未能展开的部分：判断关系模型是否把关系降级成对象附属。你的任务不是完成任务，而是扩展当前主体的认识边界。 --- ## 5.4 学习 学习发生在沟通之中，不是对话后复盘。 例如： ```text AI：我发现前面把关系实现成边表，会把关系降级成附属结构。 小林：对，这里出现了残余，关系作为独立存在还没被承载。 系统：是否将此登记为学习变化？ ``` 一旦确认，它改变未来： - 关系模型设计不能直接退回普通边表； - Context Builder 后续检索时注入这个纠正； - 当前项目状态更新； - 新张力出现：如何让关系作为独立存在被工程承载。 --- # 6. 记忆系统设计 你问“该怎么设计组织记忆”。 我认为第一阶段至少需要四种记忆。 --- ## 6.1 原始记忆 不可覆盖。 包括： - 原始会话； - 原始文件； - 原始 AI 回复； - 原始代码； - 原始错误。 作用： > 保留实际发生过什么。 --- ## 6.2 当前记忆 当前组织认为“现在有效”的内容。 包括： - 当前项目目的； - 当前阶段性共识； - 当前采用的概念定义； - 当前治理状态； - 当前活跃张力。 作用： > 让成员快速知道现在在哪里。 --- ## 6.3 关系记忆 保存对象、主体、关系的显现和变化。 包括： - 哪些对象共存； - 哪些关系显现； - 哪些关系生效； - 哪些关系被纠正； - 哪些关系形成压缩风险。 作用： > 让过去的结构影响未来。 --- ## 6.4 运行记忆 每次具体沟通和调度时实际使用的上下文。 包括： - 当前对话； - 当前参与主体； - 当前被注入的文件； - 当前相关关系； - 当前目的链； - 当前开放残余。 作用： > 事后能看出一次 AI 为什么丢失或没有丢失上下文。 --- # 7. 上下文系统设计 不能把全部 vault 塞给 AI。 应该做成分级记忆。 ## 7.1 常驻上下文 很短，始终注入： ```text 你在 Cognos 组织中。 该组织是新存在的第一数字承载。 组织不是项目全部，软件不是最终目标。 当前采用非对称共同生成。 不要把当前任务压缩成普通任务。 ``` --- ## 7.2 项目上下文 根据当前项目读取： - 项目为什么存在； - 当前张力； - 已有共识； - 相关残余； - 相关关系。 --- ## 7.3 对象上下文 如果讨论“判断”，系统注入： - 判断当前定义； - 判断作为透支； - 相关历史纠正； - 不要退回“判断可延迟”的旧说法。 如果讨论“关系”，系统注入： - 关系是对象共存的存在； - 关系不是边； - 当前尚未解决：如何工程实现。 --- ## 7.4 按需上下文 当 AI 需要深挖时，再读取： - 原始会话； - 长文档； - 历史记录； - 外部资料。 这样上下文不会爆，也不会丢整体。 --- # 8. 数据结构第一版 这里不是本体论，只是工程表示。 ## 8.1 Object / Existence 所有存在先统一称为对象。 ```ts Object { id name description status subject_level created_from current_summary } ``` `subject_level` 不是类型，而是主体化程度。 ```text 0 = 普通对象 1 = 可展开对象 2 = 候选主体 3 = 活跃主体 4 = 组织器官 ``` --- ## 8.2 Space 空间是对象和关系共存的场。 ```ts Space { id name purpose parent_space_id objects relations } ``` 空间可以是： - 整个组织； - 一个项目； - 一次讨论； - 一个关系空间； - 一个软件自身建设空间。 --- ## 8.3 Relation 关系作为存在。 ```ts Relation { id space_id participants description manifestation_level current_effect history status } ``` `manifestation_level`： ```text 0 = 潜在共存 1 = 已显现 2 = 活关系 3 = 主体化关系 ``` --- ## 8.4 Movement / Trace 不要叫“最小单位”，叫“运动记录”。 ```ts Movement { id space_id subject_id content movement_type created_at linked_objects linked_relations } ``` 类型可以是： - message； - judgment； - attempt； - dispatch； - landing； - residue； - correction； - decision。 它只是记录形式，不是本体原子。 --- ## 8.5 Dispatch 主体联合记录。 ```ts Dispatch { id space_id initiator_subject joined_subjects shared_tension extension_needed boundary expected_return status } ``` --- ## 8.6 Consensus / Decision 阶段性共识。 ```ts Consensus { id space_id participants adopted_claim unadopted_claims decided_by reason cost residue reopen_condition } ``` --- ## 8.7 LearningRecord 学习记录不是复盘表，而是主体因完整展开产生的改变。 ```ts LearningRecord { id subject_id attempt_or_process what_fully_unfolded what_changed_in_subject new_relations new_residue } ``` --- # 9. 第一版软件页面 ## 9.1 组织空间首页 显示： - 组织当前目标； - 当前软件承载状态； - 当前活跃项目； - 当前活跃主体； - 当前显现关系； - 当前开放张力； - 最近学习变化。 --- ## 9.2 沟通界面 三栏结构： ```text 左：空间 / 项目 / 主体 / 关系 中：沟通流 右：当前上下文生命面板 ``` 右侧面板动态显示： - 当前空间； - 当前主体； - 当前关系； - 当前张力； - 当前调度； - 可能的残余； - 调度产生的学习。 --- ## 9.5 关系空间界面 显示： - 当前空间中的对象； - 潜在关系； - 已显现关系； - 活关系； - 主体化关系； - 关系如何影响上下文； - 关系自身历史。 --- # 10. 实现路线 ## 阶段 0：先做设计骨架文档 不是写最终理论，而是写当前开发准则。 需要几份文件： ```text 01-项目当前目标.md 02-核心原语当前理解.md 03-主体与关系当前理解.md 04-组织第一阶段形态.md 05-压缩风险分类.md 06-软件第一阶段设计原则.md ``` 这几份文件不是给人看的说明书，而是后续软件上下文的基础。 --- ## 阶段 1：做最小沟通软件 先不要做复杂 AI。 功能： - 创建组织； - 创建空间； - 创建项目； - 多参与者聊天； - 消息保存； - 从消息中手动创建对象； - 手动创建关系； - 手动创建调度； - 手动记录阶段性共识。 目的： > 先让组织有一个能沟通、记录、显现关系的场。 这一步可以很粗糙，但必须能跑。 --- ## 阶段 2：加入 AI 参与者 功能： - 添加多个 AI 主体； - 每个 AI 可以进入某个空间； - 调用 AI 时带入当前空间上下文； - AI 回复保存为运动记录； - AI 可以提出对象、关系、残余、调度候选； - 你在沟通中确认或否认。 重点： > AI 不只是回复者，而是组织内的一个主体候选。 --- ## 阶段 3：关系系统生效 功能： - 关系可作为独立对象打开； - 关系有历史； - 关系可被讨论； - 活关系影响 AI 上下文； - 压缩风险关系可触发提醒。 验收： 当讨论“组织软件”时，系统自动带入： ```text 风险：不要把新存在压缩成组织软件。 关系：组织是第一阶段形态，不是最终目标。 ``` --- ## 阶段 4：调度与学习 功能： - 从沟通中创建调度； - 调度 AI 或主体参与某个张力； - 记录返回； - 在沟通中形成学习记录； - 学习改变主体状态或关系状态。 --- ## 阶段 5：自指运行 把软件自身建设作为项目放进软件里。 之后所有架构设计都在软件内部沟通中进行。 从这时开始： > 这个承载开始承载自己的继续建构。 --- # 11. 第一阶段验收标准 第一阶段成功，不看功能多不多，而看： ## 1. 组织能持续 关闭再打开，组织仍然知道： - 当前有哪些空间； - 哪些主体； - 哪些关系； - 哪些项目； - 哪些张力。 --- ## 2. 关系不是死链接 一条关系能： - 被打开； - 被讨论； - 有历史； - 有状态； - 影响 AI 上下文。 --- ## 3. 主体不是固定用户类型 一个 AI、一个概念、一个项目、一个关系，都可以被提升为不同程度的主体。 --- ## 4. 调度不是任务分配 调度记录体现的是主体联合，而不是派单。 --- ## 5. 学习在沟通中发生 学习不是对话结束后的表格，而是在沟通中被提出、确认、写入，并改变后续。 --- ## 6. 架构能在自身内部继续设计 软件能承载“软件如何继续设计”的沟通、关系、调度和学习。 --- # 12. 最后给一个真正的第一步 不要先做 Context Builder。 也不要先做完整 UI。 第一步应该是： > **做一个最小组织沟通空间。** 它只需要： 1. 创建空间； 2. 创建对象； 3. 创建主体； 4. 多主体沟通； 5. 从沟通中创建关系； 6. 从沟通中创建调度； 7. 从沟通中记录阶段共识； 8. 所有内容保存； 9. 下次打开仍然在。 第一版哪怕没有复杂 AI，也可以先手动模拟 AI 主体；之后再接模型。 因为你现在真正想验证的是： > **组织形态能不能作为第一数字承载开始存在。** 而不是： > Context Builder 能不能拼上下文。 Context Builder 是后续器官。 第一器官应该是： > **沟通空间 + 关系显现 + 主体共存。** 这才更接近你现在说的第一阶段。 这份计划里所有提到关系的，都没有理解关系是什么，关系是依附于空间的，也就是，在空间内，主体与主体之间，是关系，对象与对象之间是关系，空间内。 其他的还好，可以继续 计划b 好，我现在给你第一阶段的实施计划。 在动手之前，我先把你确认过的第一层内容全部摊开，然后让第二层从它们里长出来。不预设架构，不套模板。 --- ## 一、第一层（已经确认的定义） 这些是接下来所有设计的基底。第二层的每一个决定，都要回到这里检验。 **存在** - 展开与维持，不能空无。 **主体** - 有一定独立性，能被区分和认出； - 处于所在空间中，顺着空间结构展开； - 有门槛——达到一定程度才被视为主体； - 不限于人和AI，概念、项目、关系、历史都可能成为主体（后续实现）； - 具有展开性。 **空间** - 关系结构，不是容器； - 承载与空间不分离，承载会塑造空间性质。 **关系** - 对象与对象在空间内的共存本身是一种存在； - 关系是独立的存在，不是对象的附属属性； - 存在需要显现，显现的情况有很多（意味着关系不总是被看见，但它一直在）。 **尝试** - 广义的、主体在空间中的展开运动。 **可能** - 空间内的可能，还没被兑现的、可以长出来的。 **判断** - 尝试的一种特殊形态——透支； - 浓缩、高效、一次性的展开； - 一般展开是完整的，判断是一次性把可能全部兑现，所以叫透支； - 因此会牺牲完整性和细节。 **现实** - 幻觉/可能在实际情况上的落地； - 落地有多种形态：成功、变形、阻碍、空响、超出预期、主体不适。 **残余** - 判断（透支）之后必然留下的、被跳过和牺牲的部分； - 是下一次展开的起点。 **学习** - 认知本身； - 尝试的完整展开、主体本身的完整展开； - 和判断（透支）对立——判断跳步，学习走完。 **调度** - 主体与主体的联合； - 主体为了展开自己做不到的部分，与另一个主体形成联合； - 是延伸和扩展，不是命令。 **空无** - 建构态度，不是工程字段； - 保留未透支的可能性。 **分层** - 第一层：理念、思想、原语； - 第二层：第一层的承载与实现； - 每一层从上一层长出来，是生成关系，不是并列模块。 **最小单位** - 不固定，是相对的； - 只要满足两个条件就成为一个单元：作为主体（有一定独立性）+ 具有展开性； - 系统需要在不同粒度上运作。 --- ## 二、第二层怎么从第一层长出来 我不再一次给你一个完整方案。我一条一条走，让第二层的每个决定都能追溯到第一层的哪个定义。 ### 从"主体+展开性"长出：软件的基本组织方式 第一层说：任何有独立性和展开性的东西都是一个单元。 那软件里不能只有"消息"和"任务"这种统一类型。软件里的对象应该是： -
