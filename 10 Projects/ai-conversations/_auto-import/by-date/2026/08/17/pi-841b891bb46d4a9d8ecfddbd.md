# Pi 简介

**Pi** 是一个极简的终端编码代理（terminal coding harness）。它的核心理念是：**让你去适应工作流，而不是反过来让工具框定你**——无需 fork 或修改 Pi 内部代码，就能用 TypeScript 扩展、Skills、Prompt 模板和主题来定制它。

## 核心特点

- **极简内核**：默认只给模型四个工具（`read`、`write`、`edit`、`bash`），能力按需扩展
- **高度可扩展**：通过 Extensions（扩展）、Skills（技能）、Prompt Templates（提示模板）、Themes（主题）定制
- **Pi Packages**：把扩展/技能/模板/主题打包，通过 npm 或 git 分享给他人

## 四种运行模式

| 模式 | 说明 |
|------|------|
| 交互模式 | 默认的终端 TUI 界面 |
| `-p` / `--print` | 打印响应后退出 |
| `--mode json` | 输出 JSON 事件流 |
| `--mode rpc` | 供进程集成，通过 stdin/stdout 通信 |

另有 **SDK**，可将 Pi 嵌入到你自己的应用里。

## 支持的服务商

- **订阅**：Anthropic Claude Pro/Max、OpenAI ChatGPT（Codex）、GitHub Copilot
- **API Key**：Anthropic、OpenAI、DeepSeek、Google Gemini、Groq、xAI、OpenRouter、Mistral、Bedrock 等几十家

## 设计哲学（刻意"不做"的事）

Pi 故意**不内置**这些功能，而是让你按需自己构建或安装第三方包：

- ❌ 无 MCP
- ❌ 无子代理（sub-agents）
- ❌ 无权限弹窗
- ❌ 无 plan mode
- ❌ 无内置待办清单
- ❌ 无后台 bash（用 tmux 代替）

## 会话管理

- 会话以 **JSONL 树形结构**存储，支持原地**分支**（branching）
- `/tree` 跳转到任意历史节点继续，`/fork`、`/clone` 派生会话
- 自动/手动**压缩**（compaction）处理超长上下文

# Pi 的 bash 工具详解

`bash` 是 Pi 默认提供的核心工具之一（其余为 `read`、`write`、`edit`、`grep`、`find`、`ls`）。它的作用是让模型在**当前工作目录**下执行 shell 命令，并把 stdout/stderr 返回给模型。

## 1. 工具参数

```json
{
  "command": "ls -la",     // 必需：要执行的 bash 命令
  "timeout": 30            // 可选：超时秒数（默认无超时）
}
```

- `timeout` 必须是有限的**正数（秒）**，最大约 24.8 天（`2^31-1` 毫秒）
- 默认**没有超时**，命令可以一直跑，直到模型中止或出错

## 2. 执行机制

### Shell 解析顺序（`getShellConfig`）

| 平台 | 顺序 |
|------|------|
| 通用 | 1. 用户配置的 `shellPath`（如 Cygwin 路径，支持 `~`） |
| Windows | 2. Git Bash（`Program Files\Git\bin\bash.exe` 等已知位置）→ 3. PATH 上的 `bash.exe`（Cygwin/MSYS2/WSL）→ 找不到则报错并提示安装 Git for Windows |
| Unix | 2. `/bin/bash` → 3. PATH 上的 `bash` → 4. 回退到 `sh` |

### 进程启动（`createLocalBashOperations`）

- 用 Node 的 `spawn` 启动 shell，命令通过 `-c` 参数传入；**旧版 WSL bash**（`system32\bash.exe`）特殊处理为 stdin 传入
- **Unix 上以 detached（独立进程组）方式启动**，这样能连同子进程一起杀掉
- stdout 和 stderr **实时流式**返回，两个流都走同一个回调
- 执行前校验 cwd 是否存在，不存在则报错
- 子进程会被**跟踪登记**，父进程收到 SIGHUP/SIGTERM 时统一清理

### 超时与中止（kill 整个进程树）

| 场景 | 处理 |
|------|------|
| 超时 | `killProcessTree` 杀掉整个进程树，报 `Command timed out after N seconds` |
| 模型中止（abort signal） | 同样杀进程树，报 `Command aborted` |
| Windows | `taskkill /F /T /PID <pid>` |
| Unix/Linux/Mac | 对进程组发 `SIGKILL`（`kill(-pid)`），失败再回退到单进程 |

### 退出码

- 退出码 **非 0**（或 null）会作为错误抛给模型：`Command exited with code N`
- 退出码 0 正常返回

## 3. 输出处理

### 截断规则（重要）

内置上限：**2000 行** 或 **50KB**（约 1 万 token），**先到先截**，且**只保留尾部**（`truncateTail`）。

```
[Showing lines 1951-2000 of 5000. Full output: /tmp/pi-bash-xxxx.log]
```

- 截断时，**完整输出会保存到临时文件**（`/tmp/pi-bash-<随机hex>.log`），路径在结果里提示
- 内存有滚动缓冲（`maxRollingBytes = maxBytes * 2`），防止超长输出撑爆内存
- 无输出时显示 `(no output)`
- **二进制/控制字符会被清洗**（`sanitizeBinaryOutput`）：保留 `\t`、`\n`、`\r`，过滤掉其他控制字符、孤立代理对、Unicode 格式字符（防止终端 string-width 崩溃）

### 流式更新

- 交互模式下输出**每 100ms 节流刷新**一次（`BASH_UPDATE_THROTTLE_MS`）
- UI 里默认折叠显示最后 5 行，可展开（`Ctrl+O` 折叠/展开工具输出）

## 4. 注入的环境变量

每次 bash 命令执行时，Pi 会注入会话状态（`createBashTool` 默认开启）：

| 变量 | 含义 |
|------|------|
| `PI_SESSION_ID` | 当前会话 ID |
| `PI_SESSION_FILE` | 会话 JSONL 文件绝对路径（临时会话则不设置） |
| `PI_PROVIDER` | 当前模型服务商 |
| `PI_MODEL` | 当前模型 ID |
| `PI_REASONING_LEVEL` | 当前思考等级（off/minimal/low/…/max） |

> 这些变量在**每条命令启动时解析**，切换模型/思考等级后下一条命令立即生效。注意：这些变量只注入 **LLM 调用的 bash 工具**，不注入用户输入的 `!`/`!!` 命令。

## 5. 配置项（`settings.json` → Shell 节）

| 设置 | 说明 |
|------|------|
| `shellPath` | 自定义 shell 路径（如 Cygwin），支持 `~` |
| `shellCommandPrefix` | 每条命令的前缀（如 `"shopt -s expand_aliases"` 启用别名展开） |
| `npmCommand` | npm 相关操作的命令 argv（与本工具无直接关系） |

## 6. 扩展自定义

bash 工具是可深度定制的（详见 `docs/extensions.md`）：

- **`createBashTool(cwd, options)`**：创建自定义 bash 工具
- **`spawnHook`**：执行前改写命令、cwd、env，例如：
  ```typescript
  createBashTool(cwd, {
    spawnHook: ({ command, cwd, env }) => ({
      command: `source ~/.profile\n${command}`,
      cwd: `/mnt/sandbox${cwd}`,
      env: { ...env, CI: "1" },
    }),
  });
  ```
- **`exposeSessionEnvironment: false`**：关闭 `PI_*` 环境注入
- **`createLocalBashOperations()`**：复用 Pi 内置的本地 shell 后端（进程树终止、shell 解析等）
- **`BashOperations` 接口**：可完全替换执行后端，用于 SSH/容器等远程执行（见 `examples/extensions/ssh.ts`）
- **覆盖内置工具**：注册同名 `bash` 工具即可完全接管（交互模式会显示警告）

## 7. 与用户 `!` 命令的区别

交互模式编辑器里用户可主动执行命令（**不是** LLM 工具调用）：

| 命令 | 行为 |
|------|------|
| `!command` | 执行并把输出发送给 LLM |
| `!!command` | 执行但**不**发送给 LLM |

这些用户命令走 `user_bash` 事件，扩展可拦截（如用 `on("user_bash")` 路由到 SSH/沙箱）。

## 8. 权限与安全

- bash 工具拥有**完整系统访问权限**，可执行任意命令
- 可用 CLI 开关限制：
  - `--tools read,grep,find,ls`（只留只读工具，实现只读模式）
  - `--exclude-tools bash`（单独禁用 bash）
  - `--no-builtin-tools` / `--no-tools`
- Pi 刻意**不做权限弹窗**（哲学之一），官方建议：在容器里跑、或用扩展自己实现确认流程（见 `docs/containerization.md`）

# Pi vs. DeepSeek Harness（dsh）对比

先说结论：**两者都是 TypeScript 写的开源 agent harness，都强调"可扩展"，但哲学和形态差异很大。** 一个是以终端为中心的极简工具（Pi），一个是以"一切皆插件"为架构、以 Web UI 为主的产品（dsh）。

> 说明：dsh 目前处于 **developer preview（开发者预览）**，官方明确警告会有破坏兼容性的变更；以下信息基于我实时抓取的 dsh 官方仓库（`deepseek-ai/deepseek-harness`）当前文档。

## 一句话定位

| | Pi | dsh (DeepSeek Harness) |
|---|---|---|
| 作者 | Earendil Works（badlogic/Mario Zechner） | DeepSeek AI |
| 定位 | **极简终端编码 harness**，核心最小、按需扩展 | **"一切皆插件"的 agent 框架**，由 Cordis 驱动 |
| 许可证 | MIT | MIT |
| 状态 | 稳定发布 | 开发者预览，快速迭代 |

## 核心差异

### 1. 界面形态

| | Pi | dsh |
|---|---|---|
| 主界面 | **终端 TUI**（pi-tui 组件库） | **Web UI**（默认 `http://127.0.0.1:3080`） |
| 其他模式 | print、JSON 事件流、RPC、SDK 嵌入 | headless 一次性 runner（无服务器） |
| 编辑体验 | 终端内编辑器、`@` 文件引用、图片粘贴 | 浏览器界面、ConversationNode 渲染器 |

**Pi 是终端原住民**；**dsh 是浏览器优先**。

### 2. 扩展机制（最关键的区别）

**Pi**：TypeScript 扩展 + Skills + 提示模板 + 主题，打包成 Pi Package（npm/git，`pi` manifest）。

```typescript
// pi 扩展：一个默认导出的函数
export default function (pi: ExtensionAPI) {
  pi.registerTool({ name: "deploy", ... });
  pi.on("tool_call", async (event, ctx) => { ... });
}
```

**dsh**：Cordis 插件系统 —— 插件向共享 context 贡献**服务、类型化事件、可逆副作用**。连模型适配器、工具注册表、会话日志、agent 循环本身都是插件，**没有特权核心**。

```
Profile → Bundles（分层 patch 叠加）→ cordis.patch.yml
```

- 扩展点靠**事件**：`agent/*`（观察/拦截进行中的工作）、`tools/*`、`fs/*`、`session/event` 等
- 有 **Seam（可替换能力）**概念：文件系统、子进程、shell、终端、沙箱、LSP、子代理都在统一接口后，可整体切换到远程沙箱

> 对比：Pi 的扩展是"挂载到 harness 上"；dsh 的插件是"harness 本身由插件拼成"。

### 3. 内置能力与安全

| 能力 | Pi | dsh |
|---|---|---|
| 权限弹窗 | ❌ 明确不做（建议跑容器） | ✅ 内置 sandbox + approval（审批）策略 |
| 沙箱 | 无内置（推荐 Docker/容器） | ✅ 内置沙箱 + 文件系统围栏（`fs-sandbox`），Windows 走 ACL 受限令牌 |
| 子代理 | ❌ 不做（用 tmux 或扩展自建） | ✅ 内置 host-level subagent provider |
| MCP | ❌ 不做 | 未在核心文档强调（有 LSP、seam 机制） |
| 计划模式 | ❌ 不做 | 通过 goal/agent preset 机制 |
| 后台任务 | ❌ 无后台 bash（用 tmux） | ✅ `ctx.jobs` 后台任务 + `job_*` 工具 |

**Pi 哲学：刻意不内置，靠你自建或装包**（no MCP/sub-agents/plan/permission popups/to-dos/background bash）。**dsh 则把沙箱、审批、子代理、后台任务作为一等公民内置。**

### 4. 模型支持

| | Pi | dsh |
|---|---|---|
| 默认模型 | 多 provider（Anthropic/OpenAI/DeepSeek/Gemini 等几十家 + llama.cpp） | **DeepSeek adapter 为主** |
| 其他 | 订阅（Claude Pro/Codex/Copilot）+ API key | 可选 Codex、Claude Code provider（需自行安装挂载） |

### 5. 会话模型

| | Pi | dsh |
|---|---|---|

### 6. 平台处理

- **Pi（Windows）**：优先找 Git Bash → PATH 上的 bash.exe（Cygwin/MSYS2/WSL）
- **dsh（Windows）**：bash 无 Windows runner，自动切换为 **pwsh**（PowerShell）栈，沙箱走 Windows ACL

# Pi 的 TypeScript 扩展 vs. dsh 的 Cordis 插件系统

两者都用 TypeScript，但**扩展模型的本源哲学不同**：Pi 是"一个固定的核心 + 挂载扩展"，dsh 是"没有特权核心，产品本身就是一个插件树"。下面从概念到代码逐一拆解。

---

## 一、核心心智模型

### Pi：一个默认导出的工厂函数

扩展是一个 TS 模块，**默认导出一个函数**，接收 `ExtensionAPI` 对象，通过**方法调用**命令式地注册一切：

```typescript
// my-extension.ts —— 一切通过 pi 对象注册
import type { ExtensionAPI } from "@earendil-works/pi-coding-agent";
import { Type } from "typebox";

export default function (pi: ExtensionAPI) {
  // 注册事件监听
  pi.on("tool_call", async (event, ctx) => { ... });

  // 注册工具 / 命令 / 快捷键 / CLI flag / provider
  pi.registerTool({ name: "greet", parameters: Type.Object({...}), execute(...) {...} });
  pi.registerCommand("hello", { handler(...) {...} });
  pi.registerShortcut("ctrl+x", { ... });
  pi.registerFlag("my-flag", { ... });
  pi.registerProvider("local", { ... });
}
```

- **入口**：一个函数，`ExtensionAPI`（`pi`）是唯一的交互面
- **加载**：用 [jiti](https://github.com/unjs/jiti) 直接跑 TS，无需编译
- **可异步**：`export default async function`，pi 会 await 它完成再继续启动
- **热重载**：`/reload`

### dsh：一切皆插件（Cordis）

dsh 底层是 [Cordis](https://github.com/cordiverse/cordis) 框架，核心思想（官方 Primer 总结为五条）：

1. **插件是实现了 `Service` 的对象**（函数、对象、或 `Service` 子类）
2. **Context 是服务的仓库**——插件用稳定的 `ctx.<key>` 认领/查找服务，而不是 import 具体实现
3. **用 `inject` 声明服务依赖**——加载顺序由依赖决定，而非手动排序
4. **类型化事件**——通过 TS 声明合并声明事件名，用 `emit`/`waterfall`/`parallel`/`serial` 分发
5. **注册都是可逆副作用**——用 `ctx.effect()`/`ctx.on()`，卸载时自动 unwind

```typescript
// 一个 Cordis 插件（函数形式）
import type { Context } from '@deepseek-ai/cordis'

export const name = 'hello'          // 诊断用元数据

export function apply(ctx: Context) {
  console.log('hello from my first plugin')
}
```

组合由**配置文件**驱动（`cordis.yml` / `cordis.patch.yml`），而非代码里 import：

```yaml
- name: './greeter.ts'
- name: './consumer.ts'
```

**关键点：dsh 连模型适配器、工具注册表、会话日志、agent 循环本身都是插件**，官方原话："There is no privileged core to patch（没有可 patch 的特权核心）"。

## 二、逐维度对比

### 1. 依赖声明与加载顺序

| | Pi | dsh (Cordis) |
|---|---|---|
| 依赖声明 | ❌ 无显式声明 | ✅ `export const inject = ['tools']` |
| 加载顺序 | 目录/文件顺序，事件按加载顺序执行 | 由**服务依赖**决定，与文件顺序无关 |
| 服务缺失 | — | 插件保持 **PENDING**，等依赖就绪再启动；依赖被卸载则插件也被卸载重载 |

```typescript
// dsh：inject 声明依赖，apply 里保证 ctx.greeter 已就绪
export const name = 'consumer'
export const inject = ['greeter']
export function apply(ctx: Context) {
  console.log(ctx.greeter.greet('world'))  // 保证可用
}
```

Pi 没有服务/依赖的概念，扩展之间通过事件和共享的 `pi`/`ctx` 协作，顺序靠约定。

### 2. 事件模型

**Pi**：固定命名的事件，handler **返回对象**来控制行为（拦截/替换/注入）：

```typescript
pi.on("tool_call", async (event, ctx) => {
  if (event.toolName === "bash" && event.input.command?.includes("rm -rf")) {
    return { block: true, reason: "Blocked" };   // 返回值 = 控制指令
  }
});
```

事件是**写死的一长串**：`session_start`、`tool_call`、`tool_result`、`input`、`before_agent_start`、`context`、`turn_start/end`、`message_*`、`model_select`、`user_bash`…… handler 链按加载顺序执行（middleware 式）。

**dsh (Cordis)**：事件是**类型化 + 四种分发模式**，是事件公开契约的一部分：

| 模式 | 是否 await | 分发顺序 | 有返回值？ |
|---|---|---|---|
| `emit` | 否 | 观察者按注册顺序 | 无 |
| `waterfall` | 否 | 观察者按注册顺序 | **有（around-middleware）** |
| `parallel` | 是 | 所有监听者并行 | 无 |
| `serial` | 是 | 观察者按注册顺序 | 有 |

waterfall 是"围绕式中间件"，靠 `next()` 委托：

```typescript
// Cordis waterfall：收到 (args, next)，调 next() 委托，不调则短路
ctx.on('tools/pre-execute', (tool, next) => {
  if (isDangerous(tool)) return next({ allowed: false })  // 替换结果
  return next()                                            // 委托
})
```

dsh 的扩展点（`agent/*`、`tools/*`、`fs/*`、`session/event`）比 Pi 的固定事件名更结构化，且区分"持久事实"（session 事件）vs"进行中的工作"（agent 事件）vs"能力适配"（capability 事件）。

### 3. 工具定义对比

**Pi**：typebox schema + `execute()`，直接返回内容块：

```typescript
pi.registerTool({
  name: "greet",
  label: "Greet",
  description: "Greet someone",
  parameters: Type.Object({ name: Type.String() }),   // typebox
  async execute(toolCallId, params, signal, onUpdate, ctx) {
    return {
      content: [{ type: "text", text: `Hello, ${params.name}!` }],
      details: {},
    };
  },
});
```

**dsh**：`defineTool`，参数 schema + **output.schema（规范 JSON 值）+ output.render（渲染成模型可见文本）** 分离：

```typescript
import { defineTool } from '@deepseek-ai/dsh-tools'

ctx.tools.register(defineTool({
  name: 'read_file',
  description: 'Read a file from disk.',
  parameters: { path: { type: 'string', required: true, description: '...' } },
  output: {
    schema: { type: 'string' },                       // 规范返回值
    render: (_args, value) => [{ type: 'text', text: value }],  // 模型看到的
  },
  async execute(args, exec) {
    // args 从 schema 自动推导类型；exec.signal 是取消信号
    return readFile(args.path, { encoding: 'utf8', signal: exec.signal })
  },
}))
```

dsh 的关键设计：**工具返回"规范 JSON 值"**（供 Code Mode 编程式调用 `await tools.read_file(args)`），人类可读文本在 `render` 里单独生成。Pi 则直接把内容块返回给模型。

### 4. 生命周期与可逆性

**Pi**：靠 `session_start`/`session_shutdown` 事件手动做资源清理，框架不强制：

```typescript
pi.on("session_start", () => startMyWatcher());
pi.on("session_shutdown", () => stopMyWatcher());
```

文档还特别提醒：工厂函数里**不要**启动后台资源（进程/socket/timer），要推迟到 `session_start` 或具体工具/事件里。

**dsh**：所有注册都是**可逆 effect**，卸载插件自动 unwind，无需手动清理：

```typescript
export function apply(ctx: Context) {
  ctx.effect(() => {
    // 注册的东西
    return () => { /* 自动在卸载时调用，清理 */ }
  })
}
```

官方规则："Every registration should have a disposer"（每个注册都应有清理器）。

### 5. 可替换能力（关键差异）

**Pi**：可以覆盖内置工具、替换 operations 后端，但**核心（agent 循环、会话管理、TUI）是固定的**，你扩展的是"外围"。

**dsh**：**Seam（接缝）概念**——一个可替换能力有三角色：Service Definition（接口）+ Service Provider（实现）+ Consumer（消费者）。文件系统、子进程、shell、终端、沙箱、LSP、子代理都藏在统一接口后：

> "Seams are why one provider swap changes the whole product. Pointing them at a remote sandbox moves Bash, PTY, and LSP with them, with no provider forks."

也就是说，dsh 里**换掉一个 provider 可以改变整个产品**——把文件系统和子进程 provider 指向远程沙箱，Bash/PTY/LSP 全部跟着走。这是 Pi 做不到的（Pi 需要逐个 override 工具或用 `user_bash` 拦截）。

### 6. UI 扩展

- **Pi**：扩展 TUI。用 `@earendil-works/pi-tui` 组件库，`ctx.ui.custom()` 做自定义交互界面、widget、status line、footer
- **dsh**：扩展 Web UI。注册 `ConversationNodeDefinition` + 渲染器；工具通过 `presentCall`/`presentResult` 生成 **card**（卡片式 UI，带 icon、location 等）

### 7. 分发与组合

| | Pi | dsh |
|---|---|---|
| 打包 | Pi Package（npm/git，`pi` manifest） | Bundle（含 `cordis.patch.yml`） |
| 组合 | 目录自动发现 + `settings.json` 列包 | Profile → Bundles → patch 分层叠加 |
| 覆盖 | 覆盖内置工具需同名注册 | patch 按行 id 替换整段配置 |
| 配置 | settings.json（扁平 key） | `cordis.patch.yml`（结构化、可 patch、`!!js` 表达式） |

dsh 的 profile/bundle/patch 是**分层叠加**的：`dsh-base` 第一层 → `dsh-web-app`/`dsh-headless` 第二层 → 用户 profile patch → home patch → `--patch`。每一层都能按 row id 替换上一层的配置。

## 三、总结对照表

| 维度 | Pi 扩展 | dsh Cordis 插件 |
|---|---|---|
| **入口** | 默认导出函数 `(pi) => {}` | `apply(ctx)`（函数/对象/Service 类） |
| **交互面** | `ExtensionAPI` 方法调用 | 共享 `ctx` + 服务查找 |
| **组合方式** | 命令式注册 | 声明式配置（yaml）+ `inject` |
| **依赖** | 无声明 | `inject: ['tools']` |
| **加载顺序** | 文件顺序 | 依赖拓扑 |
| **事件** | 固定名 + 返回对象 | 类型化 + 4 分发模式 |
| **中间件** | handler 链返回 `{block}` 等 | waterfall `next()` |
| **生命周期** | 手动 `session_shutdown` | 自动可逆 effect |
| **核心可替换** | ❌ 核心固定 | ✅ 无特权核心 |
| **能力接缝** | operations 接口（工具级） | Seam（系统级，fs/subprocess/shell/LSP） |
| **工具返回值** | 内容块 | 规范 JSON + render 分离 |
| **UI** | TUI（pi-tui） | Web UI + card |
| **热重载** | `/reload` | HMR |
| **打包** | pi package | bundle/profile |

---

## 一句话概括

> **Pi 的扩展**是"往一个极简但固定的 harness 上挂功能"，简单直接，适合轻量定制（加个工具、拦个危险命令）。
>
> **dsh 的 Cordis 插件**是"用插件拼出整个应用，连引擎本身都可替换"，强依赖注入、类型化事件和可逆性，适合构建高度可组合、可远程/沙箱化的复杂 agent 系统——代价是心智负担和复杂度更高（且目前还在 developer preview，API 会变）。

如果你想，我可以再展开某个具体点，比如 **Pi 的 `tool_call`/`tool_result` 中间件链 vs dsh 的 `tools/pre-execute` waterfall 逐行对比**，或者**两者的热重载机制差异**。
