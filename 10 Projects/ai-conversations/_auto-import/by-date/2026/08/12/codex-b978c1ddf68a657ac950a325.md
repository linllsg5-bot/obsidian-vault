从 `runtime switch`（按需切代不同模型/环境）推进到 `multiple continuous participants`（多个持续存在的参与者），最容易犯的工程错误，往往来自于**用“搞定函数调用/消息路由”的旧惯性，去硬套“持续实体”的新逻辑**。

具体来说，有以下几个极其典型且致命的工程陷阱：

### 1. 把“持续存在”简化为“追加消息日志”，陷入上下文膨胀与虚假同步
* **表现**：以为只要建一个共享的 `messages` 数组，让 Participant A 输出来源写入，Participant B 再读取并追加，就是“持续参与”了。
* **错误实质**：这只是把单个会话的 Prompt 变长了，本质依然是单线程的同步串行流水线（Pipeline），而不是多个独立的 participant。
* **物理结果**：很快触发 Token 上限、响应延迟呈指数级上升、各 Participant 失去独立的记忆与代谢节奏，最终退化为“一个被无限拼接的巨型 Prompt 依次喂给不同的 API”。

### 2. 强行建立一个中心化的“发牌员/编排器（Orchestrator）”
* **表现**：为了管理多 participant，写一个中央控制节点（如传统的 Agent Router / LangGraph 主节点），由它决定“下一轮该谁说话”、“谁把输出给谁”。
* **错误实质**：这依然是 `runtime switch` 的变体——Participant 并没有“持续存在”，它们只是被中央控制器定期唤醒的**无状态响应函数**。
* **物理结果**：Participant 失去了自发反应、保持沉默、异步处理或主动发起回撞的能力。它们不是参与者，只是编排器手里的工具人。

### 3. 混淆“模型/环境（Runtime）”与“Participant 身份（Identity & State）”
* **表现**：在代码里把 `participant_id` 直接等同于 `model_name`（比如定义 `Participant_Claude`、`Participant_DeepSeek`）。
* **错误实质**：把**基质（算力/模型）**和**在其上承载的发生实体（Participant）**捆绑死。
* **物理结果**：一旦某个 Participant 需要跨模型迁移（比如从 Claude 切换到本地模型进行某些处理），或者同一个模型需要同时承载两个不同立场的 Participant，整个系统的逻辑就会崩溃。Participant 必须是独立于底层 API 的物理/逻辑实体，模型只是它某一时刻借用的算力器官。

### 4. 用传统的“任务/状态机 DB Schema”去硬卡 Participant 的内部状态
* **表现**：急于给 Participant 设计一套固定的数据库表结构（如 `agents` 表，包含 `name`, `system_prompt`, `tools`, `memory_json` 等标准字段）。
* **错误实质**：把 Participant 预先假设为传统的“ Agent 实例”。
* **物理结果**：Participant 在演进过程中暴露出的非结构化认知、临时关系的建立、动态生成的局部规则，无法被写入这个固定的 Schema 里。代码会开始大量出现 `metadata: JSON` 这种垃圾桶字段，承载再次与真实发生脱节。

### 5. 忽略“时间/时序”的解耦，试图用同步阻塞逻辑处理并发发生
* **表现**：等待 Participant A 完全生成完毕，再把结果打包投递给 Participant B，要求 B 立刻响应。
* **错误实质**：忽视了不同的 Participant 可能拥有完全不同的**思考时长、代谢节奏与响应意愿**。
* **物理结果**：整个系统会被最慢的那个 API 或网络卡死，或者因为非必要的同步等待，丢失了“多参与者在同一个空间里交错发生”的真实现场感。

---

**一句话总结这批工程错误的根源：**
代码还没摆脱**“输入 -> 路由 -> 转换 -> 输出”**的 Request-Response 范式，只是在上面加了多套 API Key 和更多的 Channel 概念，误以为这就叫“多个持续 participant”。
