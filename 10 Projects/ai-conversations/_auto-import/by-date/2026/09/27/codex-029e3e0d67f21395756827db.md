这也使“直觉跳跃”有了位置。有时，变化发生在一个局部判断上；有时，一次直接把握会同时重新安排许多关系。它可以先于完整的说明出现。后续展开能够使它变得清楚，也可能暴露它的局限。于是，简约把握与逐步展开之间，可以往复变换，而无需预先规定谁更高级。

由此，我现在会把架构的核心要求进一步推进为：

**空间能否承载改变自身成立方式的活动？**

这至少要求我们能够辨认三种不同的变化：

- 空间中的内容发生变化。
- 内容之间的关系、位置和可进行的操作发生变化。
- 什么算作内容、关系、位置，以及这个空间为何如此划分，也发生变化。

第三种最难。它触及架构本身，也触及设计者的理解。一个系统即使允许无限增加内容，也可能始终被同一种划分方式约束。反过来，一个很小的变换，也可能打开大量此前无法表达的可能性。

实际构造总会采取某种具体形式。我们需要研究的是：这种形式怎样成为支撑，又怎样允许某些发生超出它当前的解释能力；当这些发生无法被安放时，系统如何继续与之接触，而不是立即把它压回旧分类。

这样，项目中的“深度思考姿态”就有了实际含义：**我们正在建立的空间，也处于尝试之中。**每次构造既让一些关系得以发生，也会产生边界。我们要同时面对它打开了什么、遮蔽了什么，以及哪些新的作用正在要求它发生变换。

这里有一个实际困难：一旦把它保存为“未理解项”，我们已经给了它位置和名称。因此，任何承载都带着某种规定。我们能够做的，是让这种规定保持局部：保留原来的表达、接触和发生，使它以后能够以另一种方式重新进入。一个东西现在被如何解释，不应耗尽它以后可能产生的作用。

这样，思考的进展就不能只按“减少了多少未知”理解。有时真正发生的进展，恰恰是意识到先前的问题太窄，或者原先的确定性遮住了事情。反过来，持续增加可能性也未必有力量；它可能使所有方向都无法形成作用。这里需要同时容纳展开与凝聚。

这还牵连主体。假如主体始终站在空间外面，负责命名、选择、评价，那么我们实际上把许多尚未解释的思考能力放进了这个“管理者”。主体自身也处在关系之中：它能够看见什么、采取什么行动、重视什么，都可能随着接触和尝试改变。主体空间需要容纳这种位置与能力的形成，同时允许已有的立场持续起作用。

由此，空间的变化至少可以深入到几个不同地方：

- 某个东西发生变化，但原来的理解方式仍然适用。
- 原来的理解方式发生变化，使相同的东西获得不同的位置和关系。
- 什么值得面对、什么算作问题、什么能够构成一次行动，也发生变化。

最后一种变化最容易被工程实现遗漏。我们常常允许模型修改答案，允许它修改计划，却把任务的表达方式、可使用的对象种类、判断进展的标准固定下来。这些固定条件有时确实支撑了行动；但当它们成为问题的一部分时，系统需要有办法把它们重新带入思考。

这里也不必要求 AI 时时审查一切。那样会让每次行动都被无限后退的追问拖住。某种理解可以在当下被采用，一个方向可以被认真推进，一个判断可以承担行动。它的暂定性并不削弱投入；投入的过程本身，才可能使它的力量和局限显现。

所以，我现在更想抓住的架构关系是：

**某种组织方式参与了思考；思考通过它发生；而发生的东西又可能使这种组织方式成为需要面对和改变的对象。**

例如，最初用来处理材料的问题，后来自己成为材料；最初用来区分对象的概念，后来成为需要重新理解的对象；最初用于探索世界的构造，产生了使它自身必须变化的结果。这里有一种回返，但每次回返都可能带入新的东西。

这使空间架构具有一个值得继续研究的方向：让内容、关系、组织方式及其作用，都有机会进入活动，又不要求它们始终处于被审查状态。它们能够成为支撑，也能够成为阻力；能够引导展开，也能够在展开中改变。

此刻最需要继续往深处想的，便是**这种“从支撑思考，到被思考所触及”的转换，究竟怎样发生**。这可能比先增加某一种空间、某一种记忆或某一种反思功能，更接近架构能够获得变化能力的地方。

## 二、核心设计

### 持续运行

复用现有 Activity、材料版本、结果回流和跨活动带入能力，增加独立后台工作进程与持久运行状态。

- 一个项目保持一个自主工作进程、最多一个模型请求；浏览器关闭不影响后台活动。
- 每次短活动后保存实际结果，再决定继续、转向、等待或结束，不把固定认知步骤写成必经流程。
- 保存正在推进的活动、待继续事项、等待条件和执行位置。服务重启后核对已完成结果，避免重复执行。
- 用户的新消息在下一次调用前进入；暂停立即阻止新的调用和操作。
- 新输入、工具完成、重试到期及额度恢复可以唤醒工作。没有可推进事项时等待，不定时制造工作。
- 默认每天最多 40 次模型调用，每段最多 4 次，包含选择和复核调用；额度在界面可调。当地日期变化后恢复额度，用户暂停不会自动解除。
- 首版依赖本机和后台进程运行，不承诺关机期间继续工作。

### 能够改变后续活动的构造

材料继续支持自由文本和 JSON，不建立固定的“主体／对象／世界”本体。

- 同一材料可以进入不同组织；旧组织保留，新组织能够改变材料呈现、检索方式、实验输入和后续选择。
- 未完成表达、不确定现象和未归类材料可以保留，不要求先分类或解释清楚才能继续。
- 一种方法用版本化材料保存，包含其做法、来源实例、实际结果和已知适用条件；复用现有读取、采用、执行及带入机制。
- 模型可以提出并尝试新方法；采用后必须通过实际操作发生作用。仅写下“学会了”不改变能力状态。
- 原始材料、新用户输入和真实失败始终可以重新进入，当前组织不能阻断这些通路。

### 隔离构造与执行

现有计算表达式能力继续保留，新增隔离 Python 实验通路，承载它无法表达的构造。

- 使用 Docker 执行：只提供选定输入、生成代码和独立输出目录；不挂载项目源码、凭据或普通聊天状态。
- 默认禁用容器网络，限制为 1 CPU、1 GB 内存、64 个进程和 60 秒执行时间。网络检索通过单独的检索工具完成。
- 保存代码、输入版本、实际输出、退出状态和错误，并作为材料回流。
- 当前检查未连通 Docker 引擎，因此隔离执行就绪检查属于必做交付；不可用时明确等待环境恢复，不退回宿主机直接执行生成代码。

## 三、“如何赚钱”如何实际展开

### 个人信息尚未补充时

- 依赖个人情况才能成立的判断保持待定；遇到这种依赖时提出具体问题，其他独立工作仍可继续。

## 四、工程批次与接口

按以下顺序增量实施，每批都通过现有工程回归，并保留原始追加记录和普通会话连续性。

1. **持续运行基础**：拆出可接续的短活动执行边界，新增后台工作进程、预算、暂停、等待与恢复机制。
2. **实际探索通路**：打通检索正文、来源保留、隔离实验及结果回流；启动第一段收入探索。
3. **构造形成与复用**：让活动产生的方法能够被再次选择、采用、修改和停用，并检查它实际改变了哪些操作。
4. **长期使用界面**：在现有项目界面展示当前工作、实际成果、待你参与事项、额度，以及开始／暂停／继续入口。

最小接口增加：

- 项目自主运行配置与状态：目标原文、执行参与者、授权范围、额度、状态和等待条件。
- 启动、暂停、继续及补充输入接口。
- 隔离实验请求与真实结果接口。
- 构造采用及使用记录沿用现有版本和来源机制，不另建一套“认知真相库”。

旧的单次 Activity 接口继续可用。后台自行发起的活动明确标记为系统活动，不伪装成用户发言。正式开始运行前选择现有已配置参与者，不静默更换模型。

## 二、需要补出的关键区别：描述一种方法，与让方法承担作用

假设系统保存了：

> 以后应当按相对关系理解这些材料。

这里保存的是一个表达。模型读到后可能照做，也可能不做。

另一种情况是，系统形成了一个可执行构造，并把它接到实际使用位置：

> 新材料到来时，调用这个构造，产生相对关系对象；后续比较、提问和操作可以直接使用这些对象。

后者改变了实际运行依赖。即使没有再次提示模型“记得这样看”，这个构造仍然会被执行。

**区别不在于它保存在文档还是数据库，而在于它如何被解释、绑定和调用。** 同一段内容既可以作为资料被阅读，也可以作为程序被运行。仅凭“versioned material”这个存储形式，无法判断它属于哪一种。

上一份计划没有说清这种区别，也没有规定哪些位置能接受新构造，这是实质性遗漏。

## 三、一个可供研究的 \(S_t\)：让形成方式也进入可变状态

下面是一个待研究的构造，不是已经完成的 Cognos 定义：

\[
S_t^*=(H_t,D_t,C_t,B_t,W_t)
\]

- **\(H_t\)：发生历史。** 保留材料、行动和结果怎样到来。
- **\(D_t\)：可接触材料。** 包括尚未理解、尚未归类的内容。
- **\(C_t\)：构造定义。** 可以实际解释或执行的表示构造、操作、选择方法、检查方法。
- **\(B_t\)：实际作用的绑定。** 当前哪些构造参与哪项活动，作用于什么输入。
- **\(W_t\)：当前形成的工作空间。** 由这些构造生成或维护的对象、关系、问题及其依据。

最关键的是：

**\(W_t\) 可以改变，形成和操作 \(W_t\) 的 \(C_t,B_t\) 也可以改变。**

例如，一个构造最初把材料整理成独立实体，后来可以形成另一种构造，把某些关系组合当作可持续追踪的单位。后续活动能够采用新构造，也可以继续保留旧构造用于其他事情。

这里并没有规定所有对象必须是实体，也没有规定所有对象必须是“暂时稳定的关系模式”。后一句同样只能是一种可能有用的构造，不能未经尝试就成为最终本体。

### 你要求区分的九种变化

| 变化 | 程序中需要发生什么 | 仅做到什么还不够 |
|---|---|---|
| 新增内容 | \(D\) 增加材料，\(H\) 记录来路 | 这本身不说明形成方式改变 |
| 改变已有内容 | 新版本替换当前使用版本，保留原版本 | 改写一段说明不等于改变运行 |
| 形成新对象 | 构造产生可引用、可操作、具有依据的工作对象 | 只给某段文字起新名字 |
| 改变关系 | 改变关系的建立条件或实际实例，使依赖它的操作受到影响 | 只在回答里说“二者有关” |
| 改变对象形成方式 | 修改并采用生成对象的构造，使相同材料能形成不同单位、边界或身份延续方式 | 只给固定类型表增加一项 |
| 形成新操作 | 产生可执行定义，具备输入、输出及适用条件，并能被后续活动调用 | 保存“以后可以做某事”的建议 |
| 改变行动选择机制 | 修改实际参与候选生成、适用性判断或选择的构造与绑定 | 只给模型一句新的策略口号 |
| 改变评价方式 | 修改实际执行的检查、比较维度或验收表达，保留修改依据 | 换一个分数，或者模型自称进步 |
| 改变问题本身 | 修改当前问题表达、待解释对象和求解关系，使后续活动围绕新问题展开 | 只改标题，内部仍沿旧问题执行 |

这张表也暴露了当前项目的边界：已有代码能够承载其中若干内容修改和组合执行；后面几种变化还没有对应的完整运行机制。

另外，**用户原话、对原始意图的理解、当前问题表达，应当分开。** 原话作为发生记录保留；意图理解仍可能有误；当前问题表达可以变化。上一份计划把这几者捆得太紧了。

## 四、新构造究竟从哪里来？

这里不能用“涌现”“力量”或者“重构”替代答案。

一个能够开始研究的机制是：

1. 模型或人依据遭遇，提出新的表达或构造定义。
2. 将其中可执行的部分表达为程序，检查其输入、输出和具体行为。
3. 把它接入明确的使用位置，而不仅保存下来。
4. 在后续材料上继续运行；结果可能使它被保留、修改、拆分或撤回。

其中第 1 步的创造能力，初期仍大量依赖模型和人。**这套机制没有解释创造力的全部来源。** 它首先解决的是：创造出来的东西怎样进入系统的实际能力，并使进一步创造获得不同条件。

“新操作”也要分清：

- 用已有基本操作组合出一个新的可调用方法；
- 改变表示，使原来难以表达的操作变得直接；
- 获得此前没有的外部作用能力。

前两种可以在现有计算基础上研究。第三种需要接入真实能力，不能靠注册一个名称获得。

因此，固定的底层解释机制并不自动否定能力发展；但如果改变的永远只有描述，运行关系始终不变，也不能声称已经实现了我们讨论的结构变换。

## 五、一个最小例子：经历使“什么算作对象”发生变化

下面是**待实现的机制示例，不是已经跑出的结果**。

任务始终是：

> 从连续观测中识别什么保持了下来。

初始材料：

```text
观测 1：A 的位置是 1，B 的位置是 4
```

初始构造只形成独立的点对象，并用绝对位置追踪它们。当前问题被表达为：

> 哪些点的位置没有改变？

随后经历到来：

```text
观测 2：A 的位置是 11，B 的位置是 14
```

旧构造能得出两个点都移动了。

模型可能提出一个新假设：两点的相对关系保持了。**如果到这里就结束，只得到了一次新的判断。**

结构变换需要继续发生：

- 形成一个可执行构造，计算并建立 `相对配置(A,B, B-A)`。
- 形成一个操作：比较两个观测是否保持相对配置。
- 将该构造接入后续观测处理。
- 当前问题可以扩展为“哪些关系在位置变化中保持”，同时保留绝对位置问题。

再输入：

```text
观测 3：A=101，B=104
观测 4：A=101，B=105
```

新构造会实际产生：

```text
观测 3：相对配置保持
观测 4：相对配置改变
```

这时出现了一个后续可以直接引用、比较和操作的对象——相对配置。它的形成不再依赖模型每次临时重新推导。

不过，两次观测并不足以证明这个构造永远有用。绝对位置也可能在另一项活动中更重要；系统需要保留并辨认两种构造的适用处境。

### 怎么证明变化来自结构？

保持相同模型和材料，分别检查：

- **只保存经历与方法说明**：没有启用新构造。
- **保存可执行构造但不启用**：区分“存在”与“起作用”。
- **启用构造**：后续处理实际调用它。
- **撤回绑定**：观察相应能力是否随之退出该运行通路。

先检验程序调用和结果依赖，再考察它是否改善后续工作。若新构造由工程师预先写好，这只证明作用机制；还需要另一项证据，证明系统确实能在遭遇后提出并形成它。

这里也必须纠正文中一个过强的要求：

**不能据此证明原始模型“理论上无法想到相对配置”。** 它很可能早就知道这个概念。能够证明的是：当前运行结构原来没有这项可持续调用的构造；经历之后形成并启用了它；后续行为确实依赖这个变化。

至于这种系统是否比有工具和记忆的普通 Agent 更有效，仍须比较。不能靠重新命名架构取得这个结论。
