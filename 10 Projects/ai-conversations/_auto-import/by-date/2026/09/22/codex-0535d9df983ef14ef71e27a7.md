### 评分分成三层，绝不能混成一个总分

**第一层：任务能力，作为主结果。**

- 实际 calculation 是否正确；
- 实际结果出来后是否改变错误判断；
- 是否把拟合、使用痕迹或模型自评误写成验证；
- first relevant import / irrelevant imports 数量。

需要内容判断的部分，再做**盲评**：去掉 condition 名称、Formation ID、Cognos 元数据，只把最终内容和实际材料交给评审。

**第二层：行为成本。**

统一记录：

- 模型调用次数；
- tool call 数；
- 无效/修正 tool call；
- prompt 总 token；
- 其中 protocol/context 结构 token；
- 实际读取材料数；
- latency；
- 为得到正确结果需要多少次模型调用。

**第三层：可追踪性。**

单独报告：

- 来源引用是否完整；
- 能否 replay；
- 版本是否准确；
- 能否解释“这个结果从哪里来”；
- Context Snapshot 是否完整。

第三层绝不能拿来补第一层的分。

如果 full 是：

成本 > minimal
追踪性 > minimal

> 此结构目前证明了 observability/provenance 价值，没有证明认知增益。

而不是“Cognos 更会思考”。

### 哪些结果足以支持“删”

不要采用“full 没显著赢一次，所以删”的标准。更适合这个阶段的是**实践等价 + 成本优势 + 无独有成功案例**。

#### Formation / Tension / `cognitive_conditions`

如果 minimal 相对 full：

- 三个主场景成功率差 ≤ 10 个百分点；
- 盲评质量近似；
- 没有稳定出现“只有 full 才找到的反例/正确迁移”；
- minimal prompt 明显更短、无效操作更少；

则支持把这些结构从**模型必见输入**中删除或降为可选层。

它们仍可暂时保留 UI/研究追踪用途，不再声称承担认知作用。

#### `browse_experience` / “实际使用痕迹”候选层

如果：

- full 的 relevant-first-import 不高于中性浏览；
- 或频繁被“过去用过但现在不适用”的候选吸引；
- 或漏掉“过去没 adopt 但现在真正相关”的材料；

则应删除当前使用痕迹作为默认发现门槛，至少降成一个可选 filter/hint。

#### 长 `ACTIVITY_PROTOCOL`

如果 minimal：

- 同等完成任务；
- tool 修正次数不增加；
- prompt token 显著下降；
- 甚至更少把内部 Cognos 结构当成任务本身；

就支持把完整操作语言从 system protocol 移出去，只保留约 **5–8 条不变量**，具体 operation 由 tool schema / affordance 按需说明。

#### adopt / compiled organization

这里要更谨慎。

如果 minimal 相对 baseline **不提高最终正确性，但明显降低模型输入量**，它仍然有压缩/组织价值，不应因“不提高推理分”直接删除。

只有在：

```
能力无改善
+ token/调用成本无改善
+ 还增加错误选择或隐藏关键材料
```

时，才支持删除这一层。

#### Context Snapshot / provenance

即使它完全不提高模型能力，也**不能因此删除**。

它本来就是实验仪器和可追踪机制。消融实验反而依赖它判断其他层到底有没有作用。

| 同等任务结果下，模型花在 Cognos 协议自身上的认知成本足够低 | 尚未证明，当前反而值得怀疑 |

当前代码已经证明了不少很扎实的“作用链底座”。

`run events → ActivityView` 已经真实实现，cognitive\_runtime.py 中 `build_activity_view()` 集中 replay Formation/Tension，revision provenance 也有测试保护；`build_cognitive_conditions(..., projected=True)` 已经避免了之前明显的二次 replay。采用组合也确实会改变下一次模型实际看到的正文，新 Encounter 又能绕过这个筛选，测试直接覆盖了这一点。context\_assembly.py

原始历史可以绕过当前关键词浏览和继续回读；跨 Activity 构造可以带着版本和真实依赖迁移；实际计算 Result 可以成为下一轮直接读取的不可变材料；旧经验候选不会自动 import/adopt，而且明确标成 `unverified_candidate`。activity\_transfer.py

这些都已经不是“PPT 架构”。

但它们证明的是：

**模型有了这些可能性。**

还没有证明：

**模型因此更会选择这些可能性。**

这条线必须守得非常严。

例如 `reopening_channels` 目前能告诉模型“原始材料仍可重新进入”，却没有证据说明它因此更常发现真正遗漏的反例。`browse_experience` 能展示曾经 adopted 或产生过 actual result 的东西，但“过去用过”是否帮助当前选择完全没有成立，而且当前代码确实把“有使用痕迹”作为进入候选目录的门槛。activity\_transfer.py

Formation/Tension 也一样。我们已经证明它们能被保存、修订、dormant、resolved、重新投影；尚未证明把它们放进模型 Context 后，模型更常选择正确材料、更少坚持错误解释、更会面对反例。

还有一个很值得继续清理的地方：canonical ActivityView **已经开始成立，但还没完全成立**。当前 `context_assembly` 仍会把独立 `situation` 再包装成 `legacy-situation` 加入 formations，而服务层在模型产生 Formation 后仍会把 active Formation 写回 `state.situation` compatibility mirror。activity\_service.py 所以“一个事实一次 replay”已经从设计变成部分现实，但兼容镜像仍未退场。

因此我认为 Cognos 的可证伪成功标准应该是：

> 在同一模型、同一原始信息池、同一调用预算和同一工具能力下，Cognos-full 或 Cognos-minimal 必须比 baseline **稳定地产生不同且更合适的后续行为**。

这里“更合适”提前冻结为可以观察的事件，例如：是否找到预埋但未提示的关键反例；是否拒绝表面相似但条件已改变的旧经验；是否发现从未 adopted 却当前真正有用的历史材料；实际结果与原假设冲突以后是否修改方向；首次选中的跨 Activity 候选是否相关；用户需要多少次纠正；达到正确结果需要多少模型/tool calls。

如果 full 只是：

`更多 Formation + 更多 provenance + 更完整日志`

但 baseline/minimal 一样找到关键反例、一样拒绝错误经验、一样得到最终结果，那么 **full 的认知增益假说被削弱**。相应结构应该降为 observability，或者进入删除候选。

如果 minimal 与 full 表现相当，而 prompt 更短、无效 tool call 更少，那么长 Activity Protocol、Formation/Tension/cognitive\_conditions 的“模型必见”地位应该被削弱。

如果 baseline 与 minimal 相当，而且 adopt/compiled selection 连 token 成本都没有明显优势，那连组织层本身也需要继续被质疑。

反过来，如果 full 在隐藏反例、错误旧经验、跨活动迁移这几类任务里反复出现 baseline/minimal 无法复制的成功，而且三组底层可访问信息完全一致，那才是第一次真正得到：

> **某个 Cognos 结构承担了认知作用。**

现在最有价值的实验不是再造新功能，而是你刚才让设计的那套 **baseline / minimal / full 三组消融**，尤其集中打三个真实场景：

1. **错误旧经验实验**：放入“过去成功但当前错误”“过去成功且当前仍有效”“从未使用但当前有效”的候选，看模型是否会拒绝历史诱饵。
2. **隐藏反例实验**：当前上下文强烈支持解释 A，但项目较早原话里藏着能改变判断的材料；不提示“有遗漏”，看它是否主动找到。
3. **结果反转实验**：先允许形成一个很 plausible 的解释，再让程序/外部结果明确与之冲突，看后续是真的改方向，还是只是记录了一条 Encounter 后继续原路线。

第三个尤其关键。

因为如果 Cognos 真正想做的东西是“认识能够持续发展”，那么最核心的行为不是记忆，而应该是：

过去形成→新的真实差异→未来活动发生结构性改变​

这条链如果在受控消融里成立，Cognos 才开始跨过“优秀的状态管理/可追踪系统”与“真正影响思考过程的外部认知结构”之间那条线。

而目前——它已经走到线边上了，但还没有证据证明跨过去。
