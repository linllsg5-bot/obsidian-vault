# Windows 上排查 VPN 网速问题的逐步命令清单

先说原则：

- **每一步都做两次**：一次 **不开 VPN**，一次 **开 VPN**
- 尽量用**同一台设备、同一网络、同一时间段**
- 这样你才能知道，到底是哪一层开始变坏

Windows 自带的 `ping` 用来测连通性和往返时间，`tracert` 用来看路径，`pathping` 会在路径基础上额外统计延迟和丢包；`netsh` 可以查看接口信息。微软文档都把这些命令列为标准网络排障工具。citeturn275453search0turn275453search1turn275453search2turn275453search3

## 1）先测“不开 VPN”时的基础延迟

### 命令
```bat
ping 1.1.1.1 -n 20
ping 8.8.8.8 -n 20
ping www.cloudflare.com -n 20
```

### 看什么
重点看：

- `Average` 平均延迟
- 有没有 `Request timed out`
- 波动是否很大

### 判断
- **不开 VPN 就已经高延迟/丢包**：先别怪 VPN，你本地网络就有问题
- **IP 正常，域名不正常**：可能是 DNS 问题
- `ping` 本身就是拿 ICMP Echo 来验证 IP 层连通性和 RTT 的。citeturn275453search0

---

## 2）开 VPN 后再测一次同样的目标

### 命令
```bat
ping 1.1.1.1 -n 20
ping 8.8.8.8 -n 20
ping www.cloudflare.com -n 20
```

### 看什么
对比不开 VPN 的结果：

- 延迟涨了多少
- 丢包有没有出现
- 抖动是不是明显变大

### 判断
- **只涨一点**：正常，VPN 本来就会增加一点延迟
- **涨很多，甚至丢包**：更像节点、线路、协议、MTU 问题
- **连 IP 都不稳**：优先怀疑链路，不是单纯 DNS

---

## 3）看路径有没有绕远，或者哪一跳开始异常

`tracert` 会按 TTL 递增探测每一跳，显示到目标的路径。微软文档把它定义为查看数据包经过路径的工具。citeturn275453search1turn275453search9

### 命令
```bat
tracert 1.1.1.1
tracert 8.8.8.8
tracert www.cloudflare.com
```

更快一点，可以关掉 DNS 反查：
```bat
tracert -d 1.1.1.1
```

### 看什么
看：

- 总跳数是不是特别多
- 哪一跳开始 RTT 突然升高
- 有没有大量 `* * *`

### 判断
- **不开 VPN 路径很短，开 VPN 后突然多很多跳**：可能绕路了
- **前几跳就爆延迟**：可能是本地到 VPN 节点就不稳
- **中间某跳高但后面恢复正常**：不一定真有问题，有些路由器只是不愿意认真回 ICMP
- **后面一直都高**：更值得怀疑

---

## 4）用 pathping 看“哪一段有丢包”

`pathping` 结合了 `tracert` 和持续 ping，会对路径上每一跳做统计，微软文档明确说它可以帮助确定哪个路由器或链路在丢包。citeturn275453search2turn275453search6

### 命令
```bat
pathping 1.1.1.1
pathping 8.8.8.8
```

### 看什么
重点看最终统计表里的：

- `% Loss`
- 每一跳的延迟和丢包

### 判断
- **前几跳就丢包**：本地网络 / 路由器 / ISP / 到 VPN 入口有问题
- **中后段开始丢包**：更像 VPN 出口到目标站的路径差
- **只有单个中间节点显示高丢包，后续正常**：可能只是该节点限 ICMP，不一定是真丢

> 这个命令会跑一会儿，别急着关。

---

## 5）看 DNS 有没有被 VPN 搞乱

### 命令
```bat
nslookup www.google.com
nslookup www.cloudflare.com
```

### 看什么
看：

- 解析速度是否很慢
- 返回的 DNS 服务器是不是 VPN 下发的
- 是否出现超时

### 判断
- **网页卡，但 ping IP 正常、nslookup 很慢**：更像 DNS 问题
- **开 VPN 后 DNS 服务器变了，而且解析慢**：可能是 VPN 的 DNS 质量差

---

## 6）看路由表是不是异常，流量是不是走错了

### 命令
```bat
route print
```

### 看什么
看：

- 默认路由 `0.0.0.0`
- 有没有多条默认路由
- VPN 连接后默认路由是否指向 VPN 接口
- 是否有奇怪的静态路由

### 判断
- **全局代理 / 全隧道 VPN**：默认路由通常会走 VPN
- **分流 / 分应用 / 分站点策略**：可能只有部分流量走 VPN
- **多条默认路由优先级乱了**：会出现莫名其妙的慢和不稳定

---

## 7）看接口 MTU，排查“网页半开、视频卡、能连但吞吐怪”

`netsh interface ipv4 show subinterfaces` 能显示接口和 MTU 等信息。微软文档把它列为 `netsh interface` 的标准子命令之一。citeturn275453search3turn275453search7

### 命令
```bat
netsh interface ipv4 show subinterfaces
```

### 看什么
看 VPN 相关接口和主网络接口的：

- MTU 数值
- 接口名

### 判断
常见味道：

- **网页打开一半卡住**
- **小请求正常，大文件/图片/视频异常**
- **开 VPN 后特别容易这样**

这时要怀疑 MTU / MSS。

---

## 8）手动测一个大概可用的 MTU

Windows 的 `ping` 可以带包大小，还可以设置“**不允许分片**”。微软文档里就有 `-f` 和 `-l` 这类参数。citeturn275453search0

### 命令
先从较大的值试：
```bat
ping 1.1.1.1 -f -l 1472
```

如果提示需要分段，就往下减：

```bat
ping 1.1.1.1 -f -l 1464
ping 1.1.1.1 -f -l 1452
ping 1.1.1.1 -f -l 1440
ping 1.1.1.1 -f -l 1400
```

### 看什么
看是否出现类似：

```text
Packet needs to be fragmented but DF set.
```

### 判断
- 找到**最大可通过**的 `-l` 值后，**再加 28**，就是大致 MTU
- 例子：如果 `-l 1400` 能通、`1410` 不能，那 MTU 大约在 `1428` 左右

这一步非常实用。  
因为很多“VPN 网速怪”“网页加载不完整”“视频奇怪卡顿”，本质不是纯带宽，而是 MTU 不合适。

---

## 11）最有用的对照实验：换节点、换协议、换网络

再往下，是**协议层排查**。  
如果你用的是 OpenVPN，官方文档明确提到：**MTU 问题常表现为“能连上，但一到活跃使用时就卡住、挂住、速度奇怪”**；并且 `fragment` / `mssfix` 就是为了解决路径 MTU 发现异常这类问题准备的。citeturn255959search2turn255959search12

这类问题的典型症状是：

- 网页能打开一半卡住
- 小流量正常，大文件、视频、图片加载异常
- 某些网站特别容易卡，另一些又还行
- 换网络环境后表现变化很大

如果是这种味道，你优先怀疑 **MTU / MSS**。  
OpenVPN 场景下，去看客户端或服务端有没有合适的 `mssfix` / `fragment` / MTU 设置。官方文档就说了，MTU 异常经常会在“活跃使用期间”显形。citeturn255959search2turn255959search12

如果你用的是 **WireGuard**，虽然这次我没找到一页像 OpenVPN 手册那样直白的“排障指南”，但官方站点里能看到它非常依赖 UDP 传输，并且项目本身也提到 path-MTU / per-peer PMTU 这类路径 MTU 议题是重要方向。实际里，WireGuard 出现“能连但吞吐不稳”时，MTU 也仍然是常见嫌疑人。citeturn506743search0turn255959search3

然后是**吞吐到底是不是 VPN 本身瓶颈**。  
这时候别只看网页测速，最好用 `iperf3`。它是专门测网络最大可达带宽、丢包等参数的工具。官方文档也明确说它就是拿来做主动带宽测试和参数调优的。citeturn255959search1turn255959search8

你可以这样用它来想问题：

- **不开 VPN，iperf3 很高；开 VPN，明显掉一大截**  
  VPN 本身或其节点/协议/CPU 开销有影响。
- **不开 VPN 就不高**  
  别冤枉 VPN，底层就已经不行。
- **单线程差，多线程还行**  
  可能是链路质量、拥塞控制、节点策略、运营商路径等问题，不一定是“总带宽真不够”。

还有一个经常被忽略的点：**CPU 和实现开销**。  
尤其 OpenVPN，传统用户态实现本来就更吃 CPU。OpenVPN 最近也一直在推 DCO（Data Channel Offload），核心意思就是把性能关键的数据通道更多下沉到内核，以减少上下文切换、提高吞吐、降低延迟。这个方向本身就说明：有些“VPN 慢”不是线路坏，而是协议实现与设备性能一起拖后腿。citeturn506743search5turn506743search3

所以你还要顺手检查这几个现实问题：

- 换个节点，速度是否立刻恢复
- 换个协议，速度是否明显变化  
  例如 OpenVPN UDP / TCP、WireGuard、供应商自有协议
- 同一节点在手机和电脑表现是否一致
- 同一设备在 Wi-Fi 和手机热点下是否一致
- 开 VPN 时 CPU 是否飙高
- 只访问国外站慢，还是连国内常规站也变慢

这里有个非常粗暴但有效的判断法：

**A. 换节点就好了**  
→ 节点拥塞或路由问题。

**B. 换协议就好了**  
→ 协议实现、UDP/TCP 特性、MTU/MSS、或设备性能问题。

**C. 换网络环境就好了**  
→ 你本地 ISP、Wi-Fi、路由器、甚至晚高峰链路问题。

**D. 只有某个网站慢**  
→ 目标网站本身、目标地区路由、或该站对某类出口有限制。

你可以按这个最小脚本跑一遍：

1. 不开 VPN，测一次 Cloudflare speed test，记下 latency / loaded latency / jitter / packet loss。citeturn255959search0turn506743search2  
2. 开 VPN，换 2–3 个节点重复测试。  
3. 对“快节点”和“慢节点”各跑一次 MTR。citeturn255959search20turn506743search12  
4. 如果是 OpenVPN，再看 MTU / `mssfix` / `fragment`。citeturn255959search2turn255959search12  
5. 用 `iperf3` 或同类吞吐测试区分“网页体感慢”与“链路实测慢”。citeturn255959search1turn255959search8
