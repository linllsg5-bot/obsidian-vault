### 1. 你能直接使用真正的 Jev

可以。

也就是说：

\[
\text{你的程序}\rightarrow\text{Jev API}\rightarrow\text{typed decisions}
\]

这个意义上的“用上”，当然可以。citeturn353022search0

### 2. 你不能把 GPT “变成 Jev”

比如：

```python
response = qwen(prompt)
```

然后要求：

```text
只能返回概率，不准说话。
```

即使最后得到：

```json
{"yes": 0.83}
```

底层仍然是在：

\[
P(token_{t+1}\mid token_{\le t})
\]

一个 token 一个 token 往外生成。

所以你只是让 **LLM 模拟 Jev 的接口**。

你没有得到：

\[
\text{parallel sampling}
\]

也没有得到 Jev 原生的：

\[
\text{calibrated decision distribution}
\]

更没有得到它最大的速度/成本优势。

所以我不会跟你说：

> “照着 Jev 的思路写 Agent，你就已经用上 Jev 了。”

这句话太宽泛了。

准确说应该是：

> **你可以采用 Jev 的系统设计思想，但没有采用 Jev 的模型能力。**

这是两个东西。

---

### 3. 但你能自己做一个“Jev-like”实验

这个我反而觉得最有意思。

不是：

```text
prompt engineering
```

而是真的把模型训练任务改掉。

比如我们现在有：

\[
x
\rightarrow Transformer
\rightarrow h
\]

普通语言模型接：

\[
h\rightarrow W_{\text{vocab}}
\rightarrow 50000\text{ 个 token logits}
\]

然后：

\[
token\rightarrow token\rightarrow token
\]

你把它换掉：

\[
h
\rightarrow
\begin{cases}
\text{Boolean head}\\
\text{Choice head}\\
\text{Score head}
\end{cases}
\]

例如：

\[
h\rightarrow \sigma(Wh+b)
\]

直接得到：

\[
P(\text{YES}\mid x)=0.83
\]

这时候就已经不是：

> “让语言模型说 YES。”

而是：

> **模型直接计算 YES 的概率。**

区别非常大。

再进一步，可以让多个判断头同时输出：

\[
h
\rightarrow
\begin{bmatrix}
P(A)\\
P(B)\\
P(C)\\
Risk\\
Confidence
\end{bmatrix}
\]

一次 forward pass 全出来。

这已经碰到 Jev 所代表的那个方向了。

当然：

\[
\boxed{\text{这不等于复刻 Jev}}
\]

因为我们不知道 TypeSafe 真正的 architecture / RLCD / sampler 怎么实现。

但这是**你可以真正动手研究的部分**。

---

> **你不能靠现有 LLM 的 prompt 或普通 Agent 设计获得 Jev 的底层能力。**
>
> **但你可以直接用 Jev 的服务；也可以自己训练一个 Jev-like 的决策模型。**

**如果你的兴趣是“为什么 Jev 会这样工作”，不要急着学怎么调用 Jev。**

真正值得顺着挖下去的是：

\[
\boxed{
\text{为什么语言生成一定要是智能的默认接口？}
}
\]

以及：

\[
\boxed{
\text{如果把 next-token prediction 去掉，模型还剩下什么？}

\[
\text{普通 LLM}

\[

need_search = judge(

if need_search > 0.8:

\[
state
\rightarrow
\{J_1,J_2,J_3,J_4\}
\rightarrow

\rightarrow
action

## assistant

你说的应该是这几天突然火起来的 **Jev**——TypeSafe AI 在 **2026 年 9 月 15 日**发布的模型。它真正有意思的地方，不是“又有一个新模型”，而是它在尝试改变我们对 **AI 输出是什么** 的理解。citeturn124489search0turn873042search5

### 先抓住最核心的一刀

GPT 这类模型做的是：

\[
\text{状态/问题} \rightarrow \text{生成一串语言}
\]

比如：

> 这个用户是不是想退款？

LLM 可能回答：

> 根据用户的描述，我认为他很可能是在要求退款，因为……

然后程序还得从这段话里再解析出：

```text
YES
```

Jev 则直接变成：

\[
f(\text{state},\text{question})
\rightarrow
(\text{decision},p)
\]

例如：

```json
{
  "refund": {
    "answer": true,
    "probability": 0.97
  }
}
```

**没有作文。没有解释。直接判断。**

TypeSafe 自己给它的描述非常准确：

> unstructured state in, typed probabilistic decisions out

也就是：

**非结构化世界状态进去 → 有类型、带概率的判断出来。** citeturn124489search0

---

这其实是一个挺大的思想变化。

我们现在几乎默认：

> intelligence ≈ language generation

因为 ChatGPT 的成功太强烈了。

但 Jev 在问：

> **智能为什么一定要说话？**

如果一个 AI 的工作只是决定：

```text
这封邮件是不是诈骗？
这个请求应该交给哪个 Agent？
这个用户是不是在退款？
当前策略是否应该停止？
这个网页中的哪个按钮最值得点击？
这个异常是不是安全事件？
```

那么生成几十、几百个 token 的文字其实是一种绕路。

真正需要的只是：

\[
P(a_i\mid x)
\]

即：

> 在当前状态 \(x\) 下，每个行动 \(a_i\) 应该被选择的概率是多少。

这就开始不像聊天机器人了。

更像一种：

> **可学习的条件判断器。**

或者官方自己很喜欢的说法：

> **smart if statement**

“聪明的 if”。citeturn873042search5

---

### Jev 现在主要有三种输出

大致可以理解成：

```text
Noul
true / false + probability

Choice
A / B / C / D + probabilities

Score
连续/离散评分 + confidence
```

比如一个 Agent 面前有：

```text
当前状态：
用户问“帮我分析这个 GitHub 项目为什么运行失败”
```

我们可以问 Jev：

```text
需要搜索网页吗？
需要读 GitHub 吗？
需要执行代码吗？
问题危险吗？
复杂度是多少？
```

于是它可能一次返回：

```text
web_search       0.18
github           0.96
execute_code     0.71
unsafe           0.01
complexity       0.76
```

然后真正的程序写：

```python
if github > 0.8:
    inspect_repo()

if execute_code > 0.7:
    run_tests()

if unsafe > 0.5:
    human_review()
```

这里出现了一个非常重要的结构：

\[
\boxed{
\text{AI负责模糊判断}
+
\text{代码负责确定性结构}
}
\]

而不是：

\[
\text{把整个任务交给一个 LLM，然后祈祷它别跑偏}
\]

这就是 Jev 最值得注意的东西。

---

### 为什么它能快得离谱？

普通 Transformer LLM 生成：

```text
The
The user
The user appears
The user appears to
...
```

本质是：

\[
y_t \sim P(y_t|x,y_{<t})
\]

一个 token 一个 token 地生成。

所以有很强的**串行性**。

而 Jev 不需要生成句子。

如果你问：

```text
退款？       yes/no
诈骗？       yes/no
紧急？       1~5
类别？       A/B/C/D
```

这些输出可以高度并行地求。

TypeSafe 称其使用了新的 architecture、parallel sampler，以及 **RLCD（Reinforcement Learning for Calibrated Decisions）**训练方法。公司报告的典型端到端延迟约 **70–500 ms**；在他们自己的 System One 工作流评估中，某些场景相较传统 LLM 达到几十到近两百倍速度差距。这里要注意，这些数字目前主要来自 TypeSafe 自己的 benchmark，而不是成熟的独立第三方评测。citeturn124489search0turn814483view5

价格也很激进，目前官方标的是：

\[
\$42 / 10^9
\]

input tokens，也就是：

\[
\$0.042 / 10^6
\]

而 output 因为不是普通 token generation，官方目前标为免费。citeturn814483view1

---

### 但是有一个容易被宣传误导的点

TypeSafe 写了：

> Zero Hallucinations

这个说法要非常谨慎理解。

**Jev 当然可以判断错。**

例如：

```text
“这是不是诈骗？”

Jev：
no  0.91
```

实际上它可能就是诈骗。

这仍然是错误。

所谓“不会 hallucinate”更准确应该理解为：

> **它不会跑出你事先没有定义的输出空间。**

假设输出类型是：

```typescript
type Action =
  | "approve"
  | "reject"
  | "review"
```

Jev 不会突然返回：

```text
Maybe we should call Bob and investigate this further...
```

因为这个输出根本不存在。

所以：

\[
\text{syntactic / type correctness}
\]

可以做到很强的保证。

但：

\[
\text{semantic correctness}
\]

仍然是概率问题。

这两件事不能混为一谈。官方自己也强调判断附带 probability / confidence，让软件决定什么时候自动执行、什么时候交给人工。citeturn124489search1turn124489search0

---

而这里恰好出现了我觉得 Jev 最有价值的一层。

以前 Agent 大概是：

```text
世界
 ↓
LLM
 ↓
“我觉得接下来应该……”
 ↓
tool
 ↓
LLM
 ↓
tool
```

大量逻辑藏在 prompt 和语言里。

而 Jev 想把它变成：

```text
                ┌─ judgment A ─┐
world state ────┼─ judgment B ─┼── code ── action
                └─ judgment C ─┘
                       ↑
                  probabilities
```

于是整个 Agent 开始变成一个真正的**计算图**。

\[
S_t
\rightarrow
J_1(S_t),J_2(S_t),...,J_n(S_t)
\rightarrow
F
\rightarrow
A_t
\]

其中：

- \(S_t\)：世界状态
- \(J_i\)：AI 判断函数
- \(F\)：你自己写的确定性组合规则
- \(A_t\)：行动

这和“一个巨大的 prompt”是完全不同的工程哲学。

---

而且这和你前面一直在琢磨的那个问题有一个挺漂亮的连接：

> 一个事件能否拆成必要条件，每一环满足之后，达到阈值，于是整体出现？

Jev 的工程思想几乎就是把这种结构直接拿去做软件：

\[
p_1,p_2,p_3,\dots,p_n
\]

不是要求 AI 一口气回答：

> “最终应该怎么办？”

而是拆：

```text
条件 A 成立吗？
条件 B 成立吗？
条件 C 成立吗？
风险是多少？
证据强度多少？
```

再由：

\[
F(p_1,p_2,\dots,p_n)
\]

产生最终行为。

所以它真正押注的其实不是“一个更聪明的模型”。

而是：

> **复杂智能可能更适合由大量廉价、局部、带不确定性的判断，与确定性的程序结构组合出来。**

这个想法比 Jev 这个产品本身有意思得多。

---

比如你刚刚想做的那个**学习优先级决策器**，其实就非常适合这种结构。

假设候选任务：

```text
线性代数
Transformer
Python
Linux
Agent
法语
```

不是让 LLM 写一篇：

> “综合考虑你的长期目标，我建议……”

而是分别求：

\[
P(\text{当前是依赖项})
\]

\[
P(\text{未来价值高})
\]

\[
P(\text{以当前精力能完成})
\]

\[
P(\text{会解锁后续任务})
\]

再结合你自己设定的权重：

\[
Score_i
=
w_1D_i
+w_2V_i
+w_3E_i
+w_4I_i
-\lambda C_i
\]

这时候 AI 不再决定你的人生。

它只是成为很多个：

> **模糊传感器。**

而程序负责把这些传感器组合起来。

我很喜欢这个视角。

不过现在别太早把 Jev 神化。

它才在 **9 月 15 日**发布，目前还是 early access；公开技术细节远不足以让我们真正知道它的 architecture 到底和 Transformer 有多大区别，模型权重也没有公开。目前性能优势的主要证据仍由 TypeSafe 提供，他们自己也承认 workflow benchmark 的设计者来自公司内部，因此可能存在偏差。citeturn124489search0

所以现在比较合理的判断不是：

> “Jev 要淘汰 LLM。”

而是：

\[
\boxed{\text{LLM : language}}
\]

\[
\boxed{\text{Jev-like model : judgment}}
\]

\[
\boxed{\text{code : composition}}
\]

三者可能最后一起存在。

甚至以后 Agent 的内部可能根本不是“一个模型”。

而是：

```text
         世界状态
            │
     ┌──────┴──────┐
     │             │
 fast judgments    deep reasoning
  Jev-like           LLM
     │             │
     └──────┬──────┘
            │
       deterministic
          code
            │
          action
```

快判断交给 System-1 模型。

真正未知、需要构造新东西的问题交给 reasoning model。

结构、约束、状态转移交给代码。

这反而开始有一点像真正的**认知架构**了，而不仅仅是 chatbot。

顺带一提，名字 **Jev** 来自经济学家 **William Stanley Jevons（杰文斯）**。TypeSafe 借的是“杰文斯悖论”的隐喻：一种资源越高效、越便宜，不一定使用得更少，反而可能因为产生大量新用途而**消耗得更多**。他们押的就是——如果一次“智能判断”的成本下降几个数量级，我们不会只是少花一点 AI 钱，而可能在软件的每一个 if 附近都塞进 intelligence。citeturn124489search0

**这才是 Jev 最野的那个命题：不是让 AI 更会说，而是让“判断”变成和数据库查询、函数调用一样廉价的基础计算原语。** memcite

## assistant

你大概是在说这两天刚冒出来的 **Jev AI**。它有点特别：它不是另一个“更会聊天的 GPT”，而是在试图把 AI 从“生成语言”里剥出来，直接做**判断**。这个方向其实很贴近你之前一直在追问的“问题能不能拆成条件、阈值、判断链”。
