最值得关注的不是它又创造了一个 Agent，而是它试图解决一个更根本的问题：

**能不能不重新训练模型权重，只通过反复执行任务、分析失败、修改 Skill、验证效果，让现有 Agent 越来越擅长某一类工作？**

这正好触及你之前一直在追问的事情：一个 AI 怎样根据行动的结果改变自己的工作方式，而不是每次遇到问题都只在原来的提示词里继续打补丁。

## 1. 它到底做了什么？

这里有个重要区别：**它不是让 AI 反思得更深，而是让反思结果进入一个能够被检验的修改循环。**

普通 Agent 可能是：

> 任务失败 → 总结教训 → 下次尽量注意。

SkillOpt-Lite 则把它变成：

> 任务失败 → 找到共性原因 → 修改可执行的知识载体 → 用独立任务检验 → 决定是否保留。

第二种方式的优势是，改进有明确的对象、评价标准和版本记录，不必完全依赖模型自己宣称“我已经进步了”。<Cite refs={["turn771783view0","turn771783view3"]}/>

## 2. 为什么叫 Lite？它删掉了什么？

原版 <Entity value="SkillOpt" category="other" disambig="用于优化 Agent 外部技能文本的研究框架"/> 与 SkillOpt-Lite 的区别，不是后者简单地缩短了代码，而是它重新审视了优化过程中哪些步骤真正有必要。

| 设计 | 原版 SkillOpt | SkillOpt-Lite |
|---|---|---|
| 失败分析 | 多阶段、分批次反思与合并 | 直接从执行轨迹中寻找共同规律 |
| 更新策略 | 包含慢更新、编辑预算等机制 | 减少更新阻尼，让明确的修正更快生效 |
| 历史管理 | 保留被拒绝的修改等机制 | 简化为验证门控与回滚 |
| 核心约束 | 控制修改过程 | 用独立验证控制最终是否接受 |

这些是论文对简化方向的描述；具体实现仍应以源码为准。<Cite refs={["turn771783view0","turn698683search5"]}/>

它背后的数学视角也值得理解。

设 \(s\) 是一份 Skill，\(M\) 是固定的模型，\(H\) 是 Agent 的执行框架，\(z\) 是任务，\(R\) 是任务奖励，那么可以把优化目标写成：

\[
\max_s \mathbb{E}_{z}[R(H(M,z,s))]
\]

模型不会直接告诉我们“把这句话改成什么，准确率就会提高多少”。自然语言技能并不是可以直接计算梯度的连续参数。

所以，作者把它看作**零阶优化（Zeroth-Order Optimization）**：提出修改、运行任务、观察结果，再决定是否接受修改。与普通黑箱优化相比，这里还有执行日志、错误信息等可解释的诊断材料。<Cite refs={["turn771783view0","turn698683search5"]}/>

## 4. 更进一步：HarnessOpt 比 SkillOpt-Lite 更值得你关注

论文还提出了 HarnessOpt。它把优化对象从 Skill 文本扩展到 Agent 的执行框架，也就是实际负责工具调用、控制流程和任务执行的代码。<Cite refs={["turn771783view0","turn771783view3"]}/>

<box gap={2}>
  <row align=start gap={3}>
    <box background="surface-secondary" radius="lg" padding={2} align="center" justify="center" size="48px">
      <icon name="file-text" size="xl"/>
    </box>
    <box flex="1" gap={1}>
      **SkillOpt-Lite：改变 Agent 的知识与策略**

      例如，Agent 总是直接生成整份表格处理脚本，导致错误难以定位。可以修改 Skill，让它先检查表格结构，再分步骤执行并验证。
    </box>
  </row>
  <row align=start gap={3}>
    <box background="surface-secondary" radius="lg" padding={2} align="center" justify="center" size="48px">
      <icon name="workflow" size="xl"/>
    </box>
    <box flex="1" gap={1}>
      **HarnessOpt：改变 Agent 能做什么、如何做**

      例如，Agent 无法预览足够多的数据，或者工具失败后没有重试和备用方案。这时就需要修改 Python 执行框架，而不只是增加一条提示词。
    </box>
  </row>
</box>

这意味着，Agent 的改进可以有两个层次：

- **行为层**：改变它理解任务、选择方法和使用工具的方式。
- **机制层**：改变它能够获得什么信息、采取什么行动、如何处理失败。

这和你一直想研究的“当 AI 原有的理解方式让它看不到某种可能性时，怎样让它真正采用另一种理解”非常接近。前者可以先修改技能规则；后者则允许你进一步改变造成行为限制的系统结构。

## 6. 我对这篇论文的判断

我认为它真正有价值的部分，不是“一行指令自动优化 Skill”这个宣传点，而是把一个很容易停留在口头上的概念——**自我改进**——变成可观测、可检验的工程过程。

不过，它也有清晰的边界：

- 它优化的是既定任务分布下的表现，不会自动发现所有值得追求的新目标。
- 它依赖可以执行、可以评价的任务。评价标准本身有缺陷时，系统可能只是更擅长迎合指标。
- Skill 变好不意味着整个 Agent 的认知结构都发生了改变；更深层的改进还可能需要调整工具、状态、控制流程和环境交互机制。
- 独立验证能降低对训练任务过拟合的风险，但不能保证面对完全陌生的环境时仍然有效。

这些边界并不削弱它的价值，反而让下一步研究更清楚了。

**对你而言，我会把 SkillOpt-Lite 看作一个可以动手验证的起点，而不是最终的认知架构。** 先让一个现有 Agent 在明确任务上形成“失败—诊断—修改—验证—保留”的闭环，再观察它何时需要修改的不再是某条技能，而是它对问题的表示方式、可用行动集合乃至任务本身的定义。

这就从优化一份 `SKILL.md`，走向了你一直想研究的那个问题：一个系统如何改变自己理解世界和进入世界的方式。
