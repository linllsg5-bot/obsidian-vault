## 第一层：你看到的“Codex 软件”

你现在看到的 Codex，其实有好几个入口，它们不是几套完全不同的 AI，而是同一个 Codex 系统的不同界面。

**ChatGPT 桌面端里的 Codex**，现在是功能最完整的图形界面之一。你可以打开整个项目、让多个任务并行、看 diff、操作 Git、建立 worktree、跑终端、使用 Skills、插件以及长时间任务。早期 2026 年 2 月发布的独立 Codex App 就主打这些东西；现在官方文档说明，这些能力已经出现在 ChatGPT Desktop 的 Codex 工作流里。citeturn212629search3turn614917search14

**Codex CLI** 就是：

```bash
codex
```

它不是一个“聊天版 Copilot”。

它可以自己：

```text
读代码
↓
搜索代码
↓
修改文件
↓
运行命令
↓
看报错
↓
继续修改
↓
运行测试
↓
检查 git diff
↓
再修改
```

CLI 还支持 `/permissions`、`/review`、subagents、Web search、MCP、cloud task 等。citeturn212629search2

**IDE Extension** 则是把同一个 agent 放进 VS Code、Cursor、Windsurf 等编辑器。它天然知道你当前打开了哪个文件、选中了什么代码，所以不用每次复制代码进去。它还可以把大任务转交给 Codex Cloud。citeturn212629search0

再往外还有 **Codex Cloud**：你的电脑甚至可以不执行任务，OpenAI 给每个任务创建隔离环境，然后 agent 在那里 checkout repo、安装依赖、改代码、测试，最后给你 diff 或 PR。citeturn212629search6

所以：

```text
Codex ≠ Codex Desktop App

Codex App
Codex CLI
Codex IDE
Codex Cloud

只是 Codex 的几个入口。
```

# 第二层：Codex 真正核心的东西——Agent Runtime

这是最重要的一层。

普通 ChatGPT 基本循环更接近：

```text
你说话
 ↓
模型思考
 ↓
模型回答
```

Codex 是：

```text
你提出目标
 ↓
模型观察环境
 ↓
决定下一步
 ↓
调用工具
 ↓
环境发生变化
 ↓
读取结果
 ↓
重新判断
 ↓
再次调用工具
 ↓
……
 ↓
验证结果
 ↓
完成
```

也就是一个反馈循环：

\[
Observation
\rightarrow Reasoning
\rightarrow Action
\rightarrow Observation
\rightarrow \cdots
\]

这也是为什么你之前经常看到：

> Searching files...

> Running command...

> Reading...

> Applying patch...

> Running tests...

> Inspecting diff...

它不是模型一次性“想出答案”。

它是在**操作一个真实状态不断变化的环境**。

这其实已经非常接近你一直在研究的 Agent 概念。

# 第三层：Model 和 Codex 是两回事

这点特别容易混。

而 `/model` 可以改变模型和 reasoning effort。citeturn212629search2

所以：

```text

│
├─ Agent framework
├─ execution runtime
├─ context manager
├─ tools
├─ sandbox
├─ Git integration
├─ UI
│
```

模型可以更新。

Codex 这个系统却还在那里。

因此严格说：

> Codex 不是模型。

而是：

> **让模型变成软件工程 Agent 的运行系统。**

这和早期所谓的“Codex model”已经是完全不同的产品概念了。

# 第六层：执行环境

这是 Codex 和普通聊天机器人差异最大的地方之一。

目前桌面 Codex 有三种核心执行方式：

```text
Local
Worktree
Cloud
```

官方就是这么划分的。citeturn175379search2turn175379search10

### Local

假如你的目录是：

```text
D:\project\my-agent
```

Codex 就直接操作：

```text
D:\project\my-agent
```

所以它修改：

```text
main.py
```

你的真正 `main.py` 就改变了。

优点是直接。

缺点也很明显：

> agent 和你会抢同一份文件。

# 第七层：Worktree

这个设计非常漂亮。

假设你的 repo：

```text
my-project
│
└── main branch
```

现在你同时叫 Codex：

```text
Agent A：重构数据库

Agent B：重写前端

Agent C：修登录 bug
```

如果三个人全改一个目录：

```text
💥
```

所以 Git 有：

```text
git worktree
```

Codex 会创建：

```text
repo/
repo-worktree-agent-A/
repo-worktree-agent-B/
repo-worktree-agent-C/
```

于是：

```text
你
│
├─ main
│
├─ Agent A → branch A
│
├─ Agent B → branch B
│
└─ Agent C → branch C
```

完全隔离。

最后你再：

```text
review diff
merge
```

ChatGPT Desktop Codex 对 worktree 已经提供内置 setup scripts 和 Git 操作。citeturn175379search1

这其实就是 Codex 能做到真正：

> **多 Agent 并行软件工程**

的重要基础。

否则所谓“多个 agent”很容易只是几个聊天窗口。

# 第八层：Cloud

Cloud 又完全不同。

本地模式：

```text
Codex
 ↓
你的 Windows
 ↓
PowerShell
 ↓
你的 Python
 ↓
你的 Node
```

Cloud：

```text
Codex
 ↓
OpenAI isolated environment
 ↓
checkout Git repo
 ↓
setup
 ↓
agent
```

每个任务拥有隔离环境。

而且可以：

```text
Task A ──────────────→

Task B ──────→

Task C ───────────────────→

Task D ───→
```

并行。

你不用让电脑一直占着 Terminal。

这就是为什么大型代码库、PR、issue、自动 review 很适合 Cloud。Codex Cloud 目前还能从 GitHub、GitLab、Linear 和 Slack 启动任务。citeturn212629search6turn212629search9

# 第九层：Shell

Codex 最强的能力其实未必是“写代码”。

而是：

> 它有 shell。

例如它可以：

```bash
rg "UserService"
```

发现代码在哪。

然后：

```bash
cat src/user.ts
```

理解代码。

然后修改。

再：

```bash
npm test
```

发现：

```text
3 tests failed
```

于是：

```bash
npm test -- user
```

继续定位。

再改。

所以它获得了一条完整的：

```text
认知 → 行动 → 验证
```

闭环。

LLM 原本只能：

```text
预测文本
```

有 Shell 后变成：

```text
预测行动
↓
现实环境执行
↓
获得反馈
↓
重新预测
```

这就是 Agent 真正开始有意思的地方。

# 第十层：Sandbox

但问题马上出现。

如果 AI 可以运行：

```bash
rm -rf /
```

怎么办？

或者：

```powershell
Remove-Item C:\ -Recurse
```

所以 Codex 有非常重要的一层：

```text
Sandbox
```

默认本地 Codex 通常限制：

```text
可读文件
可写目录
网络
命令
```

例如常见 Auto 模式相当于：

```text
workspace-write
+
on-request
```

意思大致是：

> 工作目录里，你可以自己干。

但：

> 跑出去改其他地方或者访问网络，可能需要审批。

官方把 **sandbox mode** 和 **approval policy** 明确分为两个安全层。citeturn614917search12

所以你之前看到：

```text
approval
sandbox
permission
```

不是同一件事。

---

# Approval ≠ Sandbox

这个区别非常关键。

Sandbox 是：

> **技术上允许不允许。**

Approval 是：

> **要不要问你。**

比如：

```text
sandbox:
只允许 D:\project
```

Codex 想：

```text
写 C:\Windows
```

sandbox：

```text
❌
```

于是可能弹：

> Allow this command?

你同意后，它才可能获得临时升级权限。

这也解释了你最近碰见那种：

> Python WindowsApps ACL 拒绝执行

为什么 Codex 自己解决不了。

因为那里甚至可能不是 Codex 的 approval 层。

而是：

```text
Codex
 ↓
Sandbox
 ↓
Windows ACL
 ↓
Python executable
```

Windows 本身：

```text
ACCESS DENIED
```

这时候即使 Codex “想执行”，Windows 也不让。

# 第十一层：Context

Codex 并不会把你整个硬盘全塞进模型。

它大体是逐步探索：

```text
用户 prompt
+
AGENTS.md
+
当前文件
+
相关文件
+
搜索结果
+
Git diff
+
command output
+
conversation
```

然后只把需要的信息送给模型。

所以：

```text
repo = 1,000,000 行
```

不意味着：

```text
context = 1,000,000 行
```

Agent 会：

```text
搜索
↓
定位
↓
读取
↓
缩小范围
```

这也是为什么 Codex 读 repo 时经常不断 `rg`、`find`、`cat`。

它其实在构建自己的局部世界模型。

# 第十二层：AGENTS.md

这个对你以后特别重要。

类似：

```text
AGENTS.md
```

可以理解成：

> **这个 repository 给 Agent 的宪法。**

比如 OpenAI 自己 Codex repo 的 AGENTS.md 就规定了很多开发规则，包括 Rust 工程约定、测试方式、格式化要求等。citeturn614917search8

你可以写：

```markdown
# Architecture

Backend must use FastAPI.

# Testing

Run pytest after every change.

# Rules

Never edit migrations manually.

# Style

Prefer small modules.
```

这样每个新 Codex task 都不用重复告诉它。

于是：

```text
Prompt
=
这次我要什么

AGENTS.md
=
这个世界长期遵守什么
```

这是两个不同层次。

# 第十三层：Skills

Skills 又比 AGENTS 高一层。

AGENTS：

> 原则。

Skill：

> 一套可执行的工作方法。

比如：

```text
$frontend-design

$security-review

$deploy

$triage-ci
```

一个 Skill 可以规定：

```text
读取哪些东西
↓
使用哪些工具
↓
执行什么步骤
↓
怎样验证
↓
最后怎么报告
```

Codex 会从 repo、用户等不同作用域寻找 Skills，repository 也可以自己携带 Skills。citeturn175379search7

所以未来很可能出现一种开发模式：

```text
人不再保存 prompt

而是保存 workflow / skill
```

Prompt：

```text
帮我部署。
```

真正背后运行的是：

```text
deployment skill
├─ test
├─ build
├─ docker
├─ health check
├─ rollback
└─ report
```

这已经开始接近“小程序”。

```text

↓

↓

↓
```

# 那 Codex 和 ChatGPT Work 到底什么区别？

现在两者确实越来越靠近，但思路仍然不同。

我会这样理解：

```text
                 ChatGPT Work
                      │
           ┌──────────┼──────────┐
           │          │          │
         Web        Docs       Apps
        research    files       data
           │
           └──────────┬──────────┘
                      │
                 general work


                    Codex
                      │
           ┌──────────┼──────────┐
           │          │          │
          Code       Shell       Git
           │          │          │
           └──────────┼──────────┘
                      │
               engineering work
```

Work 的世界中心是：

> **任务。**

Codex 的世界中心仍然更接近：

> **repository + execution environment。**

所以你前两天问我：

> Codex 会不会比 Work 更好用？

# 1. 软件到底是什么

从物理上讲，一个软件最初不过是一堆文本文件：

```text
main.rs
lib.rs
Cargo.toml
package.json
...
```

比如：

```rust
fn main() {
    println!("hello");
}
```

这些只是硬盘上的字节。

CPU 不认识 Rust。

所以要经过：

```text
人写源码
  ↓
Rust / TypeScript / ...
  ↓
编译器、构建工具
  ↓
机器码 + 静态资源
  ↓
.exe / binary / package
  ↓
安装到电脑
  ↓
操作系统加载
  ↓
进程
  ↓
CPU执行机器指令
```

**软件真正“活起来”的时刻，是操作系统把可执行文件加载进内存，创建进程。**

源代码是描述。

`.exe` 是被翻译后的机器指令。

进程才是正在发生的程序。
