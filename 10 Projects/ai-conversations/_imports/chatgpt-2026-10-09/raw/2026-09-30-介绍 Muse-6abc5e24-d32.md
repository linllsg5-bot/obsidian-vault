## assistant

对了一半。**你确实可以让 Pi 在外层，再把你 ChatGPT 账号里的 Codex 接成 Pi 的一个 worker；但不一定需要所谓“中转站模型”。**

```text
你
│
▼
Pi
│
├── 主模型 / orchestration model
│     └─ 负责理解你、拆任务、决定什么时候调用谁

├── Structural Core
```

### 这里其实有两个模型角色

Pi 自己需要一个模型才能运行 agent loop。Pi 官方支持通过 subscription、API key 或本地模型获得模型能力。citeturn652334search10

比如：

```text
Pi
↓
便宜/general model
```

它负责：

> “用户到底要什么？”  
> “现在是什么状态？”  
> “应该自己处理还是交给 Codex？”  
> “给 Codex 什么上下文？”  
> “Codex 做完以后留下什么结构？”

然后只有碰到真正的 coding 工作：

```text
Pi
↓
codex_worker({
    task,
    relevant_context,
    acceptance_criteria
})
↓
Codex
```

这样你的 **ChatGPT Codex额度主要花在真正需要 Codex 的地方**。

---

而你自己的 ChatGPT 账号这一边，其实已经有很干净的官方接法。

Codex Python SDK 现在可以直接：

```text
Codex SDK
↓
ChatGPT browser login
↓
你的 ChatGPT account
```

而且它会自动复用已有的 Codex 登录状态，不要求你再搞一个 OpenAI API Key。官方 SDK 已经提供 `login_chatgpt()` 和 device-code 登录。citeturn652334search2turn652334search9

所以完全可以是：

```text
Pi process
│
└── extension: codex
       │
       └── openai-codex SDK
                │
                └── ~/.codex authentication
                         │
                         └── 你的 ChatGPT 账号
```

这比模拟终端输入：

```text
pi
→ exec("codex ...")
→ 解析 stdout
```

要好很多。

因为 SDK 能直接得到 thread、turn、事件、token usage 等结构化信息；TypeScript SDK 还明确支持 streaming events，包括工具调用和文件变化。citeturn652334search3

## 所以“中转站”到底要不要？

如果你说的中转站是类似：

```text
某第三方 API relay
↓
Claude / Gemini / GPT
```

**不是必须。**

它只是 Pi 的：

```text
主模型来源
```

而不是架构的必要组成。

你甚至可以以后这样：

```text
              Pi
               │
       ┌───────┼────────┐
       ▼       ▼        ▼
    Gemini   Local    Codex
     cheap   model    worker
       │       │        │
   普通判断   小任务    重代码任务
```

或者非常简单：

```text
Pi
├── 一个便宜模型
└── Codex
```

第一版我反而推荐这样。

不要一上来：

```text
中转站
├ Gemini
├ Claude
├ GPT
├ DeepSeek
├ Codex
├ local model
└ ...
```

你会先死在 routing 和配置上。

---

### 而且有一个安全边界我会坚持

如果你真使用第三方“中转站”，**不要把 ChatGPT/Codex 登录 token 交给它。**

两套认证完全分开：

```text
Pi 主模型
↓
第三方 API / 官方 API / local
```

和：

```text
Codex SDK
↓
OpenAI 官方 ChatGPT 登录
↓
你的 ChatGPT account
```

不要：

```text
ChatGPT credential
       ↓
第三方 relay
       ↓
Codex
```

没有必要，也增加凭据泄露风险。

Codex SDK本身就支持官方 ChatGPT登录，所以根本不需要绕这一层。citeturn652334search6

还有一个很重要的点：**Pi 和 Codex并不是嵌套模型调用关系。**

不是：

```text
模型 A
让
模型 B
回答
```

更准确是：

```text
Agent runtime
   ↓
决定调用工具
   ↓
Codex 被当作一种高级工具/worker
```

就像：

```text
Pi tools:
├ read_file
├ browser
├ search
├ structural_query
├ structural_update
└ codex
```

只不过：

```text
codex
```

不是普通 tool。

它内部本身又是一个完整 agent：

```text
Pi
  │
  └─ codex()
       │
       └─ Codex agent loop
            ├ inspect
            ├ reason
            ├ shell
            ├ edit
            ├ test
            └ repair
```

我觉得**这个结构才是你现在最值得做的版本**。

而且 Pi extension 本来就允许注册自定义工具、处理 session state、修改 context 等，所以把 `codex_worker` 做成一个 Pi extension 是很自然的接入点。需要注意的是 extension 与 Pi 进程拥有相同的系统权限，因此之后最好再给 Codex workspace / Pi tools 做权限边界。citeturn652334search4

所以最简洁地说：

\[
\boxed{
\text{Pi + 一个主模型 + 你的 Core + ChatGPT-authenticated Codex worker}
}
\]

**对。**

但那个“主模型”不必是什么特殊的中转站模型；它只是 Pi 的日常大脑。**真正应该保持独立的是 Codex：直接通过官方 SDK 登录你的 ChatGPT 账号，把它作为下面那只非常强的“手”。** memcite

## assistant

如果你说的是 **Meta 刚在 2026 年 9 月推出的 Muse**，那它其实很值得看。它和“更聪明的聊天机器人”不是一条完全相同的路线。

Meta 对它的定义是 **personal AI agent（个人 AI 智能体）**。9 月 8 日正式发布，核心目标不是“你问一句，它答一句”，而是：

> 你把一个目标交给它，它拥有一个持续存在的工作环境，然后自己把事情往前推进。

Meta 官方明确说，Muse 可以自己打开浏览器、填写网页表单、跨应用工作，任务时间很长时，即使你关闭 Muse，它仍然可以继续执行；遇到需要你决定的事情，例如发邮件、购买商品，则回来请求批准。citeturn419580search0turn419580view0

我觉得理解 Muse，最好不要把它想成：

**ChatGPT + 更强模型**

而应该拆成：

\[
\boxed{
Muse
=
模型
+
长期状态
+
计算机
+
工具
+
权限
+
持续执行
}
\]

大概是这样一个循环：

```text
你
↓
“我想完成 X”
↓
Muse 理解目标
↓
建立计划
↓
读取你的上下文
↓
操作浏览器 / App / API
↓
观察结果
↓
修改计划
↓
继续操作
↓
必要时询问你
↓
长期继续
```

这已经很接近我们之前一直在讨论的那个问题：

**怎样让一次认知，不只生成一句回答，而是真的进入之后的行动结构。**

---

### 最关键的东西其实不是 Muse Spark

Muse 底层使用的是 Meta 的 **Muse Spark** 模型。Meta 把它称为面向现实世界 agent 工作的模型。citeturn419580view0

但我反而觉得，Muse 最值得注意的是另外一个东西：

**Muse Secure VM。**

每个 Muse 都有一个专门的虚拟计算机环境：

```text
Muse Agent
│
├── Muse Spark
│
├── Memory / Context
│
├── Secure VM
│    ├── Browser
│    ├── Files
│    ├── Sessions
│    └── Credentials
│
├── Connectors
│    ├── GitHub
│    ├── Notion
│    ├── Shopify
│    ├── Stripe
│    ├── Box
│    └── ...
│
└── Approval / Permission system
```

也就是说，**Agent 不再只是活在一次 inference 里面。**

它有一个“世界”。

这个世界里有：

- 文件；
- 浏览器状态；
- 登录状态；
- 工具；
- 任务进度；
- 你的部分长期信息；
- 上一次行动留下的结果。

Meta 官方的说法是，这个 Secure VM 同时承载 agent 和用户数据，并让 Muse 拥有自己的浏览器。citeturn419580view0

这个变化非常大。

```text
↓
```

```text
支付
↓
继续追踪订单
```

所以它实际上是在把：

\[

\]

变成：

\[
\text{persistent process}
\]

**对话 → 持续存在的过程。**

### 这和你折腾的 OpenClaw / Agent 路线其实非常接近

抽掉 Meta 的产品包装以后，你之前做的东西和 Muse 可以画成很相似的结构：

```text
                 ┌── Memory
                 │
User → Agent → Planner
                 │
                 ├── Browser
                 ├── Computer
                 ├── Files
                 ├── APIs
                 ├── Obsidian
                 └── Other agents
                        ↓
                    Environment
                        ↓
                    Observation
                        └────→ Agent
```

Muse 做的一个关键工程选择就是：

**不给 AI 只提供“工具”，而是给它一个可以持续存在的环境。**

这两个差别很大。

工具调用是：

```text
AI → call tool → result
```

持续环境则是：

```text
AI(t₀)
↓
改变环境
↓
Environment(t₁)
↓
AI(t₁)
↓
再次观察
↓
改变环境
↓
Environment(t₂)
...
```

于是 agent 开始有了某种非常初级的：

\[
\text{历史}
\]

因为：

\[
S_{t+1}=F(S_t,A_t,E_t)
\]

下一时刻不是重新开始，而是继承上一时刻造成的世界状态。

这其实才是 Muse 比“模型参数又涨了一点”更有意思的地方。

而我们前几天一直往下挖的，其实已经是在问第五层了。memcite

## assistant

如果是我，我不会先做“完整 agent 平台”。

我会先做一个非常小、但方向完全对的东西：

**让一个 agent 在完成任务之后，真的能够改变下一次它怎么做。**

第一版我甚至只做这条闭环：

```text
你给任务
↓
Pi 运行 agent
↓
必要时调用 Codex
↓
完成任务
↓
记录完整 trajectory
↓
分析：这次哪里有效，哪里失败
↓
产生一个 Structural Change Proposal
↓
下一次运行时应用这个变化
↓
比较前后效果
```

也就是先验证最核心的一件事：

\[
Experience_t
\rightarrow
\Delta Structure
\rightarrow
Behavior_{t+1}
\]

而不是一下子做 memory、multi-agent、browser、Obsidian、知识图谱、自动研究、长期自主运行全部东西。

因为那些都可以以后加。

最难验证的是：

> **经验是否真的能够形成一种以后可复用、并改变行为的结构。**

---

我会把第一版工程拆成五个非常简单的东西。

```text
/core
    structure.ts

/events
    event-store.ts

/learning
    reflect.ts
    propose-change.ts
    evaluate-change.ts

/runtime
    pi.ts

/workers
    codex.ts
```

`Pi` 只负责 agent loop。

`Codex` 只负责复杂 coding task。

而真正重要的是：

```text
structure.ts
```

第一版 `Structure` 甚至不要搞得哲学味很重。

就用非常朴素的数据：

```json
{
  "observations": [],
  "hypotheses": [],
  "relations": [],
  "procedures": [],
  "attention_rules": [],
  "task_rules": []
}
```

比如：

```text
hypothesis:
“websocket reconnect 的 bug
经常来自 session identity 被重新创建”
```

或者：

```text
procedure:
遇到长任务中断时：
1. 先检查 artifacts 是否存在
2. 再检查 session
3. 不要默认从头运行
```

甚至：

```text
attention_rule:
如果 error 包含
"stream disconnected"
优先检查 transport/session，
而不是代码本身。
```

这就已经不是单纯的“记住一段话”。

因为下一次 context selection 和行动顺序可以真正受它影响。

---

然后我会让每一次任务产生一个 append-only event log。

例如：

```text
TaskStarted
GoalParsed
ContextSelected
HypothesisCreated
ToolCalled
ObservationReceived
HypothesisRejected
CodexStarted
FileChanged
TestFailed
RevisionMade
TestPassed
TaskCompleted
```

不要只保存最后一句：

> 修好了。

真正值钱的是过程。

于是你以后才能问：

```text
什么类型的判断经常失败？

哪些 observation 最有信息量？

什么情况下 Codex 第一次调用就成功？

哪些 context 实际上根本没有被使用？

什么 procedure 在不同任务中重复出现？
```

这就是以后“学习”的原材料。

---

然后任务结束时，我会调用一个 `Reflector`。

但它不能只输出：

Session_i = \text{一次对 Project 的操作}
\]

于是 Codex 死掉、重启、换模型，都不会把整个项目一起带走。

这反而和你前面一直在想的“怎样让一次探索留下结构并影响以后”开始碰到一起了。memcite

---

不过我会提醒你一个实际问题。

Pi 目前官方 README 明确写着：**它本身没有内建的 filesystem/process/network/credential permission system**，默认继承启动它的用户权限；如果需要更严格的边界，官方建议容器化或 sandbox。citeturn592749search1

Codex 自己反而有 sandbox / approval 体系。它的 agent harness 会根据配置决定 shell、文件修改等操作是否需要升级授权。citeturn639307search6

所以不要变成：

```text
Pi
拥有电脑所有权限
↓
Codex
也拥有所有权限
↓
自动跑几个小时
```

那是给自己埋雷。

我反而会设计成：

```text
Pi
│
├── planning
├── memory
├── routing
│
└── Codex
     │
     └── sandboxed workspace
```

Pi负责**决定谁做什么**；

Codex负责**代码世界里的具体执行**。

---

所以回到你的原问题：

**“Codex 装进 Pi agent 会不会更好？”**

如果只是：

```text
Pi → Codex CLI
```

差别不大，甚至更绕。

如果是：

```text
Pi = 长期主体 / orchestrator

Codex = coding capability
```

那就有明显区别，而且我觉得**比你继续往 Codex 本身塞越来越多记忆、规则、agent 功能，更符合你想做的方向。**

尤其是你可以最后变成：

```text
                    ┌─ Codex
                    │   coding
                    │
                    ├─ Browser Agent
                    │   web
                    │
                    ├─ Research Agent
                    │   research
User → Pi / Core ───┤
                    ├─ Memory
                    │
                    ├─ Obsidian
                    │
                    └─ Environment
```

这里 **Codex 不再是系统本身。**

它只是：

> 系统学会使用的一只“手”。

我觉得这才是这件事真正有价值的地方。

我检索了一圈以后，反而更确定了一件事：

**如果你的目标只是“做一个厉害的 Agent”，不一定选 Pi。

只是我不会做成“Pi + Codex”这么简单。

## 为什么我仍然倾向 Pi

Pi 官方现在仍然把自己定义成 **minimal agent harness**：

> “Adapt Pi to your workflows, not the other way around.”

它故意没有强塞进去固定的 sub-agent、plan mode 等架构，而是给 extension、skills、providers、session、context、compaction 这些基础构件。citeturn601875search13turn778918search1

Pi extension 又能直接加入工具、监听 session events、管理 session state、影响 context，以及改变 compaction 行为。citeturn601875search9

这个设计对普通“我要一个能工作的 AI”用户未必是优点。

因为别人会说：

> 怎么还得自己搭？

但对你却正好。

因为我们真正想碰的是：

```text
Agent 怎么运行？

↓

为什么选择这个 context？

↓

为什么把这个东西判断成重要？

↓

为什么形成这个概念？

↓

这个经验能否改变以后的选择？

↓

能否形成新的操作？

↓

新的操作能不能反过来发现以前发现不了的东西？
```

如果框架已经替你决定了一切，你很难碰到这些层。

Pi 留出来了。

# 但我发现 Letta 其实非常值得你看

这个我之前还低估了一点。

Letta 现在直接把自己定位为：

**“platform for building stateful agents”**

而且强调 agent 能从经验中学习、随着使用改善。citeturn601875search7

它现在的 AgentState 是真正持久化到数据库里的，并且保存重新建立这个 agent 所需要的状态。citeturn601875search5

更有意思的是它的 memory 不是简单：

```text
chat history
```

而分出了类似：

```text
core memory
    ↓
始终处于 context

archival memory
    ↓
需要时搜索

MemFS
    ↓
agent 可以检查和修改的长期记忆文件系统
```

Letta 的 memory blocks 是 context 中的持久结构，而且 agent 可以更新；它还有可搜索的 archival memory。citeturn601875search8turn601875search14

现在它的 MemFS 甚至是一个 **git-backed memory filesystem**：agent 可以检查、编辑长期 memory，而且这些内容跨 conversation 保留。citeturn601875search17

这已经很接近：

\[
Agent_t
\rightarrow Experience
\rightarrow Memory_{t+1}
\rightarrow Agent_{t+1}
\]

所以我觉得你应该**认真拆 Letta，而不是直接拿 Letta 当最终框架。**

因为还有一个区别。

Letta目前比较像：

\[
Experience
\rightarrow Memory
\]

而你追的更深：

\[
Experience
\rightarrow
\boxed{Structure}
\rightarrow
Perception/Action/Problem
\]

Memory只是 Structure 的一种。

---

## 然后有一个我觉得非常值得你注意的东西：DSPy

这可能比再找十个 agent 框架更接近你的问题。

DSPy现在的思想是：

> 不再手写 prompt，而把 LM system 当成一个可以优化的 program。

它的 optimizer 可以根据：

```text
输入
↓
agent trajectory
↓
结果
↓
metric
```

反过来修改：

```text
instructions
examples
prompt structure
甚至模型 weights
```

例如 MIPROv2 会收集运行 trajectory、挑选表现好的轨迹，然后生成并搜索更好的 instructions；GEPA 则会分析 trajectory 中“哪里有效、哪里失败”，生成新的改进规则。citeturn773791search0turn773791search4

这一下就出现了很关键的变化：

以前：

\[
Agent_t + Experience
\rightarrow Memory
\]

现在：

\[
Agent_t
\xrightarrow{experience}
evaluation
\xrightarrow{}
\boxed{Agent_{t+1}}
\]

至少某些 agent program 参数真的变了。

这距离你问的：

> 一次探索形成的东西，能不能变成以后真正可使用的能力？

已经明显更近。

当然 DSPy 仍然没有解决你全部的问题。

它通常要求：

\[
metric
\]

已经被人定义。

也就是说：

> “什么叫更好”

仍然是外部给它的。

而你真正更激进的问题甚至包括：

> agent 能否发现原来的评价维度本身就不对？

这又是下一层。

---

# OpenHands 也有一个很值得偷的设计

不一定使用 OpenHands。

但是我强烈建议你研究它现在的 **Event System**。

它把 agent 运行中的事情做成不可变的、typed、append-only event log：

```text
Event 1
Event 2
Event 3
Event 4
...
```

这个 event log 同时参与 agent state 和外围系统集成。citeturn413087search29

于是你不必只保存：

```text
“最终回答”
```

而可以保存：

```text
Goal
↓
Context selected
↓
Hypothesis formed
↓
Tool chosen
↓
Action
↓
Observation
↓
Prediction failed
↓
Revision
↓
Result
```

这非常重要。

因为如果将来要做：

\[
Experience\rightarrow Learning
\]

你首先必须拥有：

\[
\boxed{Experience}
\]

而不是只有一段总结。

OpenHands 现在甚至已经实验性加入 **Critic**：另一个 evaluator 会实时评价 agent 的行动，低于阈值时可以触发反思和重试。citeturn413087search12

这又提供一个组件：

```text
Actor
  ↓
Action
  ↓
Environment
  ↓
Observation
  ↓
Critic
  ↓
Learning proposal
```

所以我会**借 OpenHands 的 event architecture，而不一定整个采用 OpenHands。**

# Codex放在哪里？

这里我现在非常明确：

**不要重做 Codex 已经做得很好的东西。**

2026 年现在的 OpenAI Agents API 本身已经提供：

- managed Codex harness
- persistent session
- orchestration
- automatic context compaction
- recovery
- multi-agent
- MCP
- sandbox

这些已经属于成熟的执行基础设施。citeturn601875search0turn778918search7

甚至 OpenAI 明确把三层区分出来：

```text
Agents API
→ OpenAI 管 agent runtime

Agents SDK
→ 你控制 agent loop + handoffs

Responses API
→ 更底层，自己搭
```

citeturn601875search0

因此我不会花几个月重新制造：

```text
shell tool
patch tool
git diff
test runner
sandbox

```

这些不是你真正的新东西。

直接：

```text
Structural Core
        ↓
Pi
        ↓
Codex worker
        ↓
repo
```

就行。

# LangGraph 呢？

LangGraph其实很成熟。

它现在已经有：

```text
checkpoint
persistence
long-term stores
durable execution
human-in-the-loop
streaming
```

而且明确可以让 agent 在崩溃后恢复，并长期运行。citeturn413087search0turn413087search4

它甚至有 `sync / async / exit` 三种 durability 级别，可以控制每一步是否同步 checkpoint。citeturn413087search14

但是——

**我不会让你第一阶段从 LangGraph 开始。**

因为 LangGraph天然鼓励：

```text
Node A
 ↓
Node B
 ↘
 Node C
 ↓
Node D
```

而你现在恰恰还不知道真正的节点是什么。

如果太早写：

```text
PlannerNode
MemoryNode
CriticNode
ReflectionNode
```

很可能只是把现有 agent buzzword 画成了一张漂亮流程图。

而不是发现真正的认知结构。

所以：

> **先让结构长出来，再图化它。**

而不是：

> 先画 graph，再逼 agent 活在 graph 里面。

# Temporal更晚

Temporal非常强，但它解决的是另外一个问题：

\[
\text{Process crashes}
\neq
\text{Task disappears}
\]

它的 durable execution 可以在进程崩溃、网络断开、服务器重启后恢复 workflow 状态。citeturn601875search4turn601875search12

对于未来你的系统跑：

```text
几个小时
几天
甚至长期存在
```

会非常有价值。

但现在装它属于：

**还没造出生命，就先造 ICU。**

先不用。

# 所以如果现在真的开始，我会走这条路

第一版甚至不要多 agent。

```text
                 ┌─────────────┐
                 │     User    │
                 └──────┬──────┘
                        ↓
                ┌──────────────┐
                │      Pi      │
                │ agent loop   │
                └──────┬───────┘
                       ↓
             ┌───────────────────┐
             │ Structural Store  │
             │                   │
             │ observations      │
             │ hypotheses        │
             │ concepts          │
             │ relations         │
             │ procedures        │
             │ unresolved issues │
             └─────────┬─────────┘
                       │
             ┌─────────┴────────┐
             ↓                  ↓
          Codex             other tools
             ↓
       environment
             ↓
          Events
             ↓
       Event Store
             ↓
         Evaluator
             ↓
     Learning Proposal
             ↓
     Structural Store
```

重点是最后这三步。

不是：

```text
执行完
→ summary
→ memory
```

而是：

```text
执行完
↓
发生了什么？
↓
原来的什么判断失效了？
↓
新出现了什么关系？
↓
哪个操作以后可以复用？
↓
哪个概念应该被拆开？
↓
哪些观察今后应该被优先获取？
↓
提出结构修改
```

然后形成：

```text
ΔStructure
```

例如：

```text
+ 新关系
+ 新 hypothesis
+ 新技能
- 被证伪关系
~ 修改 relevance rule
~ 修改 context selection rule
~ 修改 task decomposition
```

于是：

\[
S_{t+1}=S_t+\Delta S
\]

下一轮不是简单“记得上一轮发生过什么”。

而是：

\[
Agent(S_{t+1})
\]

**真的和以前有所不同。**

这才是我觉得你该抓住的核心。

---

还有一个非常重要的限制：

第一版**不要让 agent 直接修改自己的整个代码、system prompt 和评价标准。**

不然很快就会变成：

```text
错误判断
↓
修改自身
↓
错误结构被固化
↓
以后所有判断都受影响
```

应该先采用：

```text
experience
↓
proposed structural change
↓
shadow version
↓
replay old tasks
↓
compare
↓
promotion
```

即：

\[
S_t
\rightarrow
S'_{t+1}
\]

先在历史经验上测试。

只有改善以后才：

\[
S'_{t+1}\rightarrow S_{t+1}
\]

这里 DSPy/GEPA 以后就能进来：它们本来就是“trace + metric → program improvement”的机制。citeturn773791search13turn773791search17

---

所以，我现在给你这条路的核心选择其实是：

```text
        Pi
         │
         │ 可修改的 agent runtime
         ↓
 ┌──────────────────┐
 │ 你自己的 Core    │  ← 真正研究对象
 └──────────────────┘
    ↑      ↑      ↑
 Letta   OpenHands DSPy
 memory   events   learning
 ideas    ideas    ideas

         ↓
       Codex
  强力执行 / coding

         ↓

后来才加入：

LangGraph → workflow / state orchestration
Temporal  → durable execution
```

**不是选一个框架。**

而是逐渐从这些框架里把已经解决的问题拿走，把那个没有人替你解决的问题留下来。

而我现在越来越觉得，那个“没人替你解决的问题”可以被说得非常精确：

\[
\boxed{
\text{一个 agent 怎样从自己的活动历史中，
产生能够改变未来活动空间的新结构？}
}
\]

这里的重点甚至不是“记忆”。

而是：

\[
\text{history}
\rightarrow
\text{structure}
\rightarrow
\text{new possible cognition/action}
\]

如果继续沿这个方向走，**Pi 很适合作为第一块实验地基；Letta 和 DSPy 是我这次检索后最建议你认真拆开的两个项目；Codex则不要改造成核心，把它留作极强的执行器。**

这条线，比继续追逐“下一个更强的 agent 框架”更接近你想去的地方。
