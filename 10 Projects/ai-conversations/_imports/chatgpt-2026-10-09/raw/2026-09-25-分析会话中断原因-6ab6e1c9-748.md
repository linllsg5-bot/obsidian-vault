## 那为什么偏偏这一条 thread 连续死？

这反而非常符合 `codex-chatgpt-web` 的运行方式。

它不是每一轮都打开一个全新的 ChatGPT 页面。


官方架构就是：**同一个 task/model/effort/compaction epoch 会持有一个确定的 WebContentsView；连续消息复用它。**citeturn662479view3

这意味着一个特别重要的事情：

假设某一次发生：

```text

        ↓

或者

旧 turn 没有完全 retire

或者

或者

browser helper 认为 DOM 消失
```

那么：

```text
这个 Codex task
      ↓
仍然绑定那个 ChatGPT browser surface
      ↓
继续
      ↓
还是那个坏 surface
      ↓
再断
      ↓
继续
      ↓
再断
```

而你新建：

```text

```


这就解释了你现在这个非常奇怪的现象：

> **旧 thread 怎么点继续都不行，新 thread 却可能完全正常。**

并不需要假设模型已经“装不下历史”。

核心流程是：

```
Codex task
   │
   │ 正常对话
   ▼
同一个 ChatGPT Temporary Chat
   │
   │ 上下文接近阈值
   ▼
Compaction
   │
   ├─ 让当前 ChatGPT agent 生成 structured checkpoint
   │
   ├─ checkpoint 保存：
   │    - 已完成工作
   │    - 当前状态
   │    - 用户约束
   │    - 关键决定
   │    - 未完成工作
   │
   ▼
关闭旧 ChatGPT chat
   │
   ▼
开启新的 ChatGPT chat / context epoch
   │
   ├─ checkpoint
   ├─ 必要的近期历史
   └─ 当前任务
   │
   ▼
继续同一个 Codex task
```

也就是说，它没有试图让一个 ChatGPT 会话无限长。**上下文到一定程度，就主动结束这一代 browser conversation，压缩成 checkpoint，然后开一个干净的新 ChatGPT 会话继续。** 对 Codex 来说仍然是同一个 task。[GitHub+1](https://github.com/miuuyy/codex-chatgpt-web/blob/main/docs/architecture.md?utm_source=chatgpt.com)

这其实正好击中了你刚才那个 `01a0c9f2...` 的问题。

你那个 task 现在相当于一直在：

```
旧历史
+ 工具结果
+ 代码
+ system/developer
+ 当前 workspace 环境
+ 历史 rollout
        ↓
重新灌入模型
        ↓
~180k input tokens
        ↓
stream disconnect
        ↓
retry
        ↓
又把巨大上下文灌进去
```

而 `codex-chatgpt-web` 的设计是：

```
180k 历史
       ↓
checkpoint
       ↓
可能只剩几千 / 几万 token
       ↓
新 ChatGPT browser chat
       ↓
继续执行
```

### 它有三层机制

第一层叫 **Native / structured compaction**。

Full mode 下，项目尽量直接使用**当前那个还活着的 ChatGPT agent**生成一次 checkpoint，而不是让另一个模型凭空重新总结。这个 checkpoint 通过一次性的 compaction control 返回。完成之后旧 browser surface 被关闭，下一阶段重新开 chat。[GitHub+1](https://github.com/miuuyy/codex-chatgpt-web/blob/main/docs/architecture.md?utm_source=chatgpt.com)

这点很重要，因为当前 agent 已经“看过”全部上下文。

所以不是：

```
巨大 JSON → 再发给另一个模型 → 摘要
```

而更接近：

```
已经拥有上下文的模型
        ↓
“把你现在知道的任务状态压成 checkpoint”
        ↓
checkpoint
```

这样传输压力小很多。

第二层是 **fallback compaction**。

如果旧 ChatGPT tab 已经死了、被关闭了或者 retained source 不存在，它不会直接宣告历史没了，而是从 **Codex canonical history** 重建一个专门用于摘要的 read-only ChatGPT 会话，再生成 checkpoint。[GitHub+1](https://github.com/miuuyy/codex-chatgpt-web/blob/main/docs/architecture.md?utm_source=chatgpt.com)

所以它本质上也有：

```
Browser memory
       ↓ 失效
Codex canonical history
       ↓
rebuild
       ↓
checkpoint
```

这和我们现在做的：

```
raw JSONL
   ↓
continuity_index
   ↓
定位原始 evidence
   ↓
新 session 恢复
```

思想非常接近。

只是你的方案更偏“**持久化、可追溯历史**”，它的方案更偏“**自动运行时上下文换代**”。

---

第三层叫 **Bigger Context**。

这不是摘要，而是解决“**一次 prompt 太大，连 ChatGPT 输入框都塞不进去**”。

它会把完整的有序记录切成最多 **6 个 staged messages**：

```
Part 1
Part 2
Part 3
...
Part 6
   ↓
最后一部分带：
- attachments
- execution contract
- output schema
```

它明确说：

> 更多 parts 只是减小单条消息尺寸，**不会减少保留的历史量**。

而且 Bigger Context 的 advertised context / compaction threshold 可以做到基础限制的大约 **3×**。[GitHub+1](https://github.com/miuuyy/codex-chatgpt-web/blob/main/docs/architecture.md?utm_source=chatgpt.com)

所以它实际上把两个问题分开处理了：

```
单条消息太大
    ↓
multipart / Bigger Context

总上下文越来越大
    ↓
compaction / checkpoint
```

这个区分非常合理。

还有一个与你现在的问题特别相关的修复。

之前它的 fallback compaction 有个严重 bug：

```
[旧 checkpoint]
[巨大 tool output]
[近期消息]
[当前压缩指令]
```

如果总大小超过 inline budget，旧版本是从头删：

```
删旧 checkpoint  ← 最不该删的反而先没了
保留巨大 tool output
保留近期消息
```

结果经过几轮 compaction 后，**早期目标、已完成工作和关键约束会慢慢消失**。

这个问题就是 GitHub **#447**。[GitHub+1](https://github.com/miuuyy/codex-chatgpt-web/issues/447?utm_source=chatgpt.com)

v5.0.7 改成了：

```
必须保护：
    最新 cumulative checkpoint
    最终 summary instruction

优先删除：
    老旧普通历史 / bulky tool output

如果 checkpoint 本身都放不下：
    明确报错
    而不是静默丢掉
```

并且它会明确告诉 compaction agent：

```
有 N 条较早历史因为 budget 被省略
当前提供的历史并不完整
```

这样模型不会错误地以为：

> “我看到的就是全部历史。”

这个修复已经进入 v5.0.7。[GitHub+1](https://github.com/miuuyy/codex-chatgpt-web/releases?utm_source=chatgpt.com)

所以现在它的记忆结构本质上已经变成：

```
             ┌──────────────┐
             │ 原始 Codex 历史 │
             └──────┬───────┘
                    │
       ┌────────────┴────────────┐
       │                         │
 recent exact history      cumulative checkpoint
 短期精确记忆                长期压缩记忆
       │                         │
       └────────────┬────────────┘
                    ↓
               当前模型上下文
```

这其实比“永远保留最近 N 条消息”强很多。
