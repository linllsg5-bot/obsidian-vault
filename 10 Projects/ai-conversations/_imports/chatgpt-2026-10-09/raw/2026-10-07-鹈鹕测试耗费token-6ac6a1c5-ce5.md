## assistant

那我建议你**不要直接跑完整鹈鹕测试**。它太浪费 token，而且“画得像不像”受随机性影响很大。

你真正要测的是：

> **中转站给你的模型，是否还是原模型的实际推理能力。**

我会做一个 **“鹈鹕 Lite”**，大概只需要 **5k～15k output tokens**，但能抓出很多降智情况。

### 测试方法

给模型同一个 prompt：

> **Draw a pelican riding a bicycle. Create the image as an SVG. Do not use external images. The SVG should be self-contained. Before producing the final SVG, reason carefully about the geometry, layering, anatomy, bicycle structure, and spatial relationships. Iterate internally until the result is coherent.**

然后**不要告诉它这是 benchmark**。

重点记录 5 个东西：

| 指标 | 看什么 |
|---|---|
| Output tokens | 有没有异常地少 |
| Reasoning tokens | 是否真的进行了推理 |
| SVG复杂度 | 有没有大量具体结构 |
| 空间关系 | 鹈鹕是否真的“骑”在自行车上 |
| 失败方式 | 是不会做，还是偷懒简化 |

### 但还有一个更狠的办法

不要只测试一次。

让：

**官方模型 → 中转模型**

跑完全相同的 prompt，然后比较：

```text
                官方       中转
──────────────────────────────
input              ≈         ≈
reasoning          ?         ?
output             ?         ?
SVG大小            ?         ?
元素数量           ?         ?
迭代次数            ?         ?
自行车结构          ?         ?
鹈鹕结构            ?         ?
空间关系            ?         ?
最终质量            ?         ?
```

尤其注意一个现象：

> **中转模型如果“特别快、特别短、特别自信”，反而值得怀疑。**

因为真正高推理模型在这个任务里，往往会花相当多 token 处理：

```text
鹈鹕身体
 ↓
重心
 ↓
腿的位置
 ↓
脚踏板
 ↓
自行车曲柄
 ↓
身体与车架的遮挡
 ↓
翅膀 / 脖子 / 喙
 ↓
前后轮空间关系
 ↓
SVG layering
```

如果中转站把 reasoning 截短了，它可能依然**声称自己“carefully reasoned”**，但实际上内部 token 数已经掉下去了。

---

### 如果你是想“一招检测”

我甚至不建议用鹈鹕。

我会用一个**极短、但需要真实推理才能完成的 SVG 几何任务**。

比如：

> **Create a self-contained SVG of a pelican riding a bicycle. The bicycle must have two wheels of exactly equal radius, the crank must be geometrically connected to the rear wheel through a chain, and the pelican's feet must visibly contact the pedals. Use no external images.**

然后要求：

> **After creating it, inspect your own SVG and list any geometric inconsistencies you find. If you find any, fix them before returning the final SVG.**

这一下就把测试从：

**“你会不会画鹈鹕”**

变成了：

**“你有没有真的进行多轮结构推理。”**

这才比较适合你现在要查的**中转站降智**问题。

而且 token 消耗会比完整版低很多。

如果你愿意，我可以直接给你一份 **“中转站降智检测 Prompt v1”**，专门针对 **GPT / Claude / Gemini 中转站**，控制在 **1～2 万 token以内**，同时设计成很难靠“表面回答”蒙混过去。

> **一只鹈鹕放在自行车上**

> **一只鹈鹕正在骑自行车。**

这恰好是这个测试有价值的地方。

### 第二个问题更有意思

它的**“局部正确”明显强于“整体约束”**。

例如：

- 鹈鹕头部像鹈鹕
- 嘴像鹈鹕
- 自行车像自行车
- 轮子像轮子
- 车架像车架

但是把这些东西作为一个**统一的空间系统**来看，就开始松了。

这正是很多模型的区别：

> **对象生成能力 ≠ 关系生成能力。**

鹈鹕测试真正有意思的地方，本来就不是“能不能画一只鸟”。

而是：

> **模型能不能让多个对象同时服从一个共同的空间约束。**

## assistant

如果你说的是现在流行的 **“鹈鹕骑自行车” Pelican Test**，那它的 token 消耗**不是固定的**，主要取决于模型和推理档位。

大致可以把它理解成：

- **普通/低推理**：几千 token
- **中高推理**：几千～几万 token
- **最高推理档**：可能 **5万～7万+**
- 极端情况下，如果模型不断自我检查、修改 SVG、调用工具，甚至可能达到**几十万乃至百万级**。

例如实际测试里：

- Kimi K3：**16,658 output tokens**，其中 **13,241 是 reasoning tokens**。输入只有 95 token。citeturn0search11
- Claude Fable 5.1 最高推理档：约 **65,927 output tokens**，成本约 $3.3。citeturn0search13
- 甚至有人让 Opus 5.5 做更复杂的鹈鹕迭代测试，报告过**单个 prompt 约 640 万 tokens**，不过那已经不是最原始的“一次生成 SVG”玩法了。citeturn0reddit24

还有一个很容易混淆的地方：

**你看到的“token 消耗”可能不是实际计费 token。**

比如 Codex / API 里通常会拆成：

> input tokens  
> cached input  
> output tokens  
> reasoning tokens

所以如果你是想拿**鹈鹕测试来检测“中转站有没有降智/偷偷限制模型”**，我反而建议不要只看总 token。

真正有意思的是看：

**同一个模型 + 同一个 prompt + 同一个 reasoning 档位 → 输出 token / reasoning token / 完成时间 / 最终 SVG质量**

这样才能看出中转站到底有没有动手脚。

如果你是准备拿它测你之前说的那些**中转站模型“默认降智”**，我可以直接给你一套**最省 token 的鹈鹕检测法**，一次测试就能抓出很明显的异常。
