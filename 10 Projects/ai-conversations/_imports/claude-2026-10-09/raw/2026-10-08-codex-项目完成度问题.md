# Codex 项目完成度问题

## You
*2026-10-08T00:42:58.293185Z*

为什么项目软件让codex做，完成度这么低

思考了 32s
因为你看到的“完成度”，和 Codex 默认理解的“完成”根本不是同一种东西。

Codex 很强，但它天然更接近一个极强的软件工程执行者，而不是一个会自己长期扮演「产品经理 + 架构师 + 交互设计师 + QA + 用户」的人。OpenAI 自己现在对 Codex 的描述也主要是从 issue 到 tested、review-ready code；官方 Cookbook 甚至明确说，它本来就最擅长的是 well-scoped coding tasks。

这对你的 Cognos 尤其严重。你说的初版已经包括组织、项目空间、讨论、文件、任务、成员主页、修改留痕，而且不是“页面摆出来”，而是希望几个同学真的能进去持续工作。这个目标实际上包含了几十甚至几百个没有显式写出来的判断。

比如你只告诉 Codex：

做一个项目空间，有任务、文件、讨论。

它很容易认为：

/project/:id 能打开
任务能 create/update/delete
文件有上传按钮
讨论能发消息
数据库有对应表
页面不报错

=> done
而你心里的“完成”其实更像：

创建组织
→ 邀请成员
→ 对方加入
→ 创建项目
→ 权限正确继承
→ 创建任务
→ 指派成员
→ 成员能看到
→ 评论任务
→ 上传附件
→ 文件能预览/下载
→ 操作留下历史
→ 刷新状态不丢
→ 删除/退出/无权限行为正确
→ 手机和桌面都不难用
→ 空状态、加载、错误状态正常
→ 页面之间信息一致
→ 连续用半小时不会不断碰到“这里还没做”
这两个“完成”甚至不是一个数量级。

所以你感觉它“明明写了非常多，项目却像个半成品”，并不奇怪。

更关键的是，Agent 有一种非常强的局部闭合倾向。给它一个模糊的大目标以后，它必须自己决定“做到哪里算结束”。而最容易验证的结束条件就是：代码编译、页面出现、API 能返回、测试通过。

但“这个软件已经像个软件了”没有那么容易被机器验证。

因此会发生一种很典型的现象：

代码完成度 80% → 产品完成度可能只有 30%。

很多剩下的 70%，不是庞大的核心算法，而是大量连接组织：

权限传播、状态同步、导航关系、交互反馈、错误恢复、数据生命周期、删除规则、边界条件、历史记录、搜索筛选、上传下载、空状态、首次使用、成员退出后的数据、刷新后的状态……

这些东西单独看都很小。

但正是它们决定软件有没有“实体感”。

而你之前的工作方式还有第二个问题：大量真正的产品定义存在于你和模型的对话里，而没有变成 repository 内可执行的约束。

于是你和我可能已经聊了：

Cognos 不是普通微信群。
项目应该是持续工作的空间。
组织不是简单群聊。
修改需要留下痕迹。
初版完成度够高以后就要直接拉同学使用。

但 Codex 新开一次任务，看见的往往只是代码和这一轮 prompt。

它并没有真正拥有那个完整的“Cognos 世界”。

这也解释了为什么你之前会觉得：讨论越来越深，代码却没有把那个东西真正长出来。

而且 OpenAI 自己在今年写 Codex 工程实践时，碰到的几乎就是这个问题。他们说早期进展比预期慢，并不是 Codex 本身不会写代码，而是工程环境 underspecified；后来他们不断把缺失的工具、抽象、文档、guardrails、测试和验证机制编码进 repository，Codex 才逐渐能端到端完成 feature。

这句话其实非常重要。

不是：

给 Codex 更聪明的模型
→ 软件自然完整。

而是：

把“什么叫完整”变成机器能够观察、执行、失败、重试的结构
→ Codex 的能力才能释放出来。

所以我现在对你这个项目的判断，比之前更明确：

你缺的主要不是更强的 coding model。你缺的是 Cognos 的「完成度控制系统」。

可以把它做成四层：

Product State：明确现在 Cognos 已有什么、缺什么、哪些决定已经确定，Pi/Fable 之类的外层 agent 长期维护它，而不是重新读几万字聊天记录。
User Journeys：不用先拆成一堆技术 issue，而是写真实行为链。例如“新用户第一次进入 → 加入组织 → 找到项目 → 接到任务 → 完成任务 → 其他成员看到变化”。一条链必须从头跑到尾。
Definition of Done：每个功能不是“implemented”，而必须满足 UI、数据、权限、错误状态、刷新、跨页面一致性和测试等条件。Codex 不允许自己决定什么时候 finished。
Independent Review：一个 Codex 做实现，另一个上下文完全独立的 agent 当用户/QA，只负责挑毛病、实际运行、点页面、检查数据库和边界。实现者自己验收自己，非常容易沿着自己的假设把错误一起验过去。
这也是为什么我之前倾向于让 Pi 做长期主 Agent，Codex 做工程 worker。不是因为 Pi 写代码比 Codex 强，而是你这个项目最大的难题已经从：

“谁能写出这段代码？”

变成：

“谁一直知道我们到底在造什么，并且知道现在离那个东西还有多远？”

Codex 的 Goals 功能现在其实也在往这个方向补：给长期 thread 一个持久目标、completion condition 和 constraints，而不是每一轮只拿一个 prompt 干活。

但仅仅打开 Goals 也解决不了根本问题。

因为你首先得定义：

Cognos 什么时候算完成？

不是抽象的“功能完善”。

而是比如第一版最终有 12 条核心用户旅程。

12 条我全部可以亲手跑通。

每条途中都没有 mock、TODO、假按钮、临时页面、断裂链接。

这时候完成度就突然变成一个 Codex 可以真正攻击的问题。

甚至我现在觉得，你下一步不应该继续让 Codex“完善 Cognos”。

这句话太危险。

应该把当前 repo 扔给它，但第一轮一行功能代码都不许改，只让它做一件事：

像一个极其挑剔的新用户一样，把现有 Cognos 从注册开始完整使用一遍，列出所有阻止它成为一个真实可用产品的断点，并把它们组织成用户旅程和依赖图。

然后我们再看那个结果。

我怀疑到那时你会第一次非常清楚地看见：不是 Codex 只完成了 30%。而是过去根本没有一个东西在持续计算“剩下的 70% 是什么”。

应该怎么做一个软件
做一个软件，真正的顺序不是“想功能 → 写代码 → 能跑就结束”。

更像是在造一个能持续运转的小世界。

先从一个最小问题开始：这个软件到底要让谁，在什么情境下，完成什么以前很难完成的事。这里不要先想页面，也不要先想技术栈。比如 Cognos 的起点不是“做组织、项目、讨论、文件、任务模块”，而可能是：

“几个人能围绕一个长期项目持续协作，而且讨论、任务、文件、决定和变化不会散掉。”

这句话很重要，因为后面所有功能都应该服务它。

然后不是列功能，而是先写用户旅程。例如，一个新成员第一次进入软件，他应该经历什么：被邀请、加入组织、理解这里在做什么、进入项目、看到当前状态、接到任务、参与讨论、上传文件、完成任务、留下历史记录。只要这条路中间断一次，这个软件对这个用户来说就还没完成。

接下来才把这些旅程拆成系统内部真正存在的东西。通常要同时设计几层：

对象：用户、组织、项目、任务、讨论、文件、成员、权限、历史记录。
关系：谁属于谁，谁能看谁，任务属于哪个项目，文件关联哪个讨论，成员退出后数据怎么办。
状态：任务从未开始到进行中再到完成；邀请从待接受到已加入；文件上传中、成功、失败。
行为：创建、修改、删除、指派、评论、搜索、恢复、退出。
规则：什么允许，什么不允许，发生错误时系统怎么处理。
这一步其实比写代码更重要。因为软件不是一堆页面，而是：

对象 + 关系 + 状态 + 规则 + 时间中的变化。

然后你再做界面。

界面只是把这个世界暴露给人。一个按钮存在，不代表功能存在。真正的完整链条应该是：

用户点击
→ 前端反馈
→ 请求发送
→ 权限检查
→ 数据改变
→ 其他相关数据同步
→ 页面更新
→ 刷新后仍然存在
→ 其他成员看到正确结果
→ 操作被记录
→ 出错时能恢复
少一两环，人就会产生那种很明显的感觉：

“这只是个 demo。”

然后才进入工程实现。

这时候最好不要告诉 Codex：

把任务系统做完。

而是给它：

实现“成员创建任务 → 指派给另一成员 → 对方在自己的任务列表看到 → 修改状态 → 项目动态记录变化”这一整条旅程。
必须包含权限、持久化、loading/error/empty 状态、刷新一致性和自动测试。
未满足全部验收条件不得标记完成。

这会比按“页面”或者“模块”拆任务强很多。

每完成一条旅程，都要真的运行软件去用，而不是只看代码。最好有一个完全不同的 agent 或人来做验收，因为写代码的人天然知道“正确用法”，真实用户不知道。

你甚至可以把软件开发理解成一个循环：

意图
↓
用户行为
↓
系统模型
↓
实现
↓
实际使用
↓
发现断裂
↓
修改系统模型
↓
继续实现
而不是：

需求
↓
生成代码
↓
结束
还有一个非常容易被忽略的阶段：收口。

软件做到后面，不应该不断加新功能，而应该进入一段专门的“消灭半成品”阶段。把所有 TODO、假数据、无效按钮、断裂页面、错误提示、权限漏洞、刷新丢失、样式异常、移动端问题、边界状态，一个一个清掉。

很多软件真正从“项目”变成“产品”，就是发生在这里。

所以，如果是我现在来做 Cognos，我不会继续让 Codex漫无目的地“完善项目”。

我会先停写新功能，建立这四样东西：

PRODUCT.md
软件究竟是什么、服务谁、第一版边界是什么

MODEL.md
核心对象、关系、状态、权限

JOURNEYS.md
10~20 条真实用户完整旅程

ACCEPTANCE.md
每条旅程什么时候才算真正完成
然后 Codex 每次只攻一条旅程。

当所有核心旅程全部连续跑通，第一版才结束。

这其实就是我现在对“怎么做一个软件”最简洁的答案：

先决定它要发生什么，再设计什么东西必须存在，最后才写代码。

代码只是最后那个让世界真的动起来的部分。

大方向是对的，但它说得比实际能确定的更肯定，有几处我会打折扣。

**说得对的部分**

核心判断站得住：你心里的"完成"是一整条能连续用半小时的链路，而 Codex 这类 agent 拿到模糊目标后，会把"能编译、页面能打开、接口有返回"当成结束条件。这是 agent 做大项目时很常见的失败模式，不是 Cognos 独有的。"产品定义留在聊天里，没进 repo"也很关键：新开一轮任务的 agent 看不到你和模型讨论过的那些东西。

**我会打折扣的地方**

1. **它没看过你的代码。** 整段分析是从你描述的现象反推的，"代码 80%、产品 30%"这类数字是编出来的修辞，没有依据。真实情况可能是别的原因：架构一开始就乱了、一次让它做的范围太大、数据模型反复改、或者它根本没有真正运行过应用。这些要看 repo 才能判断。
2. **"Codex 不是产品经理/架构师"说得太绝对。** 它缺的不是能力，而是没人给它约束和反馈。给了明确的旅程和能跑的验证，它做得不差。
3. **四份文档（PRODUCT / MODEL / JOURNEYS / ACCEPTANCE）有点重。** 文字验收标准很容易和代码脱节、慢慢过期。更有效的是把验收写成**可执行的东西**：每条旅程对应一个端到端测试（比如 Playwright 脚本），跑不过就是没完成。文档只留一份短的，说明产品是什么和已定的决定。
4. **"12 条核心旅程"是拍脑袋的数字。** 先定 3 到 5 条最关键的，比如"邀请同学加入 → 建项目 → 指派任务 → 对方看到并完成 → 留痕"，跑通一条再加下一条，别一开始就铺开。
5. **它提到的 OpenAI Cookbook、Goals 功能等细节，我没法核实**，这些在我的知识截止之后可能有变化，别当成定论。

**我觉得最值得做的一步**

它建议的"先别写新功能，让 Codex 扮演挑剔的新用户，把现有 Cognos 从头用一遍，只列断点"，成本低、信息量大。这一步做完，你才会知道问题到底是"缺很多零碎细节"还是"底层模型就不对"，后面该补还是该重构就清楚了。让它真的把应用跑起来、用浏览器点，而不是只读代码。

另外，写代码的和做验收的最好是不同的会话，上下文互相独立，这点它说得对。
