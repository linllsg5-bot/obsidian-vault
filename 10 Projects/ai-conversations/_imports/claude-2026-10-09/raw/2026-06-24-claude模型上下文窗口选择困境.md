## 为什么"1M效果提升不大"这个说法是对的，但理解有偏差

研究显示，Paul Gauthier（Aider作者）发现几乎所有模型在超过约25-30k tokens时就开始出现混乱，这是他用户报告的头号问题。NoLiMa基准测试也发现，12个被测模型中有11个在仅32k tokens时性能就跌破短上下文的50%。

所以问题不是"1M vs 200k"，而是**上下文压缩（compaction）在哪个点触发**。

关键在于：默认 auto-compaction 的触发阈值是上下文容量的约95%。也就是说，1M窗口要到950k tokens才会触发压缩——已经远超质量开始下降的节点了。相比之下，200k窗口设置70%阈值，压缩在约140k时触发，远早于质量下降点，且每次需要压缩的内容更少，压缩质量也更好。

---

## 你200k不够用怎么办

有两个环境变量可以精确控制这个行为：`CLAUDE_CODE_DISABLE_1M_CONTEXT=1` 会把上下文窗口锁回200k，从模型选择器中移除所有1M变体；`CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` 设置为1-100之间的值，控制触发auto-compaction的百分比阈值。

**你的推荐配置：**

```bash
# 不要禁用1M，但让它更早压缩
CLAUDE_AUTOCOMPACT_PCT_OVERRIDE=35
```

这样1M窗口在约350k时触发压缩——比你200k的对话长，有足够余量，但又不会让上下文腐烂到950k。

---

## 关于开1M的前提（Plan层面）

在Claude Code中使用Pro、Max、Team或Enterprise计划时，Claude Opus 4.8/4.7/4.6和Fable 5支持1M token上下文。Pro用户需要开启usage credits才能访问Opus的1M上下文窗口。Sonnet 4.6也支持1M上下文，但所有付费计划都需要开启usage credits才能使用（usage-based Enterprise计划除外）。

---

## 核心判断

| 情况 | 建议 |
|---|---|
| 对话 < 150k，偶尔超 | 保持200k，调 `AUTOCOMPACT=70` |
| **对话经常 > 200k（你的情况）** | **开1M，同时设 `AUTOCOMPACT=30~40`** |
| 需要加载整个大型代码库 | 开1M，但主动用 `/clear` 切任务边界 |

说"1M没必要"的人，通常是在**没有调 autocompact 阈值**的情况下用的——默认到950k才压缩，确实会出现 goal drift 和幻觉增加。真正的解法是这两个变量一起用。

## 先纠正上一条回答里的一个错误

**`CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` 有个重要限制：它只能让压缩"提前"触发，无法推迟到默认阈值之后。内部代码用了 `Math.min()` 上限钳制，设置超过约83%的值会被静默忽略。** 这个问题记录在 GitHub issue #31806 中。

也就是说：我之前建议你对1M窗口设35，是对的方向；但说默认是"95%触发"不够准确——

默认 auto-compaction 在约83.5%时触发，也就是200K窗口下约167K tokens时压缩；系统为响应生成预留约33K token的内置缓冲（最近从45K降到33K，这次更新未在官方changelog中公告）。

所以**对于1M窗口，默认在约830K时才压缩**，同样远超质量下降点。

## 你的问题完整解法

Anthropic官方在2026年4月15日发文明确指出：会话管理和上下文压缩策略，对Claude Code使用体验的影响比你想象的更大，几乎所有细节都来自如何管理上下文窗口。

### 第一层：环境变量配置（一次性设好忘掉）

**适合你的配置（对话长、超200k）：**

```bash
# 加入 ~/.zshrc 或 ~/.bashrc

# 开启1M窗口（如果你用的是Pro需要先开usage credits）
# 不需要额外环境变量，在/model里选 "Sonnet (1M context)" 或 "Opus (1M context)"

# 让压缩在40%时触发（即400K tokens），而非默认的830K

```

还有另一个变量 `CLAUDE_CODE_AUTO_COMPACT_WINDOW`，可以先缩小有效窗口大小，再叠加百分比阈值——两者组合能更精确控制绝对token数。

如果你想行为完全类似200K窗口（但有1M的备用空间），可以设：

```bash
export CLAUDE_AUTOCOMPACT_PCT_OVERRIDE=20   # 在200K时压缩，和之前行为一致
# 或
export CLAUDE_CODE_AUTO_COMPACT_WINDOW=300000  # 把有效窗口限制在300K
```

---

### 第二层：主动手动 `/compact`（最重要的习惯）

大多数人在看到80-95%的警告时才运行 `/compact`，但这时候已经有点晚了。更好的做法是在**约60%上下文使用量时主动触发**，在这个节点Claude对整个会话仍有完整清晰的记忆，因此产出的摘要质量更高。

而且可以**指定保留内容**：

```
/compact 保留：数据库schema设计决策、API端点列表、已排除的方案Y
/compact Focus on the auth refactor, drop the test debugging tangents
```

有指令的 `/compact` 比无指令的好——自动压缩在上下文腐烂时触发，此时模型处于"最不聪明"的状态，产出的摘要质量最差。而你主动触发时，模型还有足够余量，记忆完整，摘要质量更高。

---

### 第三层：CLAUDE.md 作为持久记忆

你每次会话都要用到的规则、项目约定、架构决策，放到 `CLAUDE.md` 而不是依赖对话历史——这个文件在 `/clear`、会话终止、重启电脑后都会自动加载。

比如对你的 prototype-spark：

```markdown
# CLAUDE.md
## 核心架构原则
- 三层架构：对话层、认知层、行动层
- "尝试"和"视角"作为共同本体论基元
- API使用claude-sonnet-4-6

## 开发约定
- 所有组件用TypeScript
- ...
```

---

### 第四层：用 Subagents 隔离上下文

Subagents 拥有完全独立的上下文窗口，它们的中间工作不会污染你的主会话。完成后只把结果摘要返回给主会话。这是长会话中保持主上下文干净的关键工具。

比如：`"use subagents to investigate how the existing API quota system works"` ——让它去读代码、搜信息，你的主会话只接收结论。

---

## 一句话总结

**开1M，设 `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE=40`，在60%时手动 `/compact` 并附保留指令，把不变的架构决策写进 `CLAUDE.md`。** 这四层叠在一起，比单纯"开不开1M"重要得多。
