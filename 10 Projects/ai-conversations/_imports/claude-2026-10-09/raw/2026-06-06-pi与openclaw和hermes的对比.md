## Pi（π-lang）是什么

Pi 是一种面向 agent 的编程语言，专为自主、持久、多工具系统设计。不同于 Python 或 JavaScript 这类为人工触发的顺序任务构建的语言，Pi 天生支持持续运行、记忆状态、跨多服务协调的工作流。OpenClaw、Hermes 和 Paperclip 都基于它构建。

---

## OpenClaw vs Hermes：两种根本不同的哲学

**OpenClaw 的核心是"控制平面"**

整个系统围绕一个长期运行的 Gateway 守护进程，统一管理所有入站和出站消息通道：WhatsApp、Telegram、Slack、Teams、Gmail、Salesforce 等。它的优势是多平台覆盖广，生态庞大。

**Hermes 的核心是"学习循环"**

Hermes 是一个执行循环，整个系统围绕"做 → 学 → 改进"的循环组织，其他所有组件（cron 调度器、终端接口、ACP 集成）都服从于这个循环。

---

## 关键维度对比

**记忆系统**
Hermes 采用四层系统：会话历史、用户画像、FTS5 全文检索、LLM 摘要，显式构建用户模型并将解题方法保存为可复用的 markdown 技能文件。OpenClaw 提供简单易读、可版本控制的记忆文件，适合团队共享；Hermes 提供结构化、可检索的记忆，更适合长期个人知识积累。

**上下文透明度**
OpenClaw 隐藏了更多资源消耗细节，不主动告诉你消耗了多少 context；Hermes 直接显示 context 使用情况，更容易判断 agent 何时过载、记忆何时可能不可靠。

**安全与复杂度**
Hermes 安全风险低于 OpenClaw，无需复杂的多组件配置。

**上手难度**
OpenClaw 安装体验接近消费级应用，用默认配置即可快速启动；Hermes 则假设你是开发者，环境配置文件可能包含 30 个以上变量，需要逐一理解配置。

Pi 的"好伸展"不是一个功能，而是**一系列相互支撑的设计决策**，从底层哲学到具体机制都在服务这个目标。

---

## 一、极简核心——故意留白

Pi 的创始人 Mario Zechner 的论点是：所有前沿模型都已经被大量 RL 训练过，它们天生理解什么是 coding agent，不需要一个一万 token 的系统提示来解释这件事。

结果：Pi 的系统提示和工具定义加在一起不超过 1000 token，只给四个工具：read、write、edit、bash。

**留白才是伸展的空间所在**——核心越小，扩展层就越不会与核心冲突。

---

## 二、严格分层的 monorepo 架构

Pi 是一个 TypeScript monorepo，各包像层叠一样构建：`pi-ai` 负责 LLM 通信，`pi-agent-core` 在其上增加工具调用的 agent 循环，`pi-coding-agent` 再往上提供完整的 coding agent，`pi-tui` 提供终端 UI。

依赖关系是强制执行的：foundation 包零内部依赖，core 包只依赖 foundation，应用层在最上面。这不是一个愿景，是构建系统强制执行的。

分层清晰意味着你可以只用某一层，不必接受整个体系。

---

## 三、渐进式 skill 披露机制

这是 Pi 最精妙的伸展设计之一：

Skill 采用渐进式披露模型来节省 context token。系统提示里只注入 skill 的名称和描述；当 agent 判断当前任务匹配某个 skill 时，才用 read 工具去获取完整的 SKILL.md 内容。

这意味着你可以挂载几十个 skill，context 开销几乎为零——只有真正被触发的 skill 才"进入"对话。

---

## 四、TypeScript 扩展系统 + 热重载

你不需要去修改 Pi 的源代码来扩展它。你让 Pi 写一个 TypeScript extension，然后热重载，就完成了。agent 扩展自身，而不是你去配置它。

Pi 有超过 25 个 hook，用于自定义行为、主题、键绑定和工具执行。extension 系统支持热重载 skill、prompt template、甚至 sub-agent。

---

## 五、统一的 LLM 抽象层，无锁定

`pi-ai` 提供统一的 LLM API，抽象了不同提供商的差异，支持 Claude、GPT-4o、Gemini、Grok、Groq、Cerebras 以及 OpenRouter 上的所有模型。切换模型只需改一行配置。

---

## 六、bash 作为终极逃生阀

与其内置专用工具（如"在代码库里搜索"），不如直接用 bash 调 `rg`；与其内置 GitHub 工具，不如 bash 调 `gh`。模型能读 README，能自己学会 CLI 工具。这个方式可组合（管道、链式命令）、易扩展（加一个脚本就行）、token 高效。

bash 本质上是一个"无限工具"——任何你需要的能力，shell 都能搭进来。

---

## 总结

| 设计决策 | 为什么带来伸展性 |
|------|------|
| 系统提示 < 1000 token | 给扩展留足 context 空间 |
| 严格分层 monorepo | 可以按需只用某层 |
| Skill 渐进披露 | 挂再多 skill 也不撑爆 context |
| TypeScript 扩展 + 热重载 | 无需 fork 就能改变行为 |
| 统一 LLM 抽象 | 模型随时换 |
| bash 作为兜底 | 任何工具都能接入 |

核心逻辑只有一条：**把"不该在 core 里的东西"彻底清出去，然后把扩展机制做成一等公民。**

```
├─────────────────────────────┤
│       语义检索层             │  ← 向量搜索，找相关记忆

│       用户建模层             │  ← 持续更新对你的认知
├─────────────────────────────┤
│       沉淀判断层             │  ← 什么值得留下，怎么写成 skill
├─────────────────────────────┤
│       观察捕获层             │  ← 记录发生了什么，效果怎样
├─────────────────────────────┤
│     Pi 的 extension/skill   │  ← 只到这里
└─────────────────────────────┘
```

Hermes 把上面五层都造好了，你用 Pi 就要自己造。

## 每层的实际工作量

**观察捕获层** — 相对简单。用 Pi 的 `tool_call` hook 把每次操作写进 SQLite，难度不高。

**沉淀判断层** — 开始复杂。谁来判断"这次值得留下"？是你手动触发、还是 agent 自己评估？评估标准是什么？这一层需要你设计。

**用户建模层** — 需要 schema 设计。你是什么人、你的工作模式、你的认知偏好——要结构化地存，还要随时间更新而不冲突。

**语义检索层** — 技术门槛最高。需要 embedding 模型 + 向量数据库（SQLite-vec 或 Chroma），新会话开始时要做相似度搜索，找到相关记忆注入上下文。

**上下文注入层** — 注入什么、注入多少、怎么避免撑爆 context window——这本身是个设计问题。

---

## 所以真实的选择是

造这五层，不是写几个 skill 文件。工作量接近造一个简化版 Hermes，但你可以让它完全符合你自己的认知架构——比如和你的 ECC 框架、贯穿式疑问的逻辑对齐，而不是用 Hermes 的"做→学→改进"那套通用循环。
