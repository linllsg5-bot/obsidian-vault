## 先说 bash 的来龙去脉

这份文档里 "bash" 出现在两个不同层次,值得先拆开看:

**Pi 里的 bash:是一个内置工具,能被事件钩子拦截**

```typescript
pi.on("tool_call", async (event, ctx) => {
  if (event.toolName === "bash" && event.input.command?.includes("rm -rf")) {
    return { block: true, reason: "Blocked" };
  }
});
```

这里 `bash` 本质上就是众多 `registerTool` 注册出来的工具之一(和 `read_file`、`edit` 平级)。Pi 的核心循环是固定的——工具调用发生时会广播 `tool_call` 事件,你的扩展在这个事件上挂一个 handler,通过返回值(`{block, reason}`)去干预。这是**行为层面**的控制:你能拦截、能替换返回内容,但 bash 命令具体怎么执行(本地进程?哪个 shell?)这件事本身,Pi 没有给你切换的接口——除非你去 override 整个 `bash` 工具的 `execute`,或者用 `user_bash` 那类专门的钩子。

**dsh 里的 bash:不是工具,是 Seam 背后的一个能力**

dsh 的说法是"Seam"——文件系统、子进程(subprocess)、shell、终端(PTY)、沙箱、LSP 这些都不是写死的工具,而是**服务接口 + 可替换实现**。文档里那句话是关键:

> "Pointing them at a remote sandbox moves Bash, PTY, and LSP with them, with no provider forks."

意思是:bash 命令实际在哪执行,取决于谁在提供 subprocess 这个 Service。你把 subprocess provider 换成"远程沙箱实现",那么不只是 bash,连带 PTY(终端)、LSP(语言服务器)都会一起被路由到远程去执行——因为它们底层共用同一套"进程/文件系统"接口,不需要给每个工具单独写一份"远程版本"。这是**实现层面**的控制,比 Pi 的事件拦截更彻底。

一句话总结这个差异:**Pi 的 bash 是"能被观察和拦截的工具调用";dsh 的 Bash 是"可以被整体换血的能力接缝"。** 前者像是给函数加装饰器,后者像是换掉依赖注入容器里的一个实现类。

## 逐个维度再展开一遍

文档本身已经很详细了,我换个角度——把每个概念拆到"为什么这么设计"和"具体后果是什么",而不只是罗列对比。

### 1. 入口形态:命令式 vs 声明式

Pi 的 `export default function(pi) {...}` 本质上是"我告诉框架我要做什么",执行顺序就是代码书写顺序。这简单,但也意味着**扩展之间的协作全靠约定**——如果 A 扩展依赖 B 扩展先注册好某个东西,你只能靠控制加载顺序(比如文件名前缀、目录层级)去保证,框架不会替你检查。

dsh 用 `inject` 声明依赖,加载顺序从命令式变成了拓扑排序的结果。好处是可靠(依赖没就绪,插件就是 `PENDING` 状态,不会跑出一半报错);代价是你要先想清楚"我依赖谁的服务",这是一种更规矩但更繁琐的心智负担——有点像从"脚本式编程"过渡到"依赖注入框架"的那种转变(Spring/NestJS 那味儿)。

### 2. 事件模型:固定命名 vs 类型化 + 分发策略

Pi 的事件表是一份写死的清单(`tool_call`、`turn_start` 等),你没法定义新事件类型,只能挂在已有的钩子上。

dsh 的四种分发模式其实对应了四种常见的"广播语义":

- `emit`——纯通知,没人关心你返回什么(日志、埋点场景)
- `waterfall`——像洋葱中间件,每一层可以修改、也可以短路(鉴权、过滤这类场景)
- `parallel`——大家同时干活,互不影响结果(比如多个插件各自做校验,互不依赖)
- `serial`——按顺序跑,且要等待,通常用在"步骤必须依次完成"的场景

`waterfall` 那个 `next()` 机制,其实就是 Koa/Express 中间件的洋葱模型——不调用 `next()` 就相当于短路整个链条,这跟 Pi 里 `return {block: true}` 的效果类似,但 dsh 把这个模式产品化成了框架内建的分发策略,而不是每个事件各写各的返回值约定。

### 3. Seam / 服务三角色

Service Definition(接口)、Service Provider(实现)、Consumer(消费者)——这套东西如果你熟悉后端开发,就是标准的"面向接口编程"。好处在于**测试和替换的解耦**:比如你想在本地跑 dsh 但把文件系统换成"内存虚拟文件系统"用于测试,理论上只需要换 provider,不用改任何消费这个服务的插件代码。

Pi 没这一层抽象,如果你想让 `read_file` 走一个虚拟文件系统,你得直接 override 这个工具的实现,等于是"手动打补丁"而不是"插拔式替换"。

### 4. 生命周期:手动清理 vs 自动可逆(effect/disposer)

这个差异其实是"谁对资源泄漏负责"的问题。Pi 明确提醒你——不要在工厂函数里启动后台资源,要等到 `session_start`,并且自己在 `session_shutdown` 里清理,这是一种**约定优于强制**的设计,信任扩展作者会守规矩。

dsh 的 `ctx.effect(() => { ...; return cleanup })` 把"注册"和"清理"绑成一个原子操作——每次注册都必须配一个 disposer,框架强制回收。这在插件热插拔(HMR)场景下特别重要:如果没有自动清理,你重载一个插件十次,可能就有十份重复的 watcher/socket 残留在内存里。dsh 能做到 HMR 而 Pi 只有整体 `/reload`,根源就在这里——**HMR 依赖"卸载是可逆的"这个前提**,Pi 没有这个保证,所以只能重启整个进程级的重载。

### 5. 工具返回值:内容块 vs "规范值 + 渲染分离"

这一条容易被忽略但挺关键。Pi 的工具直接返回给模型看的内容块(`{content: [{type: "text", text: ...}]}`),数据和展示是耦合的。

dsh 把 `output.schema`(工具返回的"真实数据",给程序用)和 `output.render`(转成模型能读的文本)拆开了。这背后是在支持"Code Mode"——也就是说,除了让 LLM 通过自然语言调用工具,dsh 还想让代码(比如另一个脚本、另一个 Agent)能直接 `await tools.read_file(args)` 拿到结构化返回值,而不用去解析一段自然语言文本。这其实是在为"工具调用" 和 "程序调用" 两条路复用同一份定义,Pi 目前没有这个考虑,它的假设是"工具的消费者始终是模型"。

### 6. UI 扩展:TUI vs Web + Card

这个差异基本反映了两个产品的定位——Pi 是终端里跑的 coding agent,扩展面向终端渲染(状态栏、自定义 widget);dsh 是 Web 应用形态,扩展的是网页里的"对话节点"渲染逻辑,工具调用会展示成一张张卡片(有 icon、位置信息等),这是给"图形界面用户"设计的展示层,跟 Pi 面向"终端重度用户"的假设完全不同的产品哲学。

### 7. 打包与配置分层

Pi 的 `settings.json` 是扁平的,包名列一列就完了。dsh 的 profile → bundle → patch 是**分层叠加**,而且能按 row id 局部替换上一层配置(有点像 CSS 的层叠优先级,或者 Kubernetes 里 kustomize 的 patch 机制)。这种设计对"要维护多套环境变体"(比如 web app 版 / headless 版 / 用户个人定制版)特别友好,但也意味着排查"某个配置到底从哪层来的"会更费劲——分层越多,可调试性通常和灵活性成反比。
