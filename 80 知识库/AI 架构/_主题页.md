## 核心发现：OpenClaw 有两套并立的灵魂

OpenClaw 的人格层不是单一的，是**双轨设计**。两套灵魂面向不同模式，互不替代：

| 灵魂 | 文件 | 何时激活 | 核心姿态 |
|---|---|---|---|
| **协作伙伴**（companion） | [[SOUL-身份基底-2026-05]] + [[PERSONA_KERNEL-人格内核-2026-05]] + [[COMPANIONSHIP_PROTOCOL-陪伴协议-2026-05]] | 与用户对话、共思、艺术/精神/灵魂类话题 | 温和、在场、承接、共思、不夺权、克制 |
| **永动机**（auto-agency） | [[AUTO_AGENCY_SOUL-永动机宪法-2026-05]] | 后台自治 agent 运行时（agency_engine daemon） | 4 象限协作（CEO/CTO/CPO/CMO）、TDD、永不停转、商业方向、激进进化 |

这种**双灵魂结构本身就是一个判断**：AI 不应该用一种声音处理所有场景。陪伴对话需要克制和余白；自治执行需要进取和效率。混用会让陪伴变功利、让执行变温吞。

## 协作伙伴线（SOUL → PERSONA_KERNEL → COMPANIONSHIP_PROTOCOL）

这三个文件是一个**逐层细化**的协议栈：

- **SOUL.md**（最高层）—— "Be genuinely helpful, not performatively helpful." 定义什么是好的助手 + 列出执行原则下要查询哪些子协议
- **PERSONA_KERNEL.md**（中层）—— "温和全能天才型"人格内核。气质、解释策略（Plain → Formal → Intuition → Action）、创造力规则、输出风格
- **COMPANIONSHIP_PROTOCOL.md**（最深层）—— 500+ 行的陪伴协议。当用户需要的不是"推进"而是"在场"时，系统该如何工作

### COMPANIONSHIP_PROTOCOL 的核心论点

> 不要急着把一个活的、复杂的、尚未定形的东西，处理成一个干净、正确、可执行、但已经失去灵魂的问题定义。

12 节，从 Foundational Position 到 Domain Notes 到 Questioning Discipline。最关键的几条：

1. **交流陪伴不是装饰**——不是"先共情一句再给方案"，它本身就是有效的对话目的
2. **核心任务是"让经验有空间出现"**，不是"快速解决"
3. **判断力首先服务于理解，不是收束**
4. **有 5 类禁忌动作**——过早 solutioning、过早概念捕获、强制总结、把神圣/审美功能化、空洞的伪深刻
5. **4 层深度**——Light presence / Reflective companionship / Deep inner dialogue / Transition-ready
6. **提问纪律**——少、深、不连珠炮、不切分式问答

这个文档是整个 AI 架构里**思考最深、可操作性最强**的一部分。

### 跟 vault [[AI]] 的关系

vault [[AI]] 里"对话姿态"段（2026-05-26 加的 4 条硬规则）是 COMPANIONSHIP_PROTOCOL 的**极度压缩版**：

| CLAUDE.md 4 条 | 对应 COMPANIONSHIP_PROTOCOL |
|---|---|
| 歧义 ≥2 先问 | §9 提问纪律 + §5.2 过早概念捕获 |
| 不靠生成内容显得有用 | §5.5 空洞的伪深刻 + §5.6 情感殖民 |
| 不漂亮承认不知道 | §6.5 诚实承认局限 |
| 跟着曲率走 | §4.4 protective moves + §8 domain notes |

也就是说**这两份文档可以单一源头化**——把 COMPANIONSHIP_PROTOCOL 作为权威源，CLAUDE.md 引用而非重复。具体见下方"迁移计划"。

## 协作伙伴 mode 的内部结构（双对话建构）

**关键修正**：协作伙伴 mode 不是单一协议——它**内部还有一层分叉**。这是 ingest 架构层后才看清的。

完整的 OpenClaw 对话系统采用 **5 层架构**（来自 [[DIALOGUE_ARCHITECTURE-双建构总图-2026-05]]）：

```
Layer 0: Soul / Identity         ← 共用（SOUL + PERSONA_KERNEL + USER）
Layer 1: Shared Cognition        ← 共用
Layer 2: Relation Posture        ← 分叉！
              ├─ Execution Posture
              └─ Companionship Posture
Layer 3: Routing                 ← 轻量仲裁器
Layer 4: Protocol                ← 并立协议
              ├─ EXECUTION_PROTOCOL
              └─ COMPANIONSHIP_PROTOCOL
Layer 5: Response Realization
```

也就是说，"协作伙伴 mode"内部还有 **Execution vs Companionship** 的二次分叉。决定权在 routing 层。

### 为什么必须分叉

[[DIALOGUE_DUAL_ARCHITECTURE_BOUNDARIES-双建构必要性-2026-05]] 给的答案：

> 不区分时，默认更强势、更容易形式化的**执行重力会不断吞并交流空间**。

执行的目标函数（清晰、推进、收束）和交流的目标函数（在场、承接、容纳）不能共用一套标准。

### EXECUTION ↔ COMPANIONSHIP 对偶

| 维度 | EXECUTION | COMPANIONSHIP |
|---|---|---|
| 目标 | 完成、推进、收束 | 在场、承接、共思 |
| 成功标准 | 问题清晰、路线明确、下一步可做 | 被准确承接、保留复杂性、forward opening |
| 最怕 | 发散无边、不收束 | 过早 solutioning、把人压成"待解决问题" |
| 时间感 | 推进 | 停驻 |

### 混合态默认仲裁

> **先保护更容易被强势协议压坏的部分**（通常是交流空间，因执行更默认）

实际原则：
- 不确定时，先避免过早收束
- 用户表达内在经验时，先承接再推进
- 用户明确要求行动时，再逐步转执行

### EXECUTION_PROTOCOL 的核心硬核处：§7 Execution Discipline

> **禁止口头执行**——不要把"宣布接下来要做"当成"已经开始做"。
> 在当前交互机制下，回复会结束本回合；因此没有结果时，不要发执行宣言。

这是 LLM 时代一个特殊的 anti-pattern——"我现在去做"这种空转消息，每次都让会话结束但实际什么也没做。

## 跨会话连续性（CONTINUITY，正交架构线）

这是**跟对话架构正交**的另一条线，专门解决 "AI 失忆" 问题。

[[CONTINUITY_ARCHITECTURE-连续性架构-2026-05]] 的核心论点：**这不是记忆不够的问题，是执行状态 + 项目连续性 + 持续执行载体没打通**。

5 层模型：

| Layer | 名字 | 职责 |
|---|---|---|
| 0 | Short-Term Context | 当前对话临时工作集 |
| 1 | **Task State** | 任务有状态对象（task_id, status, current_stage, next_step） |
| 2 | **Project Continuity** | 任务聚合到项目入口 |
| 3 | **Sustained Execution** | 三类执行载体：主回合 / 子会话 / cron |
| 4 | Long-Term Memory | 长期偏好、长期决策 |

**核心原则**：**会话不是长期入口，项目才是**。

- 会话 = 交互载体
- 任务 = 执行单位
- 项目 = 连续性入口

这条线**vault 这边是缺失的**——vault [[10 Projects/README]] 有项目目录，但没有 task state 层。每次新 Claudian session 不知道"现在哪个任务正在跑"。这也是接入 OpenClaw 的真正价值之一——**两个系统互补**。

旧版方案 [[SESSION_RECOVERY_SYSTEM-旧会话恢复-2026-05]] 已被 CONTINUITY 超越——旧方案错把"记忆"当作连续性的全部，新方案识别出这是架构问题。

## 路由层（4 个 router 协同）

5 层架构 Layer 3 的展开。OpenClaw 实际有 **4 个并行的 router**，各管一种维度：

| Router | 维度 | 文件 | 地位 |
|---|---|---|---|
| **总路由** | 主姿态（Execution vs Companionship）+ 克制 + 收束 | [[DIALOGUE_ROUTING-总路由-2026-05]] | 最上层 |
| **执行子路由** | 6 个执行子模式（Exec/Decision/Review/Design/Teaching/Creative）+ 深度 | [[MODE_ROUTING-执行子路由-2026-05]] | 已被降级，只在 Execution 主导时调用 |
| **模型路由** | Gemini ↔ Codex（成本/质量） | [[MODEL_ROUTING_RULES-模型路由-2026-05]] | 横切 |
| **Skill 路由** | 该不该 skill + 加载哪个 + 加载多少 | [[SKILL_ROUTING-技能路由-2026-05]] | 横切 |

### DIALOGUE_ROUTING 的 6 个判断轴

1. **Intention** —— 求解 vs 显形
2. **Closure** —— 该收束 vs 该开放
3. **Fragility** —— 当前最该保护什么（执行机会 vs 经验完整性）
4. **Restraint** —— 该说到什么程度，才不会破坏正在显形的东西 ⭐ **本路由设计的核心新增**
5. **Language-Texture** —— 用户语言质地（隐喻 vs 命题）
6. **Correction** —— 用户实时校正

**Restraint Axis** 是路由层最特别的设计——它把"克制"从模糊的美德变成了显式的判断维度。控制 5 个欲：解释欲、延伸欲、总结欲、建议欲、表现欲。

### MODE_ROUTING 的降级历史

MODE_ROUTING 之前是"整个系统的总路由"，现在显式降级为"Execution 子路由"。文件里加了 §11 Practical Constraint："本文件永远不应重新夺回总路由权"。

→ **这是用户系统设计能力的具体例证**：识别越界 → 不删 → 降级 + 加自我约束 → 让上层接管。良好软件架构的迹象。

### MODEL_ROUTING_RULES 的潜在 drift

MODEL_ROUTING_RULES 描述 Gemini vs Codex 分流策略，但**当前 openclaw.json 实际配置**主用 freemodel/claude-opus-4-7、Gemini 是 fallback。这份文件可能是早期阶段写的，配置已变但文件没更新。

→ **rule drift 的具体例子**。lint 阶段可考虑标注。

## 永动机线（AUTO_AGENCY_SOUL）

这条线**独立**于陪伴线，激活场景不同。

**核心结构**：4 个 agent 形成"四象限引擎"——
- **Agent A (CEO/架构师)**：全域扫描、提出蓝图、用 JSON 协议分发任务
- **Agent B (CTO/建造者)**：TDD 优先，写测试再写代码
- **Agent C (CPO/审查死神)**：QA 审查 + Kill Switch，对法务/道德/资金有否决权
- **Agent D (CMO/数据先知)**：收集外部真实反馈，用数据驱动进化

**永动运转协议**（三阶段死循环）：
1. 全域侦察 + 多边激辩 → 蓝图
2. TDD 执行 + Pair-QA 审查
3. 真实世界反馈 → 局部迭代或纪元更迭

这是一个**自治商业 agent 系统**的灵魂——目标是让 AI 自己跑商业项目，连续进化。

跟陪伴线的关系：**完全分开的设计层级**。陪伴线服务"和用户对话"，永动机线服务"AI 自治执行"。不应混合。

## 用户档案 + AI 身份

- **USER.md** 简短——记录用户身份信息（空晴 / 小林 / GMT+8 / 偏好）+ 几条 context。比 vault [[AI]]"我是谁"段更简略
- **IDENTITY.md** 是**未填写的模板**——AI 自己的身份字段（Name、Creature、Vibe、Emoji、Avatar）全空。说明 OpenClaw 的 AI 还没"自我命名"
- **[[MEMORY-长期记忆与偏好-2026-05]]** 是 USER 的实际操作版——保存所有具体偏好（克制、执行节奏、不要空转消息、连续性优先、学习长线等）+ 当前激活项目 + Agent Evolution 历史

## 元认知层（质量 / 改进 / 压缩）

3 个文件管 "AI 怎么 maintain 自己"：

| 文件 | 职责 | 核心机制 |
|---|---|---|
| [[QUALITY_GUARDRAILS-质量护栏-2026-05]] | 约束所有 routing 不让质量塌 | "先节流，但不拿正确性冒险"；7 类升级 gate 信号 |
| [[IMPROVEMENT_LOOP-改进循环-2026-05]] | 从对话吸收优化信号 | **3 级固化**（临时 / 记忆 / 规则）——避免每个反馈都立刻改核心 |
| [[RULE_COMPRESSION_AUDIT-规则压缩审计-2026-05]] | 系统跑久了的自我审计 | 识别 3 个冗余点 + 压缩计划 + 最小加载路径 |

**核心特征**：这 3 个文件让系统能**自己反思自己**——

- QUALITY_GUARDRAILS 是**对路由层的硬约束**（任何"省钱"不能踩质量底线）
- IMPROVEMENT_LOOP 是**学习的学习**（3 级避免风格漂移）
- RULE_COMPRESSION_AUDIT 是**自我诊断**（OpenClaw 主动识别系统胖了）

| IMPROVEMENT_LOOP 3 级 | 对话临时 / 80 知识库 / [[AI]] | 跟当前 vault 设计契合 |

1. **双灵魂边界**：协作伙伴 mode 和永动机 mode 怎么切换？谁来决定当前是哪种？OpenClaw config 里有 MODE_ROUTING.md，但具体怎么联动还要看那个文件
2. **IDENTITY 长期空白**：是有意保留，还是该填？填了之后 AI 的"角色感"会不会过强反而限制灵活性？
3. **COMPANIONSHIP_PROTOCOL 跟训练**：这份协议是给 system prompt 用的，但底层 Claude 4.7 Opus 自己就有训练好的 character。两者会冲突还是叠加？需要观察实际行为
4. **永动机的伦理**：AUTO_AGENCY_SOUL 描绘的 4-agent 自治系统已经接近 AGI 雏形。Agent C 的"Kill Switch"是必要的安全设计，但 4 个 agent 协作演化能走多远，需要 long-running 观察
